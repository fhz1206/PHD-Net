fix(P160): import torch_npu so the readout can actually reach the Ascend device

The diagnostic run from 2026-10-03 13:00 showed the environment is healthy:
torch 2.9.0+cpu imports, importing torch_npu 2.9.0 succeeds with device_count 1
and is_available true, the two versions are properly paired, and building a
tensor on npu through the project's own resolve_accel_device works. Step 2 had
reported no npu in torch's device table simply because it ran before
torch_npu was imported, so that was a measurement ordering artefact rather than a
real fault.

The actual bug was on our side. resolve_device in torch_lm only calls
probe_devices, which reports npu as available without ever importing torch_npu,
so torch's device table never gains npu. accel_readout had an import of
torch_npu inside its probe function, but it sat inside the probe so it repeated
on every attempt, and it was wrapped in a bare except that swallowed the failure,
which is why the production log showed fp8, fp16 and int8 all failing with a
device list containing no npu and offered no clue about the import itself.

The fix adds ensure_npu_registered to torch_lm as the single source, idempotent
and no longer silent, since it returns the exception text. resolve_device now
checks registration before trusting the probe's npu verdict and skips npu when
registration failed instead of returning a device that cannot allocate. The
probe function calls the same helper and raises with the reason attached when
registration is missing, so the cause appears in the degradation message.

One verifier detail worth recording: verify_accel_readout's interface completeness
case scans the whole repository for readout attribute accesses including text in
comments. Writing accel_readout._probe in a comment made it report a missing
_probe attribute, which was wrong since that attribute never existed on the class
either. Comments should avoid the module-dot-attribute form for that reason.
