P205a: NPU 流水线（nll 独立流 + p2 双流 H2D）+ CANN 接线器（--cann-dispatch 从核对器变接线器）

## 背景（用户指示：能否通过架构提前计算让 NPU 效率更高 + 优化 Cython/CANN 对接）
服务器 1b 档：step 12.3ms/tok，readout(NPU) 2.04ms = 8.5%，NPU 利用率
20-50% —— 本质是「NPU 每步只有 2ms 的活，却有 12ms 的周期」，NPU 大部分
时间在等 CPU。设计评估见 docs/P205a_NPU流水线设计.md（三层方案 + 为何
层 3「跨步 pipeline」不做：P117 已裁决——前移学习会改变 nll→task_gate→
主干学习率的时序，属学习规则层面的语义变更）。

## ① nll 独立流（架构级提前计算的核心）
`learn_softmax` 的 nll `.item()`（每 nll_sync_every 步一次）是 **CPU 硬
同步点**：它等的是**当前流**上全部 kernel（含读出更新 addmm_）。
改法：`_nll_stream.wait_stream(当前流)` 后再 `.item()` —— CPU 只等「nll
累积链」，同流后续 kernel 的提交不被阻塞（NPU 流水不断）。
- 数值语义不变（同一批累积值的和）；只是等待的流变了
- torch-CPU / 探测失败 → `_nll_stream=None` → 原路径逐位一致
- 懒初始化 + 幂等（`_ensure_streams`，CPU 上 ok=False → 两流 None）

## ② p2 双流 H2D（实现 P192 的死代码字段）
`_staged_to_dev` 的 H2D 提交到独立 `_h2d_stream`（此前同流 FIFO，排在
前面 kernel 之后）；消费方当前流 `wait_stream(h2d_stream)` 建立依赖
→ pinned 拷贝与上一 kernel 真并行。
- `_h2d_stream/_d2h_stream/_pinned_h_buffer/_async_ht_next/_async_event`
  五个字段此前**只声明从未使用**（P192 的 p2/p3 只有配置位没有实现）
- 数值逐位不变（ht 的值到达时点由 wait_stream 保证）

## ③ CANN 接线器（--cann-dispatch 实质化）
`cann_env.wire_dispatch()`：调 `torch_npu.npu.set_compile_mode(
jit_compile=False)` —— 官方文档「TASK_QUEUE_ENABLE 仅二进制场景生效」，
而 jit_compile 默认 True → **不调这句，TASK_QUEUE_ENABLE=2 一直白设**
（P120 以来从未解除的静默失效条件 ③）。
- train.py：`--cann-dispatch` 改为**先接线后核对**（wire → verify）
- 幂等：已是二进制场景则跳过；老版本 CANN 抛异常则如实报告 wired=False
- CPU/无 torch_npu → wired=None（不适用，不抛异常）
