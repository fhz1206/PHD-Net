fix(P144): fhz's question about Index overturned P143's conclusion

fhz asked whether aclnnIndex_IndexAiCore_Index might be an occupancy
measurement rather than real work. That question sent me back to the
aicore_time column, and P143's conclusion does not survive it.

Here is what the data actually says:
  Index (gather)     7,867,902 us   aicore_time = 0      wait = 53,268,212
  BatchMatMul         843,672 us   aicore_time = 842,527  wait = 142,059
  the other seven     4k-13k each  aicore_time = 0      wait all >> duration

So aicore_time = 0 is not missing data, it is a real zero. Index never occupies
the AI Core. A gather is a memory and vector operation, so it belongs on the
Vector/AIV unit, and its wait time is 6.8x its duration, meaning most of that
"duration" is spent waiting for resources rather than executing.

My P143 write-up said "Index is 89.3% and that is the bottleneck, so the fix is
in the gather kernel". That framing is wrong. msprof's Task Duration includes
queueing, and the AI Core is only actually busy during BatchMatMul, which is
1.41 ms per step out of 14.68. The correct statement is that the device spends
most of its time idle waiting for the CPU, because each step submits only twelve
small kernels.

Three independent measurements now agree: this msprof column, the P139
diagnostic where _staged_to_dev cost 54x more inside the loop than standalone,
and the 609% wait ratio in P142. All three say the same thing.

The direction therefore changes. It is not about swapping the gather operator,
which P134 and P135 already refuted twice. It is about pipelining, removing
synchronisation points, and letting the CPU run ahead of the NPU.

The analyser now also collects aiv_time, aiv_vec_time, aic_mte1_time and
aic_mte2_time, and prints a hardware-attribution table: over 50% AICore means
real matrix work, over 30% AIV means memory or vector work, over 30% transfer
means memory-bound, and wait far exceeding duration means the operator is not
slow, it simply is not being scheduled.

Lesson, and it is the third variant of the same failure. In P140 a static scan
reported confident false positives; in P142 a parser confidently printed a table
built from the wrong columns. This time the parse was correct but I looked at a
single dimension. Any device profiler metric raises the question of whether a
zero is a real zero or missing data, and reading one hardware unit tells you
neither what the others are doing nor how much of the time is queueing.
