perf(P134): wire the two official Ascend sparse paths, plus a gather-impl switch

fhz suggested trying third-party libraries for the NPU. Two official paths
exist and both match our shapes; a third is available immediately as a switch.

torch_npu.npu_gather_sparse_index - official custom operator, documented as
supported on both A2 and A3 training series. Signature
npu_gather_sparse_index(input, index) is semantically identical to our h[Wi]
(take elements of input's dim 0 by index). Its documented conditions for
actually gaining performance:
  (1) weight numel > 150*1024/itemsize -> ours 6,738,176 vs threshold 38,400  OK
  (2) index numel > 960               -> 6,738,176                           OK
  (3) "data must be aggregated, non-zero and zero distributions clustered"
      -> our h is a DENSE activation, so this is UNVERIFIED
Conditions 1 and 2 pass comfortably; 3 can only be settled by measurement.

aclsparseSpMM from CANN ops-sparse - documented to support CSR (exactly our
format; COO and CSC are not supported) and offers
ACL_SPARSE_SPMM_CSR_FP32_HIGH_PRECISION_ALG, a Kahan-compensated algorithm
that is kind to fp32. However torch_npu does NOT expose a Python interface, so
using it means binding aclsparse through ctypes and handling
aclrtStream/context/workspace lifetimes. This round only probes for the
library; the binding is not implemented and the tool says so explicitly rather
than skipping quietly.

New switch --readout-gather-impl index|take, default index (unchanged).
Measured on this x86 host at production dimensions (n_out=52,642, k=128,
n_h=3,072), best-of-5:
  (1) h[Wi] baseline          10.26 ms
  (2) index_select            11.03 ms
  (3) torch.take               5.94 ms   1.7x
  (4) einsum, full forward     3.87 ms
take and the baseline are BIT-IDENTICAL, which the tool verifies every run.
That 1.7x is CPU data and does NOT constitute Ascend evidence, so the default
stays on index and the choice is left to a server A/B.

New tool tools/bench_accel_kernels.py puts all six candidates on the same
device and the same tensors, reports best-of-N with the jitter ratio, and
checks numerical equality per candidate. On this host, with no torch_npu and no
ops-sparse, it degrades honestly and says what is missing.

Two mistakes of mine, both fixed:
1. Because a script edit failed twice and I retried, --readout-gather-impl got
   inserted THREE times, and argparse rejects duplicate option strings
   (compiles fine, only --help explodes). That is the P129 lesson repeating, so
   verify_ms_stream now has a dedicated duplicate-option assertion
   (43 -> 44 cases).
2. gather_impl was passed into _mk_readout, which constructs the numba
   Readout - a class with no _sp_gather and no such concept - giving
   TypeError. It now goes to the AccelReadout construction site. Discipline:
   when adding a parameter, confirm which class actually has that concept.
