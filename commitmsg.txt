fix(P130): three stacked defects in the npu-smi device-id resolution

Server evidence (2026-10-02 14:0x):
  [telemetry] could not determine NPU device id -> no -i, HBM-bw may stay empty
  [telemetry] `npu-smi -t usages` parsed no fields; rc=215
  This command must input card id.
fhz confirmed by hand that the subcommand genuinely requires a card id.

Three defects, all introduced when the telemetry was added:

1. The `npu-smi info -l` regex was wrong. It was written `^\s*(\d+)\s`, i.e. for
   table rows, but that command prints Key-Value lines. Both real forms must be
   recognised - `NPU ID : 0` (Huawei docs) and `NPU : 0` (observed) - while
   EXCLUDING count lines like `Total : 8` / `Card Count : 8`, which would
   otherwise be picked up as the id.

2. Only the readout instance's `.device` was consulted. On the server that is an
   AccelReadout and does have it, but the numba Readout fallback has no such
   attribute, so getattr returned None and the code silently degraded to running
   without -i. Now three sources in descending reliability: the PHD_NPU_ID
   environment variable, the digits of the device string, then `npu-smi info -l`.

3. The backend description string `accel:auto@npu` carries no digits, so even
   once passed in it yielded no card id. Added a fallback: if the string mentions
   npu/cuda/rocm, assume card 0 and say so once. The risk is recorded in the
   comment - on a multi-card box bound to another card this reads the WRONG card,
   which still yields valid numbers but not for this process, so PHD_NPU_ID
   exists to correct it.

Also added `-c <chip_id>`, since essentially every official and observed sample
uses `npu-smi info -t usages -i 0 -c 0` (including
`watch npu-smi info -t usages -i 0 -c 0`). Overridable via PHD_NPU_CHIP_ID.

Gate: verify_cann_env.py section E grows 5 -> 9 cases (-c present / env vars /
both -l formats / no-index fallback), 30/30 overall. fast 9/9, ms_stream 43/43,
accel_sparse 31/31, accel_readout and powlaw PASS, local smoke zero crashes.

The lesson is the same one for the third time: I guessed the external CLI's
argument shape twice in a row (first missing -i, then missing -c and parsing -l
wrongly). Anything that shells out to a device tool must have its full argument
form confirmed against the official documentation first, and must keep a "print
the raw output once on failure" hook. The hook is in place now, and it is what
surfaced rc=215 and pointed straight at the root cause - with it still silent
this would have been the fourth round of "I could not find it".
