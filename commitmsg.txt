perf(P132): add a per-segment readout benchmark - stop guessing from x86

fhz asked whether readout can be made faster. Short answer: yes, but not by
guessing on this host - I have now guessed wrong three more times.

What I measured here (x86, best-of-5), all wrong or useless:
  chunking so gather fits L2        0.83-0.91x (slower; just adds kernels)
  idx int64 -> int32 (saves 25 MiB) 0.58x (halved throughput; type conversion)
  index_select / take instead of    0.92-0.93x (no difference)
    advanced indexing
  embedding(W, Wi) fused            0.02x (catastrophic - it is a lookup, not a sum)
  CSR SpMM A @h                     15.1 ms (slower than einsum; x86 has no good
                                    SpMM kernel)
The revealing one: at smaller sizes the gather costs only 1.38 ms, so "gather is
slow" is ASCEND-SPECIFIC, not an intrinsic property of the algorithm. Any
optimisation aimed at it has to be driven by Ascend measurements, not by x86
relative timings.

Traffic accounting per step at 1b tier, total 152.6 MiB:
  idx read (int64)   50.7 MiB   33%
  W read + write     50.7 MiB   33%
  g read + write     50.7 MiB   33%   <- einsum already removes this (P131)
  y read + write      0.4 MiB
So einsum removes a third of the traffic and 10.99 ms should land near 7.3 ms.
Being straight about the target: 5 ms is NOT reachable by swapping kernels
alone, because the remaining three items are each a third and W cannot drop to
fp16/bf16 - P110 measured that doing so destroys the perceptron update rule.

New tool tools/bench_readout_segments.py. It times each stage in dependency
order: (1) H2D of h, (2) gather, (3) mul+sum, (4) einsum, (5) forward total,
(6) softmax+CE, (7) update addmm_. Every stage is best-of-N and prints its
jitter ratio; anything above 1.3x is labelled "noise dominated, not a basis for
optimisation" so a single noisy sample cannot be mistaken for a finding.

It handles both the sparse accelerated arm (torch tensors) and the dense
numba fallback (numpy arrays) - running it here end to end is what proves
neither path crashes. On this host it reports the CPU fallback, so its numbers
are reference-only; run it on Ascend for the real breakdown of that 10.99 ms.

Gates: fast 9/9, py_compile clean, bench --help exit 0.

Lesson, and it is the fourth time: every wrong conclusion about "readout is
slow" came from measuring on x86 and extrapolating to Ascend. This project has
now recorded seven platform direction reversals. For anything device-side,
segment-measure on the device first and only then choose an optimisation; the
local host is for checking that the code runs, not for predicting speed.
