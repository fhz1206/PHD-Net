perf(P128): enable torch.compile fusion for the sparse readout - the actual NPU bottleneck

Root cause: the sparse readout has never used the fused kernel.

In accel_readout.py the construction site had `if w0 is None and not
self._sparse:`, which excluded the sparse readout - i.e. the PRODUCTION default
since P108 (conn_k=128) - from compilation. It therefore ran per-op eager every
step. Meanwhile learn_softmax's runtime branch (`if self._compiled:`) has always
supported sparse. The fused kernel existed; sparse could never reach it.

Why this is the prime suspect for "the NPU is not fast enough":
- 2026-10-02 server log: readout 10.99 ms, 64.7% of the step, and 36x the
  bandwidth floor of 0.300 ms.
- The P115/P120 reading rule (high AICore plus low bandwidth means the
  bottleneck is kernel dispatch) points straight at per-op eager - many small
  kernels, one launch each.
- The magnitude is estimable: our own comment records "launch ~50-200 us/kernel
  on CANN, 5 per step", i.e. roughly 0.5 ms/step of pure launch overhead.
  P128 fuses softmax/log/sub/addmm_ into one.
- P58 turned compilation off with the reason "inductor is unstable on the
  server", but back then the sparse path could not use it at all, so that
  instability was probably a different problem misattributed. This is recorded
  in config.py, but THE DEFAULT IS STILL OFF - P58 was fhz's explicit
  instruction and I am not unilaterally reversing it.

Verification
- Local measurement (8192 x 3072, k=128): eager 6.690 ms -> compiled 6.298 ms,
  1.06x. The x86 gain is small precisely because launch overhead is a smaller
  fraction there; on NPU it should be materially larger (unverified).
- Numerically BIT-IDENTICAL: both W and nll match exactly (max|delta| = 0).
- Premise checked: _train_step_core contains no _sparse and no conn_k branch,
  so enabling it for sparse is safe.
- Gate C4d (4 cases) added, including "runtime fallback to eager is correct
  behaviour, not a FAIL" - that matters because this host cannot compile.
- Gates: accel_sparse 22 -> 31, fast 9/9, cann_env 26/26, powlaw 32/32,
  accel_readout PASS, --help exit 0.

Server A/B (this is the decisive test)
  python train/train.py --preset 1b --data pretrain --remote-data \
      --step-profiling --torch-compile
  python train/train.py --preset 1b --data pretrain --remote-data \
      --step-profiling
Compare the readout segment in segments(win). If the fused run is clearly
faster, changing the default becomes justified. If it warns "torch.compile
fusion kernel failed, permanently falling back to eager", capture that warning
and investigate it - that would mean the P58 instability was real after all.
