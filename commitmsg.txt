perf(P137): the async-wait hypothesis is dead; add per-line profiling inside the readout

Section 8 from the Ascend run (1b tier, production dimensions) settles two things
by ruling the others out:
  items 1-7, bare operators, total      ~0.35 ms
  8a real step, submission basis15.147 ms  jitter 1.0x
  8b real step, sync basis                15.204 ms  jitter 1.0x
  training log readout                    10.99 ms

Hypothesis 1, that the cost is asynchronous waiting or dispatch queueing, which
I proposed in P135, is dead: 8a equals 8b to within 0.5%. Enqueueing and
completing cost the same, so synchronisation is not the bottleneck.

Hypothesis 2, that the 100 MiB update is the cost, is also dead: the addmm_
update measures 0.061 ms. A corollary is that there is no room on the gather
side at all - the official npu_gather_sparse_index is 0.034 against a 0.020
baseline, and torch.take at 0.016 is inside the noise.

What remains: 8b matches the training log to within 0.7% (the benchmark is
slightly higher because it carries more Python overhead and no CPU/NPU overlap),
so 8b IS the real production cost. The remaining 14.8 ms is spent in code that
sections 1 through 7 never touch, and bare operator benchmarks cannot see it -
that requires instrumenting inside the production functions.

New tool tools/bench_readout_lineprofile.py. It uses sys.settrace to time
individual lines in seven readout methods only, prints the top-N most expensive
lines with their source text, and classifies each by what it is - .item() or
synchronize or an H2D copy means a synchronisation cost, plain Python tensor
arithmetic means a host cost. The limitations are recorded in the tool itself:
settrace costs 0.1-0.3 ms per line so absolute values are inflated and only the
relative ranking and the top line should be read; and on this host, which takes
the numba fallback, it cannot reproduce 15 ms at all, so it is only meaningful on
Ascend.

A mistake of mine inside this tool, worth recording. The first version computed
per-line attribution as t0 minus _last[0], where t0 was captured on function
entry while _last advanced on line events. Line events can precede the function
entry stamp, so every delta came out NEGATIVE: on this host the whole table
printed negative times and negative percentages, yet nothing raised. It now uses
each line event's own timestamp minus the previous line event, plus a filter
that discards negative values. The lesson generalises: a measurement tool whose
output is not sanity-checked for impossible values - negative durations,
percentages above 100 - is the same as having no output.
