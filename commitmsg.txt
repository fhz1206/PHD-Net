fix(P142): the timeline parser silently read the wrong columns; refuse to guess now

The msprof collection worked - 2.0 MiB of op_summary came back. Its real columns
are:
  Device_id, Model ID, Task ID, Stream ID, Op Name, OP Type, ..., Task Start
  Time(us), Task Duration(us), Task Wait Time(us), ..., aicore_time(us),
  aic_mac_ratio, aic_scalar_ratio, aic_mte1_ratio, aic_mte2_ratio, ...,
  cube_utilization(%)

My parser was broken in a way that produced a confident, entirely wrong answer.
It matched column names by exact equality against a list containing 'op name'
and 'task duration', neither of which is an actual header, so every lookup missed
and it fell back to guessing by position. It guessed columns 1 and 3, which are
'Model ID' and 'Stream ID'. So it read the operator name as 4294967295 - the
value of Model ID - while still printing a full table. Nothing about the output
looked wrong. The "uncovered operators are 100% of the total" line in that run
was fiction.

Two fixes. Column matching now uses substring containment, which is what these
headers need. And when recognition fails the tool no longer guesses: it prints
the real header, prints what it expected, and exits 3. Verified against a
synthetic timeline built with the genuine 46-column header, including
Casting, Malloc and Memset with different aicore split, and it now names them
correctly and reports the AI Core versus queueing breakdown.

The more valuable part of that header is not the operator list at all. msprof
emits aicore_time for how long the AI Core was actually busy, aic_mte1_ratio and
aic_mte2_ratio for memory movement, aic_mac_ratio for matrix work, Task Wait
Time for queueing, and cube_utilization. Those answer the question directly.
High aicore share means the device is genuinely computing and the problem is
real work; high mte ratios mean it is memory-bound; high wait time means it is
queued for resources. The parser now emits a "where the time goes" table with
AI Core share versus queueing share, plus the median cube utilisation.

Second instance of the same lesson, after P140's false positives. Both times a
tool was handed data it could not read and returned something that looked like a
conclusion. A static scan reported fifteen confident false positives; a parser
reported a confident table built from the wrong columns. The rule I want to keep
is narrow and mechanical: a parsing tool must refuse to produce a result when it
cannot find the fields it expects. Silently degrading into a guess is strictly
worse than failing, because the output is indistinguishable from a real finding.
