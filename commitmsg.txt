fix(P127): three silent failures found by reading the server log - HBM-bw, cann-env, AICore>100%

Read train_1b_1b_pretrain_20261002-130316.log (1b tier, Ascend 191 cores + NPU,
--lang zh) and found three things that had been failing quietly. None could have
been caught locally.

1. HBM-bw never appeared (0 occurrences in 59k tokens)
   npu-smi info -t usages was being called WITHOUT -i <id>. The official
   command form is `npu-smi info -t usages -i id`. The signature in the log is
   distinctive: "[telemetry] npu-smi = ..." was printed and there was NO
   "parse FAILED" - meaning the command ran fine but produced nothing we could
   parse. Added _accl_device_id() (parses the digit out of `npu:0`, falls back to
   `npu-smi info -l`) and, crucially, made a parse failure print the raw output
   once instead of staying silent.
   This is the metric the whole "is the NPU actually being used" argument rests
   on, and it was never producing data.

2. The [cann-env] block never reached the log file
   It printed at module top level, where sys.stdout is still the terminal;
   `sys.stdout = TeeLogger(log_path)` only happens ~400 lines later inside
   main(). So the four CANN variables were only visible on the console and
   absent from the file fhz actually reads. Now applied silently, the report is
   kept, and replayed right after the TeeLogger is installed. Labels are pure
   ASCII on purpose: this prints after install_stream_filter(), and Chinese
   literals get rewritten by the translator (it once produced "run 环境").
   Also fixed the provenance tag - it was reading os.environ to decide
   "user-set", but those values are what this same process just set.

3. AICore reported 102-106%
   Above 100% means the field is not a percentage the way we are formatting it
   (possibly a busy-cycle ratio or a multi-core aggregate). Telemetry prints it
   with an uncapped format. Needs the official definition checked before we
   quote it; for now the number should not be read as "the NPU is 106% busy".

Also clarified tools/rebaseline.py's "connectivity 12.5%": that comes from
lm.net.pc.stats(), i.e. M2 trunk connectivity, not the M6 readout (128/3072 =
4.2%). Label now says [M2 trunk].

Performance note for the record: end-to-end is 15.84 ms/tok versus P113's 12.09 -
the readout went 7.83 -> 10.99 ms. Cause not yet established. P123's nogil only
touches CPU kernels so it should not affect the NPU, and P120's
TASK_QUEUE_ENABLE=2 should if anything be faster. Needs a server A/B; local
reproduction is not possible.

Gate: verify_cann_env.py gains section E with five cases (usages carries -i /
warns when the device id is unknown / reports raw output on parse failure /
train passes the device id / id-parsing regex), now 26/26. fast 9/9,
--help exit 0.

Lesson, and it is the same one as B18: "the code looks right" plus "it runs
locally" does not mean the feature works. Both the bandwidth telemetry and the
CANN environment governance were written without hardware verification and both
failed silently. Anything that can only be checked on real hardware needs a
"print the raw output once on failure" hook, or it stays undebuggable forever.
