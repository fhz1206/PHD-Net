perf(P165): speed up M1 by 3.24x with a runtime probe and an ILP GEMV kernel

fhz asked to accelerate M1 and M2. M1 measured 860.8 microseconds per call with
8.4 MB of weight traffic, which is only 9.8 GB/s, far below what memory can
deliver.

For M1 two changes landed. First, the dispatch no longer keys off the platform
name. P77 had used machine().startswith("aarch64") as a proxy for whether BLAS is
slow, but that is a property of the OpenBLAS build rather than of the architecture,
and it cannot notice a fix in a newer build or a change of CPU. There is now a
_process-level probe that times BLAS against the numba kernel once per dtype and
caches the answer, so the choice follows measurement instead of a hard-coded name.
Second, the kernel now uses four independent accumulators inside each row instead
of a single serial dependency chain, which is what had been capping throughput at
10.5 GB/s. The ILP version reaches 13.1 GB/s on its own, but the probe is what
matters: numpy BLAS runs this GEMV at 56.9 GB/s, about 41GB/s of effective
saturation, which is 5.4 times the numba kernel under fp32 and 56.9 GB/s versus
10.5. End to end the encode call drops from 860.8 to 265.8 microseconds, 3.24 times
faster. The ILP kernel is bit-identical to the original under fp32 and differs by
about one ulp under fp64, and PHD_GEMV_ILP=0 restores the exact-arithmetic path.

For M2 the work is measured but deliberately not applied. Inference breaks down as
603 microseconds of matvec, which is 75 percent, plus 198.9 microseconds for eight
tanh calls at 15.3 each plus clip, subtraction and allocation. Every candidate
failed. Narrowing the index to int32 and the weight to fp32 halves traffic from 16
to 8 bytes per edge yet measured 75.9 against 75.4 microseconds, so traffic is not
the bottleneck. Dropping prange made it 2.6 times slower, which says the matvecs
are already being parallelised. The two-accumulator ILP variant was slower and not
bit-identical. The fused kernel beats plain by 1.16x on x86, but P113 measured the
opposite on Ascend where plain was 5.41 times faster, so changing the default path
would be betting against the platform that actually runs production. That waits for
a measurement on the server.

A side finding worth recording is that tools/bench_local.py hardcodes fp64 while
production is fp32, so it cannot see the M1 gains at all; its 860.8 to 923.9
microsecond movement is fp64 noise. That is a real gap in the benchmark and is
queued for a separate fix.

New gate tests/verifiers/verify_encoder_gemv.py covers the probe's caching and
idempotence, the ILP kernel's bit-exactness under fp32 and its one-ulp drift under
fp64, the absence of the platform-name check in code with comments stripped, and
end-to-end encode under both dtypes. Two of its checks failed on first run for
reasons of my own making, since a fixed 1e-12 tolerance can never pass for fp32
whose epsilon is 1.19e-7, and because the aarch64 string legitimately survives in
comments; both tolerances are now dtype-derived and the source is stripped before
inspection.
