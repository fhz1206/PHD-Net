fix(P159): add a torch_npu registration diagnostic after the readout fell back to CPU

The production log from 2026-10-03 12:56 on Ascend910B4 with torch 2.9.0+cpu and
torch_npu 2.9.0 shows the readout running on numba-cpu rather than the device.
The reported fallback reason is that no precision is available on the auto
device, with the fp8 attempt failing on a message listing the device types torch
knows: cpu, cuda, ipu, xpu, mkldnn, opengl, opencl, ideep, hip, mps, meta, hpu,
xla.

That list contains no npu at all, which means this is not fp8 being unsupported.
torch_npu never registered npu as a device, so even an ordinary fp16 tensor
cannot be created. Since the precision probe genuinely allocates, fp8, fp16 and
int8 all fail, the degradation chain runs out of options, and the readout falls
back. The capability line claiming device npu:0 is available is not a
contradiction but a shallower check, since it never imports torch_npu.

Two other log lines point at the cause: CANN was not detected, and there is an
owner and permission mismatch warning for /usr/local/Ascend/cann-8.5.0. Torch
being the +cpu build also matters because torch_npu requires a strictly matched
torch.

The new tools/diag_torchnpu.py walks six steps: environment facts, torch device
table, the actual tensor allocation, importing torch_npu, version pairing, and
finally the project's own resolve_accel_device. Its decision tree separates an
environment problem from an import-order problem from a genuine regression. It
exits zero on machines without an NPU.

This also updates a rule for the project: that a device-detected line cannot be
taken as evidence the readout is on hardware, since it has now been shown to be a
false positive. The only valid evidence is the per-token readout timing line that
names the backend and device.

Gates: fast 9/9, accel_readout, precision_policy and cann_env all PASS, the
diagnostic exits zero.
