## 一、并行性模型：这个系统能并行什么、不能并行什么

### 1.1 根本约束：逐 token 语义禁止数据并行

`PHDNet.step`（`phdnet/model.py:204-459`）不是「一批样本过一遍网络」，而是
**一个时间步内把六个机制按固定顺序串起来、每个机制都原地改写自己的持久状态**。
把 `step` 的机制序列摊开（`model.py:227-452`）：

| 序 | 机制 | 源码位置 | 原地改写的状态 |
|---|---|---|---|
| 1 | M1 稀疏编码 | `model.py:228` | `encoder.W`（`learnable_encoder` 开启时） |
| 2 | M2 预测编码推理 | `model.py:231` | —（纯前向，读 CSR） |
| 3 | M3 时序预测 | `model.py:237,246` | `stdp` 的迹、`_prev_rate` |
| 4 | M5 神经调制 | `model.py:254` | 调制器内部状态、`_last_da` |
| 5 | M4a 工作记忆 | `model.py:263-272` | `wm.slots` / `wm.strength`（先 `decay()` 再 `write()`） |
| 6 | M4b 长期记忆 | `model.py:289-306` | LTM 的 CSR（`imprint`）/ WM 槽位（`recall` 回写） |
| 7 | M6 读出 + 更新 | `model.py:316-341` | `readout.W`（`addmm_` / 稀疏 `add_`） |
| 8 | 全模块局部学习 | `model.py:378-452` | `pc` 的 CSR、`stdp.W`、`encoder.W`、`_prev_pc`、`_exp` |

关键在于**这些状态全部跨 token 连续演化，且演化顺序不可交换**：

- `model.py:451-452` 把本步的 `rate` 与 PC 缓存写进 `_prev_rate` / `_prev_pc`，
  它们是**下一步** M3 预测与 T1.2 预测编码目标的输入。跨 token 串行不是实现选择，
  是这份代码的显式数据结构。
- `model.py:455` 的 `step_count += 1` 决定 LTM 检索节奏
  （`model.py:283-288`：`step_count % retrieve_interval`）、回放节奏、摘要槽节奏。
  跳步就等于改写记忆的行为。
- M4b 的 `imprint` 走 `bigltm.py:140-141` 的 `self.table.learn(self._prev, cur)` ——
  **成对学习**。第 t 步的写入依赖第 t−1 步的活跃集合。并行两个相邻 token 就等于
  删掉了这对共现关系。

训练入口把这件事打印成了一行契约（`train/train.py:719-720`）：

> `[context] state never reset (WM/STDP/LTM carried continuously across samples/shards/epochs)`

跨 epoch 时的 `prev` 断开也是显式实现的（`train.py:801-806`：`p2, _ = None, True`
+ `first step's prev link severed`）—— 即便语义上允许断，也只断在 epoch 边界，
而不是断在并行分组边界。

**推论（本文的第一条结论）**：系统**没有 batch 维**（`step` 的签名是
`step(x, target=None, ...)`，`x` 是单个 token 的组合编码），也**没有梯度**
（`learn_softmax` 用的是感知器局部梯度 `p − t`，见 `accel_readout.py:407-416`；
`pc.learn` 用的是误差驱动 + Oja，无反向图）。DDP 需要 all-reduce 梯度、
DataParallel 需要 batch 轴——**两者在本架构下都没有作用对象**。
这不是实现缺陷，是语义约束的直接后果。

### 1.2 唯一可并行的维度：机制内部的行级 / 条目级

排除数据并行之后，可并行的只剩「同一个 token 内部互不依赖的行或条目」。
逐条核对源码，并标注每条**是否已被实测否掉**：

| 维度 | 源码依据 | 现状 |
|---|---|---|
| **M2 CSR matvec 行级** | `sparse_pc.py:43-53` `_csr_matvec`：`parallel=True` + `prange(n)`，行内按 `indptr` 顺序累加、行间并行 | ✅ **未被否，且 P113 实测 5.41×，现为默认**（§1.3.1） |
| M2 融合推理核 | `sparse_pc.py:216-273` `_pc_infer_fused`：`parallel=True`，**10 个 prange 区** | **已否**（昇腾慢 3–4×） |
| M2 学习融合核 | `sparse_pc.py:302-356` `_pc_learn_fused`：8 个 prange 区 | 已上线，`homeostasis=True` 时**刻意不走**（`sparse_pc.py:299-300`：e0p/e1p 需在核外归一化） |
| M2 `learn_predictive` 融合 | `sparse_pc.py:549-551` | **已否并停用**：26 万边 1.36× / 105 万 0.96× / 419 万 0.91×。函数保留（删除会让回归护栏失去被测对象） |
| M4b imprint 逐行 | `ltm_kernel.py:84-142` `_ltm_learn_rows`：`prange(R)`，行内与原版同序；门槛 `BATCH_MIN_COMBOS = 4096`（`sparse_table.py:209,320`） | 已上线，但**收益完全押在服务器侧，该结论至今未复测**（性能文档 §4.3） |
| M4b recall 反投影 | `ltm_kernel.py:65-81` `_recall_project`：**串行**，因为不同大空间索引共享同一输出维度 → prange 会写竞态（`ltm_kernel.py:16-18`） | **结构性不可并行**，不是调优问题 |
| M4b `encode` 去重 | `bigltm.py:113-135` 走 `dict.fromkeys`（C 层保序去重） | **已否**：核内 O(n²) 线性去重 0.84×，输给 Python 的 O(1) 哈希 |
| M6 读出更新行级 | `readout.py:35-45` `_ro_dense_update`：`prange(n_out)`，元素级独立、无跨行归约 | 已上线（numba 路径） |
| 词表扫描 / 分词 | `tokenizer_core.py:238,303` `njit(nogil=True)` | **已 nogil 化** → 线程化才有意义（GIL 已释放） |
| 词涌现层间并行 | `vocab_parallel.py:120` `ThreadPoolExecutor`（5 个 L 各自 nogil 核）；核内 prange 固定传 `nthreads=1`（`word_induce_numba.py:51-57`，P22 实测 1→6 线程仅 1.16×） | 已上线 |

**必须澄清的一处常见误读**：纯 Python 热路径（未 nogil）线程化在 CPython 下无效，
因为 GIL。这不是本项目的结论，而是前提条件——所以「先 nogil 再谈线程」
在本仓库的落实情况是：`tokenizer_core.py` 与 `word_induce_numba.py` 已 nogil，
而 `bigltm.py:121-135` 的 `encode`（`dict.fromkeys` 已在 C 层，但外层
`chain.from_iterable` 与列表推导仍在解释器里）**没有** nogil 化，也**不该**再化
（实测已否）。

### 1.3 P76 否掉的是「prange 融合」，不是「CSR 行级并行」

这是本文档最容易被写错的一处，因此单列。

`sparse_pc.py:473-497` 的 `infer()` 是一个三态分派：

```
fused == "serial"  → _pc_infer_fused_serial   （P99，无 prange）
fused 为真          → _pc_infer_fused          （P52，10 个 prange 区）
fused 为假          → 原始 5 次 _csr_matvec    （P75，每次调用内部有 prange）
```

昇腾上被实测否掉的是**第二条**（fused 20–27 vs plain 6.7–11.9 ms/tok，慢 3–4×）。
根因写在 `sparse_pc.py:613-623`：10 个 prange 区的 fork/join 屏障成本，
在「很多核 + 小矩阵」（1B 档 1024 行 × 128 边）上远大于计算本身。
P99 因此新增了第一条（去掉 `parallel=True`，保留融合的「一次调用 + 核内复用中间数组」）。

**但第三条从未被否**。`_csr_matvec` 自 P43 起就是 `parallel=True` + `prange(n)`
（`sparse_pc.py:43-53`），它的并行粒度就是 CSR 的行——1B 档是 1024 行，
行内 128 条边，是**真正与融合核无关**的另一个维度。

### 1.3.1 ✅ P113 结论：第三条赢了，已成默认

`--m2-kernel plain` 曾经是「一个未验证的候选」。**P113 已在服务器上验证并采纳为默认**：

| 项 | 值 | 口径 |
|---|---|---|
| `M2_infer` | 6.92 → **1.28 ms/tok（5.41×）** | 1b 档，昇腾 191 核 + NPU，`[日志]` |
| 端到端 | 17.63 → **12.09 ms/tok（1.46×）** | 同上 |
| 零回归 | 四个采样点（10250/20250/30250/40250 token）sliding PPL **逐位相同**：38101.949 / 25042.421 / 22693.449 / 19602.394 | `[日志]` 跨 run 观测 |
| 受控门禁 | `tests/verifiers/verify_m2_kernels.py` **11 例三态对拍** | 同进程、同输入 |

⚠ **历史值标注**：上表 6.92 / 17.63 是 **serial 口径（历史对照）**。
另有一组更早的 plain 值 6.7–11.9 ms/tok（P76 A/B 期间，**线程配置未标**），
与 1.28 **不是同一口径**，两者不可比。

⚠ **两条纪律**：
1. 写文档/做决策时不要把「prange 融合核被否」写成「CSR 行级并行被否」。
   **这条现在有实测背书，不再是推论。**
2. ⚠ **但不要把「plain 赢了」推论成「191 核被吃满了」**。
   M2 赢 5.41× 之后，**进程实际用核数几乎没变（1.1 / 191）**，
   因为 CPU 侧整体只有 4.26 ms（§2.1），且 `--numba-threads 8` 之上就是访存饱和区（§2.3）。
   **「M2 不再是单核」≠「核用满了」** —— 这两件事必须分开说。

### 1.4 逐位对拍是这些维度的存在前提

并行化的每一条都必须证明「并行版与串行版逐位相同」，否则无法排除语义漂移。
仓库用两个 verifier 把关：

- `tests/verifiers/verify_parallel_consistency.py:78-122`：五个 CSR 核
  （`_csr_matvec` / `_csr_add_outer` / `_csr_oja_up` / `_csr_row_norms` /
  `_csr_scale_rows`）的 prange 版对 numba 串行版逐位对拍，含零行（触发 skip 分支）。
  第二部分（`:126-172`）对拍 zh 多进程流与串行参考。
- `tests/verifiers/verify_multi_device.py:124-136`：读出 4 路分片与单设备
  前向 / NLL / 更新后权重**逐位**一致。

⚠ 逐位对拍的基线必须是**同库、同 fastmath 口径的串行实现**——
用纯 Python 当基线会得到满屏假阳性（`BUGS.md#E1`）。这条纪律是本文所有
「已并行 / 未并行」判断的可信度前提。

### 1.5 数据侧：进程只做跨文件并行

数据侧的并行与模型侧的并行是**两件事**，不要混算进「核利用率」。
`corpus_stream.py:113-170` 的 `PrefetchChars`：

- 进程数 `w = min(PREFETCH_MAX_PROCS=8, cpu, len(files))`（`corpus_stream.py:48,161`）
- 每进程解码核 `decode_threads = max(1, cpu // w)`（`corpus_stream.py:167`），
  在生产者内通过 `pa.set_cpu_count(decode_threads)` +
  `pa.set_io_thread_count(max(1, decode_threads // 2))` 分摊（`corpus_stream.py:68-69`）

191 核下按 `auto_workers() = cpu × 0.8 = 152`（`vocab_parallel.py:77-79`）计算：
**8 进程 × 19 解码核 = 152**，`train.py:403-408` 会把这行算式打印出来。
所以「191 核用不满」在数据侧的表现是**预期行为**：多核来自
（a）主进程 numba nogil 线程 +（b）生产者内 pyarrow 解码线程池，
不来自 191 个进程。

⚠ **不要再往进程数上加**。两个源码约束：
1. `corpus_stream.py:113-129` 的设计说明记录了原因——解码在 pyarrow 内自身多线程
   且释放 GIL，进程数越多，每进程一份 Python + pyarrow 上下文（~100–200 MB）
   线性增长。
2. `train.py:359-360` 明确记录：**153 进程实测崩过**（超订 + 内存爆炸）。

⚠ **一个必须分清的层次**：`train.py:623-626` 里，**词表全量扫描阶段**的
多生产者数与**训练稳态预取**的进程数是两个不同的量
（前者 `min(16, 文件数, cpu_count)`，后者 `min(8, cpu, 文件数)`）。
`docstring` 里的「层间线程池」（`vocab_parallel.py:120`）也属于**词表构建阶段**，
不在 M4b 也不在训练稳态路径上。

## 二、实测证据：CPU 与 NPU 严重不对称

### 2.1 三个数字同时成立，才是本项目的核心事实

稳态（1B 档，昇腾 191 核 + NPU，P113 / `--m2-kernel plain`）：

| 观测 | 值 | 口径 |
|---|---|---|
| 端到端 | **12.09 ms/tok** | `--m2-kernel plain`（P113 现行默认） |
| 读出（NPU） | **7.83 ms/tok，64.7%** | 后端 `accel:npu` |
| `M2_infer`（CPU） | **1.28 ms/tok，10.6%** | ✅ **行级 `prange`**（`plain` / `_csr_matvec`），**不再是单核** |
| CPU 侧合计 | **4.26 ms/tok，35.2%** | 端到端 − 读出（**本文复算**） |
| 进程实际用核 | **1.1 / 191（0.6%）** | `time.process_time` 差 / 墙钟差 |
| CPU 系统占用 | **1–2%** | `psutil.cpu_percent` |
| NPU AI Core | **99%** | `npu-smi info` 子进程 |

**与 P113 前（serial 口径，历史对照）的对照**：

| 量 | serial（P113 前） | plain（P113 现行） | 倍数 |
|---|---|---|---|
| 端到端 | 17.63 | **12.09** | 1.46× |
| `M2_infer` | 6.92（**单核**） | **1.28**（行级 prange） | **5.41×** |
| CPU 侧合计 | 9.95 | **4.26** | 2.33× |
| 读出占比 | 43.5%（7.68 ms） | **64.7%**（7.83 ms） | — |

**这四组数字必须一起读**：读出（NPU）已占 64.7% 且 AI Core 满载，
CPU 侧只剩 4.26 ms（35.2%）而只用掉 0.6% 的核。
**不对称的方向在 P113 之后翻转了** —— P111 段是 CPU 侧占一半、NPU 侧 43.5%；
现在是 NPU 侧是大头。

⚠ **不要把「M2 不再单核」读成「核用满了」**：进程用核数仍是 1.1 / 191。
原因见 §2.3 —— CPU 侧总量只有 4.26 ms，且线程上限之上就是访存饱和区。

### 2.2 三个原因，三种解法：**(a)(b) 架构性仍在，(c) 已解决**

「191 核用不满」这个观测背后有**三个互相独立的原因**。
把它们混成「算力不足」会导致错误的解法：

| # | 原因 | 性质 | 对应的解法方向 | 现状 |
|---|---|---|---|---|
| (a) | 逐 token 语义禁止数据并行（§1.1） | **架构性** | 无解——除非放弃逐 token 语义 | **不可解除** |
| (b) | 可并行的机制内维度太少、且多为结构性串行（§1.2） | **架构性** | 只能逐条增加行级并行点 | 大部分已否或结构性不可并行 |
| (c) | 唯一的大段 `M2_infer` 跑单核 | **配置性** | `--m2-kernel plain` A/B | ✅ **P113 已解决并采纳为默认**：6.92 → 1.28 ms/tok（5.41×） |

**P113 之后的状态**：

- **(c) 已被 `--m2-kernel plain` 摘掉**。这是**唯一一个可以在不动语义的前提下立刻验证**的原因，
  现在已经验证完并写进了默认值（§1.3.1）。它是**配置性**的，所以一旦解决就永久解决。
- **(a)(b) 完全没变**，仍然是架构性的。逐 token 语义（铁律③）不松动，
  §1.2 那张表里「结构性不可并行」的项（`_recall_project` 的写竞态、
  M3 只能走 numba、机制间顺序依赖）**一条都没动**。

> **所以「加机器 / 加核 / 加线程」现在在 (a)(b) 上依然无效** ——
> 而在 (c) 上已经**试完并解决了**。
> **这改变了论证的形状**：「191 核用不满」曾经有一半是「还没试」，
> 现在那「还没试」的部分已经归零，剩下的**全部是架构性的**。
>
> ⚠ **但结论本身没有变**：CPU 侧仍只用 0.6% 的核。
> **变的只是「其中有多少是可修的」——从 1/3 降到 0。**

### 2.3 为什么 CPU 侧的「加线程」在多数段上注定无效

`--numba-threads 8`（`train.py:262-267, 478-488`）的现行上限来自一条实测：
核内 1 → 6 线程仅 **1.16×**（x86 本机），瓶颈是**内存流量**而非算力
（两张 ~64 MB 哈希表远超 L3）。在 191 核上，8 线程以上只增加调度与空转成本。

⚠ **P113 之后这条上限的性质变了**：M2 走 `plain` 拿到了行级 prange 的 5.41×，
但**进程用核数仍是 1.1 / 191** —— 不是 prange 没生效，
而是**CPU 侧总量只有 4.26 ms，且其余各段都落在访存饱和区**。
**「并行度已经用上」与「核被用满」是两件事**，前者 P113 做到了，后者仍然做不到。

这个 1.16× 直接决定了 §1.2 那张表的判读方式：
**任何「把工作量放大 N 倍就能吃满核」的推理在本项目都不成立**，
因为扩展性在 6 线程处就已经饱和。

⚠ 口径提醒：1.16× 是 **x86 本机**实测。`BUGS.md#E5` 记载
「本机复现与服务器差一个数量级时，本机结论作废」——
但这条恰恰是**方向性**结论（访存饱和），不是绝对值。
本文用它做**上界估计**（「即使给 6 线程也只有 1.16×」），
不用它做昇腾的绝对性能判断。

## 三、加速器的结构性上限：这是带宽账，不是利用率账

### 3.1 为什么只有 M6 值得上设备

`accel_readout.py:1-22` 给出的理由是三条，都可从源码复核：

1. **占比最大**：读出在 P111 之前占端到端 ~89%（那个 89% 是读出仍在 numba CPU 上时的
   历史值；稀疏读出上设备后是 43.5%（serial 口径），P113 起是 **64.7%**——
   **三个数字口径不同，不可混用**）。
2. **通信可忽略**：逐 token 只传**一个 h 向量**（1B 档 n_h = 3072，fp32 = 12 KB 上行）。
3. **机制覆盖完整**：`AccelReadout` 实现了稀疏感知器前向 + softmax + rank-1 更新
   的完整语义（`accel_readout.py:264-284, 496-546`），包括稀疏 gather-GEMV
   （`accel_readout.py:280`）与 P112 的 epoch 判据（`accel_readout.py:286-307`）。

不能迁移的部分同样是源码给出的硬约束：

- **numba 只能编译到 CPU 机器码**（`multi_device.py:322-328` 的 `BACKEND_MATRIX`）。
  M1/M2/M3/M4 的生产路径全部是 numba。这是**物理限制**，
  在 NPU 机器上它表现为「已启用（numba nogil 线程）」但实际跑在 CPU 上。
- **M3 的 torch 后端已随 P30 删除**（`model.py:47-57`）：STDP 的逐突触状态
  （自适应 LR / 稳态 / 元可塑性 / E-I）在 torch 上无法保留，迁移会**丢机制**。
  `model.py:53-57` 现在对任何非 CPU 的 `backend` 直接 fail-fast。
- **权重与生产 ckpt 不通用**（`multi_device.py:329-336`）。

### 3.2 GEMV 是带宽受限负载：看字节流量，不看利用率

读出前向是 `y = W·h`，W 是 `(n_out, n_h)`，h 是**一个向量**。
算术强度 = 1 次 MAC / 4 B（fp32）= **0.25 MAC/B**。
这个比值由「每步只有一个 h」决定，与 W 多大无关。
昇腾 AI Core 做 bf16 矩阵乘期望的 MAC/B 高出两个数量级——
**所以这个 kernel 必然是访存受限的**，且这个结论不需要任何实测支撑。

由此得到判断规则：**看字节流量，不看「利用率」。**
一个 AI Core 99% 忙的 kernel 完全可能只用了个位数百分比的 HBM 带宽
（本文复算见 §3.4）。

### 3.3 字节流量：源码决定，不看文档口径

**本文复算**（1B 档稀疏读出，`readout_conn_k=128`，fp32 val + int64 idx，
`accel_readout.py:123-178` 的实际布局）：

```
val  = n_out × k × 4 B          （W 本体，稀疏臂强制 fp32 —— accel_readout.py:170-174）
idx  = n_out × k × 8 B          （Wi 列索引，int64 是刻意的 —— accel_readout.py:131-133）
```

一步内的 HBM 流量取决于两处**会物化 (n_out, k) 临时张量**的实现选择：

| 环节 | 读 | 写 | 源码 |
|---|---|---|---|
| `_sp_gather`：`ht[Wi]` | idx 75.7 MB | g 37.9 MB | `accel_readout.py:304` |
| forward：`W * g` | W 37.9 + g 37.9 | tmp 37.9 | `accel_readout.py:280` |
| forward：`.sum(dim=1)` | tmp 37.9 | y 0.2 | 同上 |
| update：`dp ⊗ g` | g 37.9 + dp 0.2 | tmp 37.9 | `accel_readout.py:539` |
| update：`add_` | tmp 37.9 + W 37.9 | W 37.9 | 同上 |
| **合计** | **340.8 MB** | **151.7 MB** | **492.5 MB/步** |

⚠ **本口径是「设计词表 73,958」**（`n_out` = 73,958）。按本次训练实建词表 51,962
同口径缩小为 **346.0 MB/步**。**性能文档 §3.5 用的是第三套数（229.15 MiB/步，
`diag_readout_npu.py` 实算）** → **三套口径的差异与各自适用范围见 §3.6，刻意不统一。**

对照 `bench_accel.py:73-75` 自己的口径说明：
「等效带宽 = 3×|W| / 耗时（读 W 一次 + 读写 W 各一次）」——
那是**稠密**口径。稀疏臂的流量只有 `k/n_h = 4.2%` 的权重加上 int64 索引
（`accel_readout.py:129-133`：idx 占了总流量的 2/3）。

### 3.4 ⚠ 一处必须纠正的字节口径（本文复算，与性能文档 §3.3 不同）

⚠ **本节的分母 7.68 ms/tok 是 serial 口径的历史值**；P113 现行实测是 **7.83 ms/tok**
（读出绝对值几乎没变，占比从 43.5% 涨到 64.7% 是因为分母变小）。
**本节要纠正的分子口径问题与 P113 无关**，结论继续成立。

性能文档曾用 **866.7 MiB × 3 = 2600 MiB/步**（稠密 fp32 W，设计词表）
除以稀疏臂实测耗时，得到「~339 GB/s ≈ HBM 的 21%」。

**这个分子与被测运行的口径不一致**。三条交叉证据：

1. 该耗时是**稀疏臂**（`--readout-conn-k 128`）的实测值，
   其设备端驻留权重是 113.6 MB（`val` fp32 + `Wi` int64），
   **不是 866.7 MiB 的稠密矩阵**。
2. 同一份日志的 HBM 占用是 **0.1 / 29 GB**——与 113.6 MB 的稀疏布局一致，
   与 866.7 MiB 的稠密布局不一致。
3. `MiB → GB` 的换算也差 5%：2600 MiB = 2726 MB，÷ 7.68 ms = 355 GB/s（非 339）。

→ **「带宽已用 21%」这句话已作废**（性能文档 §3.3 已同步标为历史对照）。
稀疏臂的实际流量见本文 §3.3 复算与性能文档 §3.5 实算，两套口径的对照见 §3.6。
真正的原因在下一段。本文把两个口径并列写出来，是为了防止下一次引用时把分子分母配错。

### 3.5 真正的结构性上限：算术强度被逐 token 语义锁死

把 §3.2 与 §3.4 合起来，NPU 侧的结构性上限可以精确表述：

- 读出是 GEMV，**每读 1 字节权重只做 1 次 MAC**。
- 逐 token 语义要求每步只提交**一个 h 向量**（`model.py:316-341`：
  设备直通路径 `forward_dev` 每步传一个 `n_h=3072` 的向量）。
- 因此**每步的字节流量是固定的**，而字节流量 ÷ 假设带宽给出搬运下限：
  性能文档 §3.5 用 `diag_readout_npu.py` 实算的 **229.15 MiB ÷ ~800 GB/s = 0.300 ms**
  （⚠ **估算下界，不是实测**；本文 §3.3 的 492.5 MB ÷ 1.6 TB/s = 0.31 ms 是同一量级的另一口径）。
- 实测 **7.83 ms** 是这个下界的 **26.1×** → **瓶颈不在带宽，在算子效率**。

  P113 的静态扫描已确认**读出热路径无设备同步点**（`tools/diag_readout_npu.py`），
  所以这 26.1× **不能再归因于「CPU 被设备等住」**，只能是
  **gather 指令效率 + elementwise 临时张量 + kernel launch** 这些实现层问题，
  需要 NPU 内核级 profiling（msprof）才能定位。
- **批处理是唯一能提高算术强度的手段**（一个 W 读一次服务 B 个 h），
  但批处理改变 W 的更新次数与顺序 → 违反铁律③ → **出局**。

> **所以「NPU 利用率是结构性上限」这句话的正确表述是**：
> **不是带宽用满了，也不是算力用满了，而是「每步只有一个 h」这个约束
> 让访存量无法被摊薄。** 提高设备利用率只有一条路（批处理），
> 而这条路由逐 token 语义封闭。
> ⚠ **但 P113 的实测把这句话往前推进了一步**：既然实测是估算下界的 26.1×、
> 且热路径无同步点，那么**「结构性上限」不是当前 7.83 ms 的成因**——
> 当前成因是**算子效率**，它是**可改的**。结构性上限约束的是「能到的最好情况」，
> 不是「现在为什么慢」。**这两件事必须分开说。**

### 3.6 ⚠⚠ 三套「读出每步字节」口径：刻意并存，不要强行统一

这是本文档与性能文档之间**最容易被误当成错误的地方**，所以单列说明。
**三套数字各自都是对的，差别在三个维度上**：

| # | 口径 | 值 | 词表 | 计 idx？ | 计临时张量 g / tmp？ | 来源 | 用途 |
|---|---|---|---|---|---|---|---|
| **①** | 稠密上界 | **2600 MiB/步**（= 866.7 MiB × 3） | 73,958 设计 | —（无稀疏 idx） | ✅ | 性能文档 §3.3（**历史对照，该结论已作废**） | 访存**上界**估算；⚠ **不能**除以稀疏臂耗时 |
| **②** | 本文复算 | **492.5 MB/步**（51,962 口径 → **346.0 MB/步**） | 73,958（主）/ 51,962（换算） | ✅ | ✅ | **本文复算**，本文 §3.3 | 源码级流量拆解，逐环节列式 |
| **③** | P113 实算 | **229.15 MiB/步** | **51,962 实建** | ✅ | ✅ | 性能文档 §3.5 / `tools/diag_readout_npu.py` | 与**实测 7.83 ms 同口径** → 26.1× |

**为什么 ① 与 ②/③ 差这么多**：①是**稠密**矩阵的三倍搬运（读 W + 读写 W 各一次），
而稀疏臂的真实权重只有 `k/n_h = 4.2%`；①里连`idx` 都不存在。
**②与③的差别主要是词表**（73,958 vs 51,962，比值 1.42）**与环节计数粒度**
（②按 5 个源码环节逐条列式，③按「前向 ×1 + 更新 ×1」聚合）。
**② > ③ 是预期的** —— 聚合口径不会比逐环节口径更大。

⚠ **必须遵守的三条**：
1. **不要把 ① 的数字除以稀疏臂耗时** —— 这是「带宽已用 21%」那个作废结论的来源。
2. **引用 ② 或 ③ 时必须带词表口径**（73,958 vs 51,962），否则字节数会差1.42×。
3. **只有 ③ 与实测 7.83 ms 同口径**，所以「26.1×」这个判断**只能由 ③ 给出**。
   ②配 1.6 TB/s **标称**带宽得到的是 64.1 GB/s ≈ 4.0%，
   方向与 ③ 一致（**都不是带宽饱和**），但**倍数完全不同**（4.0% vs 26.1×）。
   根因是③用 ~800 GB/s 的**假设**带宽（gather 的有效带宽远低于标称），
   而②用 1.6 TB/s **标称**带宽 → **两个下界不是同一个下界。**

> **本文保留三套的目的**：防止下一次有人「统一数字」时，
> 把词表口径、idx 是否计入、临时张量是否计入这三个维度中的一个悄悄改掉。
> **统一的前提是先选定词表口径并重算，不是把两个现成数字取一个。**

⚠ 观测手段本身的诚实边界：`torch.npu.utilization()` **内部同步设备流**，
每次采样都在训练热路径上打一次全局同步（`telemetry.py:156-160` 的注释与实现）。
因此 `phdnet/telemetry.py:193-224` 改走 `npu-smi info` **子进程**。
**观测手段不能破坏被观测的流水线**——这是一条方法论约束，不是实现细节。

## 四、线程治理：为什么 191 核反而更慢

线程治理的三个约束全部是**时序约束**：违反后无法事后补救。
它们共同解释了「机器越大越慢」这类反直觉现象。

### 4.1 三个时序约束

| 约束 | 源码位置 | 违反后果（实测） |
|---|---|---|
| BLAS 线程上限必须在 **`import numpy` 之前**设 | `train.py:54-61` 在 `import numpy`（`train.py:68`）**之前**设 4 个变量（`OMP_NUM_THREADS` / `OPENBLAS_NUM_THREADS` / `MKL_NUM_THREADS` / `NUMEXPR_NUM_THREADS`，缺省 `min(8, cpu_count)`） | OpenBLAS 初始化后再设**无效** → 191 线程去跑 1024×2048 的 sgemv（M1 编码器） |
| `numba.set_num_threads` 必须在**任何核首次执行之前** | `train.py:478-488` | 线程池首次调用时定型 → 191 线程跑千行级 prange → 纯空转 |
| `OMP_PROC_BIND` 必须在 **numba 初始化之前**进环境 | `train.py:427-432` | 绑核在 OpenMP 初始化时生效，**事后补不上** |

这三条**都无法在 CI 上验证**（CI 机器核数不同）——限线程的正确性依赖部署机器的核数。
这是 §4.1 的门禁缺口，也是为什么「限流」这件事必须靠人工确认。

### 4.2 `OMP_PLACES=cores` 为什么被撤

`train.py:423-426` 记录了实测：`OMP_PLACES=cores` 在 191 核机器上要为 191 个核
建 place 表，OpenMP / numba **每次线程池同步都要遍历它** → `M2_infer` 2.4 → 19–32 ms/tok
（涨 8–13×），CS/s 反而升到 600 万。现行只保留 `OMP_PROC_BIND=close`。

⚠ 注意 `train.py:238-242` 的 argparse help 里同时出现了两个口径
（「M2 慢 8-13×」与「实测 M2 慢 8-13×」），而 `BUGS.md#E4` 与性能文档 §五 记的是
「约 8×」。**引用时用源码里带 ms/tok 原始值的那一档**（2.4 → 19–32 ms/tok）。

### 4.3 一个「修了一半」的典型：`configure_host_threads()`

`multi_device.py:166-182` 提供了 `configure_host_threads()`，
docstring 明写「必须在 numpy/torch 初始化前调用才完全生效」。
但全仓库搜索的结果是：**它只有一个调用点——`verify_multi_device.py:161` 的 F 用例。**

`train/train.py` 与 `train/infer.py` 都**不调用**它。
生产侧的线程收敛完全由 §4.1 的三行环境变量 + `numba.set_num_threads` 承担，
`configure_host_threads()` 是一条**已实现、未接入**的路径。

这为什么重要：多卡场景下「OMP/MKL/NUMEXPR/OPENBLAS 全部收敛到 1」是必需的
（否则 CPU 线程与卡内线程争抢），而这条逻辑已经写好、已被 verifier 覆盖，
却**没有生产调用点**。这是「修了一半」的典型形态——不是 bug，是接线缺失。
本文只指认，不给实施步骤（那是性能文档的职责）。

## 五、多卡定位：模型并行，不是数据并行

### 5.1 为什么多卡只能是模型并行

§1.1 的结论直接决定了多卡的形态：`multi_device.py:4-19` 的模块 docstring
把这一层论证写在了代码里——DDP 按参数分片 + all-reduce 梯度，
而本项目**没有梯度可分**（无反向图、无 batch）；DataParallel **无 batch 轴可切**。
因此走**模型并行**路线，且只切**真正可分**的部分。

### 5.2 读出列并行：按词表行切分，逐位等价已验

`MultiDeviceReadout`（`multi_device.py:215-299`）的切法是**按 V 维（词表行）**：

- 各卡持 `W[s:e, :]`，`shard_ranges`（`multi_device.py:145-163`）给出均衡区间
- 前向 = 分片 matvec → 主设备 `cat`（`multi_device.py:250-251`）
- 更新 = 主卡 fp32 算全局 `p`，把 `dp` 分片下发，各卡本地 `add_(outer(dp_i, h))`
  （`multi_device.py:267-273`）

**每步通信量**（`multi_device.py:194`）：`V × 4 B × 2`。
按本次训练实建词表 51,962 复算 = **415,696 B ≈ 406 KB/步**（`[本文复算]`；
`multi_device.py:15` 用的 V=9,219 是更早的词表口径，已过时）。
相对于读出本身的访存量（§3.3 的 346 MB/步），通信量低三个数量级——
**不构成瓶颈**，这是选它的唯一理由。

**等价性判据要分两种**（`multi_device.py:42-48` 已显式声明）：

- **同设备分片**（同一张卡上按行切分再 `cat`）→ **逐位一致**。
  每行 dot 与分片顺序无关，softmax 在 `cat` 后的同一向量上算。
  `verify_multi_device.py:124-136` 对此给**逐位**断言（4 路分片 vs 单设备：
  前向 / NLL / 更新后权重）。
- **跨设备** → **容差一致**（不是逐位），因为归约顺序不同。

⚠ `verify_multi_device.py:14-16` 明说：**GPU 真机多卡路径待硬件到位后另测**。
本机无加速器，D 例是「同设备 4 路分片」验证分片逻辑。
所以「多卡已验证」的准确表述是**分片逻辑已逐位验证，跨设备一致性未实测**。

### 5.3 LTM 分片：只是计划层

`multi_device.py:21-25` 给了 LTM 分片的定位：big_ltm 的 CSR 天然可按神经元区间切分，
`shard_ranges(n_neurons, n_devices)` 给出区间，跨神经元的 STDP 共激活交互是唯一的跨卡通信需求。

⚠ **它没有实现**。原文自陈「本机（无 GPU、256M 档）不可验证，
仅提供计划与诚实限制说明，不提供假实现」。
本文不把它计入「可用的并行维度」。

### 5.4 加速比上界是读出的线性加速，不是全模型加速

`plan_parallel`（`multi_device.py:185-212`）给的公式是
`1 / (1 - s + s/n)`，其中 `s = readout_share` 默认 **0.89**。

⚠ **这个默认参数已经过时**：0.89 是读出仍在 numba CPU 上的历史占比。
稀疏读出上设备后是 43.5%（serial 口径，**历史对照**），
**P113 现行口径是 64.7%**（§2.1）。三档复算如下
（`[本文复算]`，公式取自 `multi_device.py:200`）：

| n（设备数） | s=0.89（源码默认，读出在 CPU 上） | s=0.435（serial 口径，历史） | **s=0.647（P113 现行口径）** |
|---|---|---|---|
| 2 | 1.79× | 1.28× | **1.21×** |
| 4 | 3.01× | 1.48× | **1.31×** |
| 8 | 3.58× | 1.62× | **1.38×** |

**P113 之后，多卡上界比serial 段又降了一档**（n=4 从 1.48× → 1.31×）。
根因是读出占比从 43.5% 涨到 64.7% ——**读出越是大头，多卡线性加速它的收益越被稀释**，
因为剩下 35.2% 的 CPU 侧完全不动。
⚠ 这**不改变**「多卡只线性加速读出那一段」的结论（§2.2），
只是把那条结论的**数字**更新了。**源码默认 0.89 高估收益约 2.3 倍**（n=4）。

⚠ 另注：`multi_device.py:18` 的注释写「N=4 → ≈3.3×」，
而同文件 `plan_parallel` 的公式算出的是 3.01×——**注释里的数字与自己的公式也不一致**。

`plan_parallel` 的 `not_parallel` 字段（`multi_device.py:208-209`）
如实列出了未并行部分：PC 栈、STDP 印迹、LTM 长时记忆、分词/编码。
**这与 §2.2 的结论一致：多卡只线性加速读出那一段。**

## 六、平台差异：x86 的结论不是昇腾的证据

### 七次实测：五次方向相反，一份「未 A/B」

| 改动 | x86 本机 | 昇腾 aarch64 | 源码位置 |
|---|---|---|---|
| M1 编码器 fp32 | 快 **1.80×**（606.7 → 337.7 µs） | 慢 **约 70×**（0.85 → 58–60 ms/tok） | `sparse_encoder.py:104-108`（平台自适应分支） |
| M2 融合核 | 快 **1.15–2.16×** | 慢 **3–4×**（fused 20–27 vs plain 6.7–11.9 ms/tok） | `sparse_pc.py:483-485` |
| **`--m2-kernel serial` vs `plain`** | 未 A/B | **plain 赢 5.41×**（6.92 → 1.28 ms/tok，P113） | `train.py:250-255`；性能文档 §4.2 |
| `OMP_PLACES=cores` | 无感 | 慢 **8×**（`M2_infer` 2.4 → 19–32 ms/tok） | `train.py:423-426` |
| M1 GEMV 走 BLAS vs 自写核 | BLAS 更快（953 vs 1532 µs） | numpy 对该形状**病态慢**（57–58 ms/tok，fp32/fp64 都慢） | `sparse_encoder.py:107-123` |
| 词涌现核内 prange | 1 → 6 线程 **1.16×** | 191 只会更差 | `word_induce_numba.py:51-57` |
| LTM 批量核 | 1.0–1.1×（收益未复现） | **收益完全押在服务器侧，至今未复测** | 性能文档 §4.3 |

**七次里有五次方向相反，另一次（`serial` vs `plain`）在 x86 上从未 A/B。**
这不是七个独立的 bug，是同一个根因在 aarch64 上的三种表现：

> ⚠ **P113 新增的一行给这条铁律加了一条更强的推论**：
> `--m2-kernel serial` vs `plain` 在 x86 上**「未 A/B」**——
> 不是「测了没差别」，而是**根本没测**。
> **而昇腾上 plain 赢 5.41×。** 所以：**x86 上的「无差别」甚至不能用来推断昇腾，
> 只能用来推断「本机测不出来」。** 必须去目标机器测。

1. **BLAS 少线程优化差**：M1 的 GEMV 在 aarch64 上无论 fp32 还是 fp64 都病态慢
   ——与 dtype 无关，说明是**该平台的 GEMV 内核没有针对这个形状调优**。
   仓库的应对是 P77 的平台自适应（aarch64 走自写 numba 核，x86 保留 BLAS）。
2. **prange 的 fork/join 屏障相对更贵**：191 核上建线程池、同步的开销，
   与「1024 行 × 128 边」这种小矩阵的计算量同阶甚至更高。
3. **Python 解释器与 dict 访问更贵**：`BUGS.md#E5` 记载
   「本机 800×800 组合 0.36 ms，服务器 6.5 万组合 19.5 ms/tok（约 54 倍）」，
   因为服务器 `active` 只有 256、且 aarch64 的解释器开销更高
   → **不是组合数问题**。这直接给出「本机计时结论在昇腾上作废」的方法论。

### 6.1 唯一两条跨平台都成立的规则

1. **GEMV/GEMM 前必须 `W.dtype == x.dtype`**（`sparse_encoder.py:99-103`）。
   混合 dtype 会脱离 BLAS 的 sgemv 走逐元素慢路径。
   ⚠ 这类缺陷**不报错、结果正确，只是慢**——在所有正确性门禁下都不可见。
   目前**没有任何断言检查 `A.dtype == b.dtype`**。
2. **numba 的 dtype 支持是平台 × 版本相关的**：`sparse_encoder.py:113-116` 记录
   P107b 曾把 W/x/b 转 fp16 进核，**aarch64 numba 没有 float16 数据模型**
   （`NotImplementedError: float16`），已回滚为 fp32 进核。
   → **aarch64 上「把计算核降到 fp16」这条路在 numba 侧是封死的。**

### 6.2 门禁覆盖的不对称

`sparse_encoder.py:110-112` 的 aarch64 分支意味着
`_gemv_rows` **只在 aarch64 生效 → x86 CI 永远跑不到它**。
`cfg.m2_kernel` / `cfg.encoder_dtype` / `cfg.readout_dtype` 三个计数器开关
就是这条铁律的产物（`train.py:250-261`、`train.py:206-213`）。

### 6.3 ⚠ 设备 profiler 的解读纪律（P144 教训，跨平台通用）

msprof 昇腾实测曾让我下错两次结论，**两次都是读指标的方法错**：

1. **算子名里的硬件名不等于它跑在那个硬件上。**
   `aclnnIndex_IndexAiCore_Index` 名字带 "AiCore"，但 `aicore_time=0`、
   `aiv_time=99.6%` →它跑在 **Vector 单元**。"AiCore" 只是 CANN 的**分类标签**。
2. **`Task Duration` 含排队，不等于执行时间。**
   该算子 Task Wait 是自身耗时的 **6.8 倍** →「算子慢」是错误表述，
   真因是**没被调度到**（= 每步只提交 12 个小 kernel，NPU 大部分时间空转等 CPU）。

→ **三条纪律**：
- 每个 profiler 指标都要问「**这个 0 是真 0 还是缺数据**」。
  我第一版解析器只取 `aicore_time` 一个指标，把 0 当「没数据」→误判。
- **必须看多个硬件单元**（Cube / Vector / 搬运 / 排队），单看一个必误判。
  `tools/analyse_readout_timeline.py` 已内置「硬件单元归属判读」：
  AICore>50% = 真在算矩阵｜AIV/Vector>30% = 访存/向量型｜
  搬运>30% = memory-bound ｜**wait ≫ 耗时 = 不是它慢，是没被调度到**。

## 附录 B 判据：以后怎么判断一个并行/加速方案值不值得做

1. **它需要 batch 维或梯度吗？** 需要 → 直接出局（铁律③，§1.1）。
2. **它并行的粒度是行级/条目级，且行间写集不相交吗？** 不是 → 结构性串行
   （`_recall_project` 是范例），谈并行度无意义（§1.2）。
3. **它减少了必须搬运的字节数吗？** 否 → 最多常数级收益（§3.5：
   访存量由「每步一个 h」锁死）。
4. **它的实测在目标机器上吗？** 七次实测里五次方向相反、一次在 x86 上未 A/B（§6）——
   x86 结论不构成昇腾证据，**x86 的「无差别」也不构成**。
5. **它过了逐位对拍吗？** 判据见 `verify_parallel_consistency.py`（五核）
   与 `verify_multi_device.py`（4 路分片）。⚠ 基线必须是同库同 fastmath 的串行实现。
6. **它加的是核还是进程？** 加核在访存饱和区（1→6 线程 1.16×）无效；
   加进程在数据侧已被 8 进程 + 19 解码核封顶（§1.5）。

## 附录 B：numba 的GPU 能力与本项目的关系（P121，2026-10-01）

fhz 提出「numba 有 API 能把运算放到 CUDA 上」。核实结论：

### B.1 `numba.cuda` 存在，但**对本项目不可用**

`numba.cuda` 确实能把 Python 数值核编译成 CUDA kernel（`@cuda.jit`，
可访问 NumPy 数组、自动在 host/device 间传输）。但它**硬绑 NVIDIA CUDA 驱动**：

| 依赖 | 要求 | 昇腾 910B |
|---|---|---|
| `CUDA_HOME` / `/usr/local/cuda` | NVIDIA CUDA Toolkit ≥ 11.2 | ✗ 不存在 |
| `libcuda`（`NUMBA_CUDA_DRIVER` 指定路径） | NVIDIA 驱动库 | ✗ 不存在 |
| Compute Capability | ≥ 5.0（Maxwell 及以后） | ✗ NPU 无此概念 |
| 后端| `numba-cuda` 独立包 / ROCm（AMD） | ✗ 无昇腾后端 |

**numba 没有任何昇腾 NPU 后端**。P18 已实测确认这条边界：numba 只编译到 CPU
机器码，故加速器必须走 torch 栈（`phdnet/backends/accel_readout.py`），
而 torch 栈缺 7 项机制（含 `big_ltm`）→ **整体迁移会丢机制**，且权重与生产
ckpt 不通用。

### B.2 但这次核查发现一个**真实的 CPU 侧缺口**：`nogil` 覆盖不全

我们用了 42 处 `@njit` + 77 处 `prange`，其中 `parallel=True` 的核**有 11 个
缺 `nogil=True`**，包括 **`--m2-kernel plain` 走的 5 个 CSR matvec 核**
（`sparse_pc.py:43/55/66/86/97`）。

- `nogil=True` 让 numba 核在执行期间**释放 GIL**，从而能与Python 线程并发。
- 本机（x86 8 核、1B 档真实尺寸 n=1024/k=128）实测**单次调用慢 7.8%**
  （0.090 → 0.097 ms），数值逐位相同。
  → **单线程路径下加 nogil 是纯亏**，只在「该核与其它 Python 线程并发」时回本。

**结论与后续**：`nogil` 该不该加，取决于 CPU/NPU 重叠（P117方案 A）做不做：

| 场景 | 建议 |
|---|---|
| **当前**（CPU 侧串行，无并发） | **不加** —— 单次调用慢 7.8%，白亏 |
| **若做 P117 方案 A**（M1(t+1) 与读出并发） | M2 的 matvec 仍排在关键路径上（依赖 PC 权重），故**仍不加** |
| 若将来把 `bigltm.imprint` 的 `learn` 挪进线程池 | 那时给 `_ltm_learn_rows` 保持 `nogil`（**它已有**），并考虑给被并发调用的核加 |

⚠ 本条纪律：**不要为了「看起来更并行」到处加 nogil**。它是一个**有成本的
选项**（单次调用变慢），只在真正的并发场景才回本——与 P22（prange 线程数
1→6 仅 1.16×，访存饱和）是同一类「先量再开」的问题。
