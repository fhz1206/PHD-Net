# PHD-Net 并行与加速架构分析

> **目标**：回答一个问题——**为什么吃不满 191 核与 NPU**，以及在项目约束下**还有没有量级提升的杠杆**。
> **方法**：全部结论必须**可复算**：从依赖链推出串行性，从每步工作量推出并行度上界，
> 从访存量推出设备带宽天花板。凡引用实测数字一律链接到唯一权威出处，不在此复制。
> **数据截止**：2026-09-30。
> 性能数字见 `PHD-Net_性能评估与迭代方案.md`；被否决的优化与踩坑见
> `PHD-Net_迭代优化与修复日志.md`；缺陷台账见 `BUGS.md`。

## 一、逐 token 依赖链：串行性是结构决定的

### 1.1 依赖图

```
token t:  x_t ──M1 编码──> s0_t ──M2 推理──> r2_t ──┬──M3 STDP 预测──> pred
                                                       ├──M5 调制(surprise)
                                                       ├──M4a 工作记忆(r2)
                                                       ├──M4b LTM(imprint / recall)
                                                       └──M6 读出 h_t ──> y_t ──> W 更新 ──┐
                                                                                              ↓
token t+1: x_{t+1} ──M1──> s0_{t+1} ──M2──> ...  必须看到**已更新的 W(t)** ◄──────────────┘
```

### 1.2 串行性的三个来源（都可复算）

| # | 约束 | 来源 | 可否在不改语义下解除 |
|---|---|---|---|
| 1 | **跨 token：W 每步原地更新**，`y_{t+1} = W(t+1)·h_{t+1}` 必须看到 `W(t+1)` | 铁律③「逐 token 语义」——状态跨 token / shard / epoch 连续演化 | **否**。解除需批处理，而批处理改变 W 的更新次数与顺序 → **改变训练语义** |
| 2 | **步内串行**：M1→M2→M4→M6 有真实数据依赖（`h` 由 `r2`、`WM`、`pred` 拼装而成） | 数据流定义 | 部分可解：见 §四段级重叠 |
| 3 | **状态依赖不可预计算** | CPU 侧每步 PC 权重都在被前一步的更新改写 → 下一步输入无法提前算 | **否**。这是「预计算类优化收益 <1%」的根本原因（实测 onehot 43× 但只占端到端 0.069%） |

**结论 1：跨 token 严格串行。** 这是逐 token 语义的直接后果，不是实现问题。
任何「把 NPU 打满」的方案若必须靠批处理实现，就等于放弃铁律③。

### 1.3 由此推出的 NPU 利用率上界

单步读出的访存量 ÷ 设备带宽 = 该段的**物理天花板**。要提高利用率只有两条路：
**搬更多数据**（批处理，违反约束 1）或**搬得更少**（稀疏化，见 §五）。
中间地带（融合 kernel、消除 launch、减少同步）只能把「暴露出来的延迟」压掉，
压不到带宽墙以下——这是 §四的天花板判断依据。

## 二、CPU 侧：为什么 191 核用不满

### 2.1 实测现象

进程实际用核 **1.1–3.2 / 191**，上下文切换 250 万–600 万/秒（数据与口径见性能文档 §3.3）。
表面看是「线程开多了空转」，但限流到 8 线程之后**用核数并没有变多**——说明限流不是解，
根因在别处。

### 2.2 三层可复算的论证

**第一层：每步可并行工作量本身太小。**

单步九段中，除读出（已上设备）外，CPU 侧的段都是 µs–低 ms 量级
（`M3_pred` / `M5_mod` / `M4a_wm` / `PC_learn` / `STDP_learn` 均 < 1 ms/tok，
主循环三段 `tokenize` 0.06 / `encode_onehot` 0.13 ms）。
191 核的线程同步与调度开销与这个量级同阶甚至更高 → 加核只加开销。

**第二层：核内并行度已被访存带宽锁死。**

P22 实测：核内 1 → 6 线程仅 **1.16×**。原因是热核要扫两张 ~64 MB 的哈希表，
远超 L3 → 扩展性受**内存带宽**而非算力限制。
这意味着即使把可并行的工作量放大 100 倍，8 线程以上也拿不到线性加速。
**这是「每步工作量小」之外的第二个独立上界**，也是为什么 8 线程是合理上限而非保守妥协。

**第三层：并行宽度在训练过程中动态变化，静态线程池无法始终匹配。**

把整个 step 看作一个任务，其并行宽度受 M2 推理的 CSR 边数（1B 档百万级）
与 M4b 的绑定遍历量约束，而这些量本身随步数增长（P66 实测 `scores` 288 → 7200，25×）
——线程池的宽度在第 1 步和第 10000 步的最优值不同。

**结论 2：CPU 吃不满 191 核是架构性的。** 逐 token 串行 + 每步可并行工作量太小 +
核内扩展受访存饱和，三者叠加。任何「加机器/加核/加线程」的思路在这个约束下都无效。

### 2.3 一个被误解的对照

小栈（256 维栈）上 M3/M4 的 STDP 与 LTM 是 µs 级、被明确判定为**不是瓶颈**。
但 1B 档的 M4b 曾达 63.5 ms/tok 占 76%——**因为 1B 档的 LTM 表规模让每步的
Python dict 更新量放大到 1.8 万次量级**（P70 定位，见迭代日志）。

结论：M4b 在小栈可忽略、在 1B 档是最大单段，**不能用小栈的 profiling 推 1B 档**
（这也是全文要求「可复算 / 带规模口径」的原因）。
注意区分两种病态：**「工作量变大」是可并行的**（能加核），
**「单位工作量太贵」（解释器逐元素开销）是不可并行的**（只能改实现）。
M4b 属于后者，所以加核对它无效——这也是 §2.2 第二层上界的另一个佐证。

## 三、NPU 侧：每步 320 MB 访存的天花板

### 3.1 访存账（两套口径，都要标明）

| 口径 | 每步访存 | 构成 | 来源 |
|---|---|---|---|
| 概算口径 | **2 × 320 MB = 640 MB** | forward 读 W 一次 + update 的大流量一次 | 性能文档 §四（沿用多年的简写） |
| 详细账 | **960 MB/步（bf16 全程）** | forward 读 W（320）+ update `addmm_` 读 W（320）+ 写 W（320） | P84 代码注释（bf16 对照基准） |

⚠ **2 × 320 MB 是简写，漏掉了 update 的写**。做带宽复算时必须用详细账，否则会低估 50%。

### 3.2 复算

设 W = 1.6 亿读出参数，bf16 存储 = 320 MB；昇腾 HBM ~1.6 TB/s（口径见硬件后端适配报告 §六）。

| 量 | 算式 | 结果 |
|---|---|---|
| 单次读 W 的纯搬运下限 | 320 MB ÷ 1.6 TB/s | **0.2 ms** |
| 一步两次大流量的搬运下限 | 640 MB ÷ 1.6 TB/s | **0.4 ms** |
| 一步完整访存的搬运下限 | 960 MB ÷ 1.6 TB/s | **0.6 ms** |
| 实测读出墙钟 | — | **5.5–7 ms/tok** |
| 反算有效带宽 | 960 MB ÷ 5.5–7 ms | **137–175 GB/s ≈ HBM 的 9–11%** |
| 差值归因 | 5.5 − 0.6 ≈ 4.9 ms | 同步、kernel launch、小 kernel 串行提交、kernel 效率 |

**结论 3：读出是访存受限而非算力受限，且当前离带宽墙还有约一个数量级。**
这个数量级差不是「算力不够」，而是**每步只有 320 MB 可搬**——
把 NPU 打满需要一个数量级更多的数据，而数据量由 `V×H` 决定，**不引入批处理就无法增加**。

### 3.3 与「~50% 利用率是结构性上限」的关系

早期观测给出的「NPU ~50% 利用率是结构性上限」在今天的实测下**依然成立**，
且已通过消除同步/launch/Python 开销把**暴露出来的延迟**压掉（读出 9.5–13.5 → 5.5–7 ms/tok）。
需要说清两件事：

1. **「50%」是哪个 50%**：AI Core% 遥测的瞬时值（NPU 已可见 98%）。
   它反映的是「这一瞬间设备忙不忙」，不是「带宽用满没有」。
2. **带宽账才是物理约束**（§3.2）：即使 AI Core% 显示 100%，带宽也只用了 9–11%。
   **两个口径不可混用**。

## 四、为什么「100% 占满 191 核 + NPU」在约束下不可能

把 §一–§三的结论合起来，四个独立的约束同时成立：

| # | 约束 | 数量级 |
|---|---|---|
| 1 | **逐 token 串行**：一步内 M1→M2→M4→M6 有数据依赖，跨步被 W 更新串住 | 步内可重叠的只有 M1/M2 与 M3/M4/M5（§4.1） |
| 2 | **每步工作量太小**：CPU 侧单步可并行部分 µs–低 ms 量级 | 191 核的调度/同步开销与它同阶或更高 |
| 3 | **核内扩展受访存饱和**：1→6 线程仅 1.16× | 再加核只加内存流量 |
| 4 | **NPU 访存上限**：每步只搬 320 MB（详细账 960 MB） | 满带宽也只有 0.2–0.6 ms；要打满需**批处理** |

而批处理改变 `W` 的更新次数与顺序 → **改变训练语义** → 违反铁律③。
**所以「100% 占满 191 核 + NPU」在约束下不是一个待优化项，而是一个不可达目标。**

### 4.1 唯一不违反约束的重叠：段级流水

`M1(x)` / `M2(s0)` 只依赖**本 token 的 x**，与 `M3/M4/M5`（依赖 `r2_t` / 跨步状态）**无依赖**
→ 可重叠。W 更新的顺序要求由 NPU stream 保序自动满足（同 stream 内 `addmm_` → 下一次 `W@h`）。

**收益上界 = max(CPU 侧, NPU 侧)，而不是相加。** 这也再次说明为什么
「先让 CPU 和 NPU 都不闲」不可能带来数量级提升——重叠只能吃掉等待，不能创造并行度。
step 重构的具体做法属于优化步骤，不在本文展开。

### 4.2 本项目的正确定位

**「单 token 极低延迟 + 状态连续演化」，不是「吞吐最大的批处理引擎」。**
这不是能力缺陷，而是铁律③（逐 token 语义）的直接推论：
一个**不允许批处理**的系统，其并行度上限由「单步可并行工作量」决定，
而不是由「机器有多少核」决定。

## 五、量级提升的唯一杠杆：稀疏化

前三节论证了「换一个量级的加速」不可达。于是问题变成：**什么才能带来一个数量级？**
答案只有一个方向——**减少必须搬的字节数**。

### 5.1 欠账

M6 读出目前 **100% 稠密**。这是**明确的架构欠账**，不是实现选择：
人脑皮层的连接率约 **2e-8**，「人脑是稀疏的」是本项目脑同构原则的直接推论。
换言之，稠密读出不仅慢，而且**在架构上是不合格的**。

### 5.2 杠杆的量级

幂律稀疏化方案（已设计、未实施）把读出按幂律稀疏到 **5–12% 活跃度**
（区间为原方案设计估值，出处：本文 2026-09-29 稿 §4.1；**尚未在代码中实施，也未实测**）：

| 口径 | 稠密 | 稀疏 5–12% |
|---|---|---|
| 读出参数量 | 1.6 亿 | 0.08–0.19 亿 |
| bf16 访存/步 | 320 MB（×3 = 960 MB） | **16–38 MB（×3 = 48–115 MB）** |
| 满带宽搬运下限 | 0.6 ms | **0.03–0.07 ms** |

**访存量降 8–20×**，且这是唯一能把 §3.2 的带宽墙整体左移的手段。
其余所有优化（kernel 融合、消除同步、段级流水）都在**墙右侧**做常数级改进。

### 5.3 为什么只有稀疏化够量级

| 手段 | 改善的对象 | 量级 |
|---|---|---|
| 消除同步 / 减少 launch | 延迟（不搬数据） | 常数级（已做，读出 9.5–13.5 → 5.5–7） |
| 段级流水 | 等待（不增加并行度） | 常数级（上界 = max 而非相加） |
| 加核 / 加线程 | 访存饱和区 | 1.16×（P22 实测） |
| fp8 forward | forward 读流量 | 320 → 80 MB，但**总访存 +42%**（更新侧 fp16 换精度） |
| **幂律稀疏化** | **访存总量** | **8–20×** |

**结论：稀疏化是唯一的量级杠杆。** 它同时解决三件事：
把 NPU 带宽墙左移一个数量级、让 CPU 侧读出前向的计算量同比下降、
消除「稠密读出 vs 人脑 2e-8 连接率」这笔架构欠账。

## 六、判据：以后怎么判断一个优化值不值得做

在上述约束下，任何新优化按这个顺序判：

1. **它减少了必须搬运的字节数吗？** 否 → 最多常数级收益（§5.3）。
2. **它的实测在目标机器上吗？** x86 的结论不构成证据（已在 P61/P52/P74 上连续反噬三次）。
3. **它保持逐 token 语义吗？** 任何需要批处理的方案直接出局（铁律③）。
4. **它过了逐位对拍吗？** 本项目已有 4 个「看起来是热点」的优化实测为负收益
   （0.91–0.96× / 0.72–0.76× / 0.96× / 0.84×）——**负收益立即回滚**，明细见迭代日志。
5. **它有 profiling 支撑吗？** 无 profile 的优化要么收益 <1%，要么负收益。

> 最重要的判据是第 1 条：在「搬的字节数」这个维度上，
> 本项目已经处于**访存受限**区间（§三），因此任何不减少字节数的优化
> 都不可能带来数量级提升。这与「1B 档 M4b 曾占 76%」并不矛盾——
> 那 63.5 ms/tok 是**每组合约 300 ns 的解释器开销**（P65 定位：65k 组合对应 19.5 ms，
> 出处：迭代日志同批次记录），属于「单位工作量太贵」，修正后即回到 µs–ms 量级（§2.2 第一层）。
