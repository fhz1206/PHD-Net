# PHD-Net 并行与加速架构分析（2026-09-29）

> 目标：**结构不变、原理不变**的前提下吃满多核与计算卡。
> 本文用 191 核昇腾服务器的真实数据说明：约束在哪里、瓶颈在哪、还能做什么。

## 1. 每步的依赖链（结构决定的天花板）

```
token t:  x_t ──M1 编码──> s0_t ──M2 推理──> r2_t ──┬──M3 预测──> pred
                                                      ├──M5 调制(surprise)
                                                      ├──M4a WM(r2)
                                                      ├──M4b LTM(imprint/recall)
                                                      └──M6 读出 h_t ──> y_t ──> W 更新 ──┐
                                                                                          ↓
token t+1: x_{t+1} ──M1──> s0_{t+1} ──M2(s0_{t+1})──> ... 需要**已更新的 W** ◄──────────┘
```

**关键事实**：`W` 每步原地更新，`y_{t+1} = W·h_{t+1}` 必须看到 `W(t)`。
→ **跨 token 严格串行**，这是逐 token 语义（状态跨样本/shard/epoch 连续演化）的
直接后果，也是「NPU 利用率的数学上限 ≈ 每步读出流量 / 设备带宽」的原因。

## 2. 实测：191 核用不满、NPU 闲逛的真实数字

| 指标（191 核昇腾，1B 档，token 7500） | 值 | 解读 |
|---|---|---|
| 总耗时 | 83.6 ms/tok | — |
| readout（NPU） | 9.5 ms/tok | 320 MB bf16 ×2 访存 → **64 GB/s**（NPU 带宽的 ~5%） |
| M4b_ltm | 63.5 ms/tok（修复前） | **Python dict 遍历**（P70 已修，44.6×） |
| 进程实际用核 | **1.1–3.2 / 191** | 串行依赖链 + 每段只有 µs 级可并行工作 |
| 上下文切换 | **250 万–600 万 /秒** | 线程空转 + 核间漂移（P62/P71 处理） |

**结论 1：NPU 的 64 GB/s 不是算力问题，是访存量问题。** 单步读出只有 320 MB，
即使 100% 带宽也只有 0.3 ms；实测 9.5 ms 说明绝大部分时间在**同步、launch
开销与小 kernel 的串行提交**上（P55/P58 已分别处理）。

**结论 2：CPU 吃不满 191 核是结构性的。** 每个 M 段的可并行工作量都在
µs–低 ms 量级（P22 实测 prange 1→6 线程仅 1.16×，访存带宽饱和），
而 step 之间有严格依赖 → **能吃满的核数 ≈ 单段工作量的并行度**，不是 191。

## 3. 不违反约束的改造清单（按实测收益排序）

| # | 改造 | 收益 | 状态 |
|---|---|---|---|
| 1 | `predict` 脱离 Python dict（P70） | M4b **63.5 → ~1 ms**（44.6×） | 已上线，待服务器验证 |
| 2 | recall 反投影 numba（P68） | 21.9× | 已上线 |
| 3 | nll 设备累积 + 关图优化 + pinned H2D（P58/P62） | 消除每步同步，端到端 −20~30% | 已上线 |
| 4 | M2 学习侧融合（P59，8→1 核） | 1.15–1.72× | 已上线 |
| 5 | M1 编码器 fp32（P61） | 1.80× | 已上线 |
| 6 | **段级流水**：M1/M2 与 M3/M4/M5 重叠 | ~1 ms/tok（隐藏 M4b 剩余成本） | 待做（step 重构） |
| 7 | **imprint（learn）路径 numba 化** | 低（imprint 触发 <10 次/千步） | 待做，优先级低 |
| 8 | 批量并行读出 | **不可行** —— 违反逐 token 语义 | 否决 |

**第 6 项（段级流水）的可行性**：`M1(x)`/`M2(s0)` 只依赖本 token 的 x，
与 `M3/M4/M5`（依赖 r2_t / 状态）**无依赖** → 可重叠。W 更新依赖由 NPU
stream 保序自动满足（同一 stream 内 `addmm_` → 下一次 `W@h`）。
收益上限 = max(CPU 侧, NPU 侧) 而非相加。

## 4. 为什么「吃满 191 核 + NPU 100%」在约束下不可能

1. **逐 token 串行**：一步内 M1→M2→M4→M6 有数据依赖，跨步被 W 更新串住。
2. **每步工作量太小**：单步可并行部分 ~1 ms，191 核的调度开销远超收益。
3. **NPU 访存上限**：读出每步只搬 320 MB；把 NPU 打满需要**批处理**，
   而批处理改变 `W` 的更新次数与顺序 → **改变训练语义**。
4. **因此**：本项目的正确定位是「**单 token 极低延迟 + 状态连续演化**」，
   不是「吞吐最大的批处理引擎」。P23/P24 的 50% 利用率结论在今天的实测下
   依然成立，且已通过消除同步/launch/Python 开销把「暴露出来的延迟」压掉。
