### 1.5 日志字段与读法

| 字段 | 读法 |
|---|---|
| `sliding PPL … X ms/tok` | 端到端步时。**跨 run 比较必须同数据、同 `--remote-fraction`、同机器、同 token 预算** |
| `readout X ms/tok (后端@设备, Y% of total)` | 读出分项。`% of total` 直接判断加速是否生效、耗时是否转移到 PC 栈 |
| `loop: tokenize A  encode_onehot B  step C` | **主循环三段**（需 `--step-profiling`）。此前主循环开销从未被测量 |
| `segments(cum): <名> <ms/tok> …` | **`net.step` 内部九段**的历史平均（从 token 0 起累加，`_prof` **从不清零**）→ ⚠ **混着启动期编译开销，系统性高估稳态**。判断加速生效看下面这行 |
| `segments(win): <名> <ms/tok> … [N steps]` | **P115 新增**：上一个打印间隔内的**真实平均**。**做性能判断一律用这行**。这就是「readout 从 28.77 衰减到 7.68」的真相——不是模型变快，是早期昂贵样本被摊薄 |
| `HBM-bw X%/vec Y%/aicpu Z%` | **P120 新增**（来自 `npu-smi info -t usages`，每 4 tick 抽样）。**判读规则：高 AICore + 低带宽 = 瓶颈在 kernel 下发/调度**，既不在算力也不在 HBM 带宽。⚠ 高 AICore 单独**不能**说明算力用满（大量小 kernel 也能顶到 99%） |
| `CPU …%  proc X核 … CS/s … GC …` | `proc X核` = 进程实际用核数；`CS/s` = 上下文切换频率（线程空转的指纹） |
| `NPU/GPU …%  HBM …GB` | AI Core%（瞬时，设备忙不忙）与 HBM（host 侧计数器）。**AI Core% ≠ 带宽利用率**，见 §三 |
| `[readout] backend=… \| fallback reason: …` | **读出是否真在设备上**。判断加速生效看这行，**不看「检测到设备」** |
| `[readout] compute precision = …` | 读出实际精度。精度降级必须在这一行可见 |
| `[parallel] numba prange threads = N … OMP_PROC_BIND=… BLAS/OpenMP threads=N` | 线程治理是否真生效（§八） |
| `[numba] cache dir = … size = X MB` | 持久缓存是否命中（命中启动 ~2.6 s） |
| `[ltm-diag] imprints=… / recalls=…` | LTM 规模与召回遍历量演化（每 10 次触发） |
| `[log] start: … argv: …` | 完整命令行。「行为没生效」**先查这里**，再查代码（`BUGS.md` E6） |

### 1.6 九段 + 三段的正确读法

**九段**（`phdnet/model.py` 的 `_prof_t` / `_prof_end` 段名）：
`M1_encode` / `M2_infer` / `M3_pred` / `M5_mod` / `M4a_wm` / `M4b_ltm`（内嵌 `M4b_imprint`）/
`PC_learn` / `STDP_learn`。

⚠ **`readout` 不在 `segments` 里** —— 它走独立累计器，打印在训练主行的
`readout X ms/tok`。所以 `segments` 之和**天然不含读出**，对账时必须把主行的读出值加进来。

⚠ **`M4b_ltm` 只覆盖 imprint 分支**。recall 分支没有独立计时，其时间落在
「九段之和 + 读出 ≠ `loop.step`」的差额里。

三步读法，缺一步就会得出错误结论：

1. **先对账**：`loop.step` 是否 ≈ 主行的 `ms/tok`。不等则差额在主循环或计时之外。
2. **再求和**：`segments` 九段之和 **+ 主行读出值** 是否 ≈ `loop.step`。
   不等则还有未计时的工作（已知两处：recall 分支、`critical_period` 突触修剪在 `PC_learn` 计时之外）。
3. **最后看趋势**：同一 run 内把 `segments` 按 token 数排成序列。
   **绝对值小但超线性增长的段才是真元凶** —— 2026-09-29 的 M4b 就是这样定位的：
   token 1500 时 `M4b_ltm` 仅 0.14 ms/tok，token 3500 涨到 19.54，
   同期 `M2_infer` 反而从 5.05 降到 2.70。

> 只看「当前最大段」会追错目标：那一段可能正在下降，而下一段正在超线性增长。

### 2.1 端到端：P113 之后 8.05× 提速

| 指标 | 值（ms/tok） | 说明 |
|---|---|---|
| **P111 之前** | **97.07** | 稀疏读出回落 numba CPU，`readout` 占端到端 ~89% |
| **P111 之后**（serial 口径，历史对照） | **17.63** | 稀疏读出实现在加速后端，后端 `accel:npu` |
| **P113 稳态**（plain，**现行基线**） | **12.09** | 叠加 `--m2-kernel plain` |
| **累计提速** | **8.05×** | 97.07 → 12.09 |

**P113 变更前后对照**（同一档位、同一平台，两个 run 的稳态值）：

| 量 | P113 前（serial，历史对照） | P113（plain，**现行**） | 倍数 |
|---|---|---|---|
| **端到端** | 17.63 | **12.09** | **1.46×** |
| **`M2_infer`** | 6.92 | **1.28** | **5.41×** |
| **CPU 侧合计**（端到端 − 读出） | 9.95 | **4.26** | **2.33×** |
| **读出占端到端** | 43.5%（7.68 ms） | **64.7%**（7.83 ms） | — |
| 遥测 | NPU 99% / CPU 1–2% | NPU 99% / CPU 1–2% | 不变 |

⚠ **读出绝对值几乎没变（7.68 → 7.83）**，所以端到端的 1.46× **全部来自 CPU 侧**
（M2 6.92 → 1.28 省下 5.64，摊平到其它 CPU 段后端到端省 5.54）。
**读出占比从 43.5% 涨到 64.7% 不是读出变慢了，是分母变小了。**

**零回归证据**：P113 与 serial 两个 run 在四个采样点
（10250 / 20250 / 30250 / 40250 token）的 sliding PPL **逐位完全相同**：
**38101.949 / 25042.421 / 22693.449 / 19602.394**。
→ `plain` 是**纯调度变化、零语义变化**，这是它能当默认值的唯一理由。
⚠ 这份「逐位相同」是**生产日志观测**（两次 run 的其余条件相同，但不是同进程内比），
已由 `tests/verifiers/verify_m2_kernels.py`（13 例三态对拍）固化成**可复跑的受控门禁**。

**收敛曲线**（P111 那一段 run 内按token 数采样，**这是「稳态」的唯一依据**）：

| token 数 | 500 | 10k | 20k | 40k | 56k |
|---|---|---|---|---|---|
| ms/tok | 97.07 | 22.15 | 19.36 | 17.99 | **17.63** |

曲线形态说明：前 10k token 的 97.07 是**冷启动 + LTM 未生长**的混合值；
10k→56k 从 22.15 单调降到 17.63，**降幅 20%**。
⚠ 56k 之后是否继续下降**未测**（run 未跑到更长）——**不预测**；
P113 run 的采样点止于 40250，**未跑到 56k**，所以两条run 的稳态不可直接比长度。

`1.03 + 1.28 + 0.04 + 0.40 + 0.40 + 0.06 = 3.21` → 合计 **11.04**，
对主行 12.09 的差额 **1.05 ms/tok** 落在主循环三段（`tokenize` 0.02 +

## 三、访存与带宽账

> **GEMV 是带宽受限负载。** 判断优化空间时看**字节流量**，不看「利用率」——
> 一个 99% AI Core% 的 kernel 完全可能只用了估算带宽的个位数百分比（§3.5 实算）。

### 3.1 稀疏 vs 稠密的访存账（1B 档，设计词表 vocab 73,958 × n_h 3,072）

⚠ **两套词表口径，不要混用**：
- **73,958** = 设计态满词表（`tools/bench_accel.py` 的缺省 `V`），用于访存/带宽**上界**估算。
- **51,962** = 本次训练实建词表（`[日志]`），实际读出规模比上界小 30%。

| 布局 | 每步字节 | 相对稠密 |
|---|---|---|
| 稠密 fp32 W | **866.7 MiB**（= 908.8 MB） | 1.0× |
| **稀疏 k=128**：`val` fp32 37.9 MB + `idx` int64 75.7 MB | **113.6 MB** | **8.0× 省** |

⚠ **8.0× 是含 idx 开销的真实比值**（75.7 MB 的 int64 索引占了总量的 2/3）。
若只看 `val`，会得出 24× 的错误结论。

### 3.2 CSR 内存账与 25% 交叉点

| 布局 | 每突触/每权重字节 |
|---|---|
| CPU 侧 CSR（`phdnet/sparse_pc.py`：`idx` int64 + `val` float64） | **16 B/突触** |
| 稠密 fp32 | **4 B/权重** |

**交叉点 = 密度 25%**（`16 B × d = 4 B` → `d = 0.25`）。
即：**CSR 在密度 >25% 时反而比稠密 fp32 更大**。
1B 档 `k/n_in = 128/3072 = 4.2%`，在交叉点以下 6 倍，稀疏成立。
⚠ 这也解释了为什么 §3.1 的 8.0×（4.2% 密度）低于理论上限 `1/0.042 = 24×`。

来源：`tools/bench_readout_sparse.py` 的 docstring（数值推导）+
`[日志]` 1B 档实测 113.6 MB。

### 3.3 ⚠ 稠密读出的旧口径（历史对照，分子分母不匹配）

**下面的表是 P111 段的**稠密**口径，**保留作为历史对照**，但它的分子与
被测运行（稀疏臂）口径不一致，**不能用来论证任何带宽结论**：

| 量 | 算式 | 结果 |
|---|---|---|
| 一步完整访存（读 W forward + 读 W update + 写 W update） | 866.7 MiB × 3 | **2600 MiB/步** |
| 单次读 W 的纯搬运下限 | 866.7 MiB ÷ 1.6 TB/s | **0.54 ms** |
| 一步完整访存的搬运下限 | 2600 MiB ÷ 1.6 TB/s | **1.6 ms** |
| 实测读出墙钟（P111 serial 口径） | — | **7.68 ms/tok**（`[日志]`，**历史对照**） |
| 反算有效带宽 | 2600 MiB ÷ 7.68 ms | **~339 GB/s ≈ HBM 的 21%** |
| 差值归因 | 7.68 − 1.6 ≈ 6.1 ms | gather 实现、kernel launch、小 kernel 串行提交、同步 |

⚠ **三条不自洽**（并列文档《并行与加速架构分析》§3.4 已独立指出同一问题）：
① 分子用**稠密** 866.7 MiB，分母却是**稀疏臂**实测的 7.68 ms；
② 同一份日志的 HBM 占用是 0.1 / 29 GB，与 113.6 MB 的稀疏布局一致、与稠密布局不一致；
③ `MiB → GB` 换算也差 5%（2600 MiB = 2726 MB ÷ 7.68 ms = 355 GB/s，非 339）。
→ **「带宽已用 21%」这句话已作废**，正确诊断见 §3.5。

**更早的历史对照**（bf16 稠密口径，`[台账]`）：960 MB/步 → 实测 5.5–7 ms
→ 反算 137–175 GB/s ≈ HBM 的 9–11%。⚠ 这是**稀疏化之前**的口径，
引用时必须标注，否则会与上面两套口径都冲突。

### 3.4 为什么 NPU 迁移是唯一出路（不是调优）

| 路径 | 实测 | 结论 |
|---|---|---|
| ~~CPU numba 读出核~~ | ~~43 GB/s ≈ DDR4 上限，`fastmath` 无收益~~ | ⚠ **P178–P183 已修正**：这条结论建立在**错误的性能画像**上（见下） |
| NPU gather-GEMV（现行） | 7.83 ms/tok（`accel:npu`），P113 口径 | 唯一出路已走通 |

> ⚠⚠ **P178–P183 修正：所谓「CPU 读出核已饱和、无优化空间」是误判**
>
> 三个独立原因导致长期错误结论：
> 1. **M1 一直用 BLAS 而非自写 AVX2 核**。`simd::gemv_row_avx2`（4 路 FMA
>    累加器）早已存在但只被 `m1_gemv_simd` 调用，生产前向走 `self._W @ h`（BLAS）。
>    P183 实测**Rust AVX2 比 BLAS 快 1.09–1.75×**（8192×8192 达1.75×）。
>    🔴 **该数字为已删除臂的历史记录**：`phdnet_rs/` 已于 P188 整体删除，
>    现行 M1 前向是 numba / BLAS 运行时探测（`_prefer_blas_gemv`）。
> 2. **M2 读出门的真实瓶颈是 Python 校验层**，不是内核。`_check_csr` 的
>    `idx.min()/idx.max()` 对 9.47M 元素做全量numpy 扫描，单次 **6.05 ms**
>    = `m2_matvec` 总耗时的 **65.8%**（P179）。修掉后 **9.18 → 3.8 ms（2.4×）**。
> 3. 🔴 **Rust M2 融合核一直损坏但被当成"未启用"**。P178 实测 relerr≈1.9，
>    P182 定位根因是**融合核漏了 int64→int32 转换**（Rust 按 i32 读int64
>    数组 → 读垃圾），修复后 relerr ~2e-07、门禁 5 FAIL → **0 FAIL**。
>
> **当前口径**（🔴 下表为**已删除臂的历史实测**；生产形状 73958×3072 / k=128，同进程交错 best-of）：
> | 实现 | 1 线程 | 8 线程 | 带宽 |
> |---|---|---|---|
> | ~~Rust 稀疏 SpMV（i32 gather）~~ 🔴 | 6.6 ms | **3.8 ms** | **18.8 GB/s** |
> | numba 稀疏 SpMV | 9.1 ms | 2.6 ms | — |
>
> → 当时结论「**18.8 GB/s 仍是 DDR4 上限（~44%）**」以 Rust 行为准；
>   🔴 **该行实现已随 `phdnet_rs/` 于 P188 整体删除，不可复现、不可引用为现状**。
>   仍然成立的是方法论结论：「完全没空间」不成立 —— **i32 化 + 去掉校验层全扫 +
>   融合核修复**合计已带来 2.4×。

**P76否掉的是 prange 融合核，不是 CSR matvec 自身的行级并行** ——
`plain` 已于 P113 服务器实测采纳为默认（5.41×，§2.1），这条区分已被实践验证。
🔴 **P182 补充（该方案已随 P188 删除）**：当时 `fused` 路径改走 Rust 融合核（融合核已修好），
但仍受**规模门限**约束——小 shape 时 ctypes 跨界开销占主导（见 §3.6）。
**门限机制与 Rust 融合核实现均已不存在**，`--m2-kernel` 现只走 numba 路径（`plain`/`serial`/`fused`）。

### 3.5 ✅ 读出带宽诊断：不是带宽饱和，是算子效率问题（`tools/diag_readout_npu.py` 实算）

**这是读出优化的第一份实算诊断**，工具 = `tools/diag_readout_npu.py`
（同步点静态扫描 + 字节流量拆解）。

**稀疏臂每步触达字节 = 229.15 MiB**，拆解如下（fp32 `val` + int64 `idx`，
vocab 51,962、k=128）：

| 环节 | 触达字节 | 倍数 |
|---|---|---|
| `idx`（int64 列索引） | 50.74 MiB | **2×** |
| `val`（fp32 权重本体） | 25.37 MiB | **3×** |
| 临时张量 `g`（稀疏 gather 出的 `(n_out,k)` fp32） | 25.37 MiB | **2×** |
| `dp`（感知器误差向量） | 0.59 MiB | — |
| **合计** | **229.15 MiB/步** | — |

**下界与实测的差距（本节唯一的核心结论）**：

| 量 | 值 | 口径 |
|---|---|---|
| 每步触达字节 | **229.15 MiB** | `[工具]` `diag_readout_npu.py` 实算 |
| 带宽假设 | ~800 GB/s | ⚠ **这是估算假设**，不是实测 HBM 带宽 |
| 搬运下界 | **0.300 ms** | 229.15 MiB ÷ ~800 GB/s，**估算值** |
| 实测墙钟 | **7.83 ms** | `[日志]` P113 |
| **实测 / 下界** | **26.1×** | — |

→ **不是带宽饱和，是算子效率问题。**
⚠ **绝对不要把 0.300 ms 当实测**：它依赖「~800 GB/s」这个假设带宽
（本项目 HBM 标称 ~1.6 TB/s，但稀疏 gather 的有效带宽远低于标称），
**下界是估算值**，这一点已写进工具的 docstring（引用纪律同`BUGS.md` A8/B12）。

**同步点：已清零（静态扫描确认）**。`diag_readout_npu.py` 的静态扫描确认
读出热路径**已无设备同步点** —— P112 修掉的那个每步 `torch.equal` 硬同步是**唯一**一个。
→ **所以 26.1× 的差距不能归因于「CPU 被设备等住」，只能是算子本身的效率**
（gather 指令效率、elementwise 临时张量、kernel launch 串行）。
⚠ 但**静态扫描只能证明「没有显式同步原语」**，不能证明设备端没有隐式同步；
后者需要 CANN 级 profiling（msprof）。

> ### 正确表述（对照 §3.3 的作废表述）
> **不是带宽用满了，也不是算力用满了。** 每步只触达 229.15 MiB，
> 按~800 GB/s 估算下界只有 0.300 ms，实测 7.83 ms 是它的 **26.1×**。
> 提高设备利用率只能靠改算子实现（融合、减少临时张量、减少 launch），
> **批处理是唯一能摊薄访存量的手段，而它违反铁律③ → 出局。**

## 四、分段剖析与 CPU/NPU 不对称

### 4.1 不对称的量化（稳态，`[日志]`，P113）

```
端到端 12.09 ms/tok（`[日志]`）
├─ NPU 侧   7.83 ms   64.7%   AI Core 99% 满载，HBM 0.1/29 GB
├─ CPU 侧   4.26 ms   35.2%   进程仅用 1.1/191 核，CS/s ~0.9M，RAM 2.9 GB
└─（两侧合计 100%，无未拆分余量）
```

**对账**：CPU 侧 4.26 = 端到端 12.09 − 读出 7.83，**是减出来的、不是日志直接给的**。
⚠ P111 那一段日志给的是「CPU 侧占 50.6%」这个百分比，
**不要用它乘以任何端到端值反推 ms** —— 那会把一个百分比当成独立测量。

**这是本项目当前最重要的性能事实（P113 后）**：NPU 侧占 64.7% 且已满载，
CPU 侧只剩 35.2%（4.26 ms）。**不对称的方向翻转了** —— P111 段是 CPU 侧占一半、
NPU 侧 43.5%；现在 NPU 侧是大头。

**191 核不是「算力不够」，而是架构性用不满** —— 两层原因：

1. **逐 token 语义禁止批处理**：状态跨 token / shard / epoch 连续演化，
   读出 W 每步原地更新 → 数据并行（同一 batch 元素互相独立）在语义上不成立。
2. **模型状态跨 token 连续** → 同一样本的相邻 token 不能并行，
   而这是唯一能在不破坏语义的前提下用上多核的并行维度。

⚠ **P113 摘掉的是第三类原因（配置性）**：此前还有一条「`M2_infer` 跑在单核」，
它不是架构性的，已由 `--m2-kernel plain` 解决（§4.2）。
**剩下的是上面两条架构性的**，论证与量化见《PHD-Net_并行与加速架构分析.md》，本文不复制。

### 4.2 ✅ `M2_infer`：从单核 6.92 到并行 1.28（P113 已采纳为默认）

**P113 之前的事实**（历史对照）：稳态下 `M2_infer` 占 6.92 ms/tok（39.3%），
是 `--m2-kernel serial` 的**单核**融合核（P99 加入，因为昇腾上 prange 融合核反而慢 3–4×）。

**P113 的实测结论**：`plain` 服务器实测 **6.92 → 1.28 ms/tok（5.41×）**，
端到端 17.63 → 12.09（1.46×），四个采样点 sliding PPL **逐位完全相同**
（38101.949 / 25042.421 / 22693.449 / 19602.394）→ **纯调度变化、零语义变化**。
**已采纳为 `--m2-kernel` 的默认值**。

**当初那个极易被误读的区分，现已被实践验证**：

| 被否掉的 | 没被否掉的 → **P113 实测赢了** |
|---|---|
| **prange 融合核**（`--m2-kernel fused`）：把多次核调用融成一核 + 行间 prange。<br>昇腾实测 fused 20–27 vs plain 6.7–11.9 ms/tok，**慢 3–4×**（`[台账]` D5）。**已否决。** | **CSR matvec 自身的行级并行**：`--m2-kernel plain` 走的 `_csr_matvec`（`phdnet/sparse_pc.py:44`）**有 `prange` + `parallel=True`**，行内串行累加、行间并行。<br>**未被否 → P113 实测 5.41×，现为默认。** |

> **⚠ 写文档/做决策时不要把这两件事混为一谈。** P76 否定的是「融合 + prange」这个组合，
> 不是 CSR 行级并行本身。**「191 核能否吃掉 M2 那 6.92 ms」曾是一个开放问题，
> P113 给出答案：能吃掉 5.64 ms（5.41×），但 191 核并没有被吃满**
> —— CPU 侧整体只从 9.95 降到 4.26 ms（§2.5）。

**零回归门禁**：`tests/verifiers/verify_m2_kernels.py`（**P113 新增，13 例**）——
三态（fused / serial / plain）在同一进程、同一输入下对拍：
A1 fused vs serial、A2 plain vs serial（**容差**，归约顺序不同，偏差 1e-7 量级）、
A3 `n_steps=1/2/3`（单步一致不代表多步一致）、B 类断言 plain 的行级 prange
**不改变求和顺序**（理论上与 serial 逐位相同）。
⚠ 日志观测到的「PPL 逐位相同」是**跨 run 观测**，本 verifier 才是**受控对拍**。

### 4.3 `M4b_ltm` 从 63.5 ms/tok 降到 0.40 ms 的完整路径

| 阶段 | 值 | 平台 | 措施 |
|---|---|---|---|
| 优化前 | **63.51 ms/tok（占端到端 76%）**，随步数增长 | 昇腾 `[台账]` C3 | — |
| `predict` 批量化 | 8.780 → **0.197 ms（44.6×）** | **x86 本机** `[台账]` C3 | `predict_arr()`（numpy gather，返回 `(keys, vals)` 不合并重复键）+ 核内按「行序 → 槽位序」逐次累加（浮点顺序与原 `p[k] += v` 完全一致 → **逐位相同**）；recall 投影 **21.9×** |
| `learn` 批量核化 | 阈值 4096 组合 | x86 本机 `[台账]` C1 | `_ltm_learn_rows` 批量核（行间 prange，行内与原版同序） |
| `encode` 线性去重 | **1.44×** | x86 本机 `[台账]` C2 邻近 | 核内去重改成 O(1) 哈希前，核化是 0.84× 负收益 → **回退 Python**；1.44× 来自调用方改为 numpy 批量 + 排序去重 |
| **当前稳态** | **0.40 ms/tok**（P113 口径；P111 段为 0.44） | 昇腾 `[日志]` | — |

**根因（必须写清，否则会误判为「又一个调优问题」）**：
**`predict` 每步做 18,000 次 Python dict 更新**。
具体量级：256 活跃行 × 约 72 槽 = **1.8 万次 dict 更新 + numpy 标量取值/step**（`[台账]` C3）。
C2 之后 recall 投影已 numba 化，但**跑在已物化的 dict 上** → dict 工作量原样保留。
**这类缺陷的特征是「单步便宜、逐步超线性」** —— token 1500 时 `M4b_ltm` 仅 0.14 ms/tok，
token 3500 涨到 19.54（§1.6 第 3 步读法）。

⚠ **关键判断**：这段**故意不上 numba gather 核** —— 1.8 万元素比批量 learn 的
64 万组合小两个数量级，核的固定开销会吃掉收益（`[台账]` C3）。

⚠ **诚实边界**：`[台账]` C7 记载 —— imprints 侧的批量核化**本机计时只有 1.0–1.1×**
（x86 Python 在这个规模已经够快），**收益完全押在服务器侧，该结论至今未复测**。
所以上表「0.40 ms/tok」是 `[日志]` 的**端到端实测值**，
而 44.6× / 21.9× / 1.44× 三个倍率是 **x86 本机实测**，**两者不是同一口径，不可相乘外推**。

## 五、平台差异铁律（x86 ≠ 昇腾）

**四次方向相反的实测**：

| 改动 | x86 本机 | 昇腾 aarch64 |
|---|---|---|
| **M1 编码器 fp32** | 快 **1.80×**（606.7 → 337.7 µs） | 慢 **约 70×**（0.85 → 58–60 ms/tok） |
| **M2 融合核**（`fused` vs `plain`） | 快 **1.15–2.16×** | 慢 **3–4×**（fused 20–27 vs plain 6.7–11.9 ms/tok）⚠ 早前记为 8–13×，见附录 A。⚠ **该 plain 值是 P76 期间另一批 run**（线程配置未标），与 P113 的 1.28 ms/tok **不是同一口径** |
| **`--m2-kernel serial` vs `plain`** | 未 A/B | **plain 赢 5.41×**（6.92 → 1.28 ms/tok，P113）。⚠ 这是**同族反例的另一面**：同一条 CSR 行级 prange，在 x86 上无可测差别、在昇腾上赢 5.41×——**说明 x86 连「无差别」都不足以推断昇腾** |
| **`OMP_PLACES=cores`** | 无感 | 慢 **约 8×**，CS/s 升到 650 万 |

> ### 规则：x86 的性能结论不构成昇腾的证据。
> 任何优化必须在**目标机器**复测。本文凡标「x86 本机」的数字只在本机成立。
> 文档中出现的**计数器开关**就是这条铁律的产物：`--m2-kernel`、`--encoder-dtype`、
> `--readout-dtype`。

**唯一一条在两个平台都成立的规则**（`[台账]` D1/D2）：

> **GEMV/GEMM 前必须 `W.dtype == x.dtype`。**

fp32 权重 @ fp64 输入会**脱离 BLAS 的 sgemv**，走逐元素慢路径，
实测退化 **5.9×**（x86：857 → 5047 µs，修复后 606.7 → 337.7 µs）。
在 aarch64 上这条规则更严 —— fp32 sgemv 本身**慢约 70×**，
`phdnet/sparse_encoder.py` 因此做**平台自适应**：aarch64 走自写 numba GEMV
（`_gemv_rows`，行间 prange、行内顺序累加，容差 1–2 ulp），x86 保留 BLAS。

⚠ **混合 dtype 是隐形缺陷**：它不报错、结果正确，只是慢 ——
**在所有正确性门禁下都是不可见的**（`[台账]` D2）。目前**没有任何断言检查 `A.dtype == b.dtype`**。

⚠ **门禁覆盖不对称**：平台分支意味着两条路径的门禁覆盖不同 ——
`_gemv_rows` 只在 aarch64 生效，**x86 CI 永远跑不到它**（`[台账]` D3）。

## 六、精度与速度的取舍

### 6.1 读出精度的实测保留率（`tools/probe_readout_precision.py`，`[工具]`）

**判据**：同精度舍入后元素是否**真的变了**（更新是否被保留）。
量级 `|W| ~ 1e-2`、`|dp| ~ 1e-6`（感知器 `p − t` 的非目标行更新）。

| 精度 | 非目标行保留率 | 目标行保留率 | 判读 |
|---|---|---|---|
| fp32 | **99.95%** | 100% | 语义正确（显式 opt-in） |
| fp16 | **26.67%** | 100% | 73% 的非目标行更新被丢弃 |
| bf16 | **5.79%** | 100% | 94% 被丢弃 |
| **fp8（P189 默认）** | 更低（步长比 fp16 粗约 4 倍） | 100% | fhz 知情选择：「模型 fp8，迭代 fp16」；验收靠 probe_PPL |

**目标行全部 100%**（目标更新 `~1e-2` ≫ 半 ULP）→ 低精度不是「完全不学习」，
而是**丢掉了非目标行的抑制项**。

> ### 结论（P110 仍有效，口径随 P189 更新）：低精度的速度收益伴随语义损失，不能只看快。
> `p − t` 规则的非目标行更新被舍入 → 学习**部分退化为纯 Hebbian**
> （只提升目标行，无抑制）。**现行默认 fp8（P189）** 是 fhz 2026-10-07 的
> 知情决策（访存减半的收益 > 非目标行损失），**验收只能靠 probe_PPL**
> （`--probe-every`）确认学习仍在进行。启动日志按精度分叉打印警告。

⚠ **两条方法论教训**（`[台账]` B13）：

1. **半 ULP 的数量级估算不能替代实测。** P105 曾判定「fp16 半 ULP 比 bf16 小 8 倍，
   能保住非目标行更新」→ 实测证明 fp16 只是「比 bf16 好」，**离正确还差一个数量级**。
   「8 倍差距」在跨越两个数量级的问题面前不成立。
2. **精度判据必须用同精度舍入后的基线。** 第一版拿 fp32 值与 fp16 值直接比，
   得到「fp16 保留 100%」的**反向假阳性**（fp32 值与 fp16 值几乎总不相等）。

⚠ **本节全部数字来自 `[工具]` 在 x86 本机的构造量级测量**，
反映的是舍入机制本身（dtype 半 ULP 是纯数值性质，与平台无关），
但**「哪种精度跑得快」的平台相关部分不在此表**。

### 6.2 fp8：硬件限制与 P189 软件绕行（本节旧结论已被推翻）

| 平台 | 实测 |
|---|---|
| 昇腾 Ascend910B4 + CANN 8.5 + torch_npu 2.9 | `float8_e4m3fn` / `float8_e5m2` 的 **create / cast / matmul 全部 ERR01007**；`torch.ops` 里**零个 fp8 算子** |
| CPU torch | 能分配 fp8 张量，但**无 fp8 addmv**（炸在 `@`） |

旧口径「P92 从加速后端整体删除 fp8」**已被 P189 推翻**：fp8 显式请求一律进
候选链首（探测决定），910B 上走 **fp8 e4m3fn 位模式（uint8 承载）存储 +
fp16 迭代计算**，访存与原生 fp8 相同（1 B/元素）；前向可选每步 CPU 转换
int8 码本走真实存在的 int8 算子（P154/P155，`--fp8-conv` 选核）。机制细节见
《PHD-Net_硬件后端适配报告.md》§3.2，本文不复制。

⚠ **能力表里的一行「不支持」只能靠目标机器实测确认**（`[台账]` B4/B11）——
这条纪律不变；变的是「不支持」之后的动作：从「整体禁用」改为「位模式绕行」。

### 6.3 低精度在本机 CPU 上是计算受限而非带宽受限

`[工具]` x86 本机读出更新核实测：fp32 **13.3 ms** vs fp16/bf16 **226 ms**（**慢 17×**）。
死因是**位运算重量化 > 带宽节省**。
→ **在 CPU 上「降精度换速度」是反的**；低精度的收益只在存储压缩与加速器原生张量核。
⚠ 此为 x86 口径，昇腾未复测。

### 6.5.2 四次自我纠正（**这是本节最有价值的部分**）

**① P178 误判：「numba 快 2.5×」**
先前用一个 `csr_row_avx2_i32` TEMP 核测得「2.98 ms / 38 GB/s、追平并略超
numba」，该符号 **git 历史查无**。P178 复测结论反转为「numba 快 2.25–2.48×」。

**② P179 推翻 ①：瓶颈根本不在内核**
关键实验是**绕过 Python 校验层直调FFI**：
| 路径 | 8T |
|---|---|
| 完整 Python 包装 | 9.180 ms |
| **绕过校验 raw FFI** | **3.135 ms** |
| → `_check_csr` 开销 | **6.045 ms（65.8%）** |

`_check_csr` 的 `idx.min()/idx.max()` 对 **9.47M 元素**做全量 numpy 扫描，
**比整个 SpMV 内核（3.1 ms）还贵 3 倍**。
→ **教训：先量「绕过校验 vs 完整包装」的差，再谈内核优化。**

**③ P181 误判：「Rust 融合核不可用」**
Rust 融合核 relerr≈1.9，门禁 M7 写「fused=True 时仍走 numba（如实标注未生效）」，
我据此判定不可用并回退。**错在没查数据 dtype**。

**④ P182 找到真因：漏了 int64→int32 转换**
P178 落地 i32 时**只改了原子算子**（`_idx_i32`），**融合核的 idx 走 `c_void_p`
从未转换** → Rust 按 `*const i32` 读 int64 数组 → **读到垃圾**。
定位链：门禁 relerr~1.9 → `n_steps=0` 也错 → 手工构造 int32 用例**完全正确**
→ 打印真实栈的 dtype 发现 **idx 是 int64**。
⚠ 附带坑：`c_void_p` **不持引用**，写成 `_p(self._idx_i32(x).ctypes.data)`
会让临时数组被 GC → **access violation**，必须存列表再 `del`。

### 6.5.3 一个反直觉的配套：修好后仍慢 3.2×

修好数值后 Rust 融合核**仍比 numba 慢 3.2×**——因为每次调用要转 4 个 CSR 的
idx（**1.85 ms/次**），**比核本身（1.01 ms）还贵**。
因**稀疏结构终身不变**（学习只原地改 `val`）→ 按 `(tag, id(indptr), id(idx), size)`
**缓存 int32 视图**（key 不含 `val`）→ 回到 1.01 ms。
→ **教训：修好一个 bug 后必须重新测性能，不能假设修好=变快。**

### 6.5.4 P180 负结果：动态 work-stealing 池（**已回退**）

参考 OpenMP/TBB 实现 `DynPool`（原子 `epoch` 发布 + 自旋 200 轮后 `park()` +
`next.fetch_add` 动态领活，块数 ×4粒度），切换 11 个调用点，补 4 个测试。
**3 轮交替进程 A/B 结果：dynamic 5.47 ms vs fixed 5.44 ms → 无收益，已回退。**
假设被逐一证伪：
- **负载不均**：均匀 k=128 /幂律变长 / 极端不均（90% 行=8、10% 行=1400）
  → 差距稳定 2.1–2.3×，**动态分块能解决的问题本就不存在**。
- **派发延迟**：mpsc 21 次同步原语 vs 原子+自旋，打平。
→ 剩余差距是**访存带宽下的 SMT 行为**，非调度可弥补。
⚠ 保留本机环境限制记录：`time.process_time()` 与 `GetProcessTimes` **都返回 0**
→ 有效核数测不了；**同一份代码 cargo 缩放 2.38×/ Python 缩放 1.2–1.3×**
→ **跨环境缩放率不可比**，只能在同进程内比。

| 5 | **P180 动态 work-stealing 池**（原子 epoch + 自旋/park + `fetch_add` 动态领活） | **3 轮交替进程 A/B：dynamic 5.47 ms vs fixed 5.44 ms → 无收益**（x86 本机） | 假设「固定分块导致尾延迟」**被证伪**：均匀/幂律/极端不均三种 CSR 分布下差距稳定 2.1–2.3×，**负载不均本就不是瓶颈**；派发延迟（mpsc 21 次同步原语 vs 原子+自旋）打平 | **已完整回退**（`git checkout`）。剩余差距是**访存带宽下的 SMT 行为**，非调度可弥补 |

**另有三处已撤销的环境/结构配置**：

| 配置 | 状态 | 依据 |
|---|---|---|
| **`OMP_PLACES=cores`** | **已撤**（只保留 `OMP_PROC_BIND=close`） | 191 核 place 表 → 每次线程池同步都要遍历它 → M1_encode 0.85 → 58–60 ms/tok（**70×**）、M2_infer 再慢约 8×、CS/s 升到 650 万（昇腾 `[台账]` B10） |
| **核内 `prange`（词涌现）** | **已回退** | 核内 1 → 6 线程仅 **1.16×**（x86 本机）—— 瓶颈是内存流量（两张 ~64 MB 哈希表远超 L3），不是线程数 |
| **`torch.npu.utilization()` 遥测** | **禁用**，改走 `npu-smi` 子进程 | 它**内部同步设备流**，每次采样都在训练热路径上砍一刀（`[台账]` B9）。**观测手段本身不能破坏被观测的流水线** |
| **局部词表复用** | **已放弃** | 破坏正确性。**性能优化先过对拍** |
| **`torch.compile`** | **默认关** | inductor **惰性编译** → 构造期不失败、首次调用才编译 → 无 C++ 编译器时直接抛 `InductorError` 崩生产（`[台账]` B2）。本机曾实测 +15%（26.34 vs 30.98 ms/tok，x86 口径） |

### 7.1 三条通用教训

1. **核的固定开销要先算**：访存/调度受限规模上，加并行度前先算核启动 + 线程同步成本。
2. **逐位对拍的基线必须是同库、同 fastmath 口径的串行实现**，否则满屏假阳性。
   ⚠ **假阳性比没测试更危险** —— 它会让人去「修」正确代码（`[台账]` E1）。
3. **计时必须复现「命中位置随机 + 行已满 + 真实规模」**。
   `[台账]` E5 记载：本机 800×800 组合 0.36 ms，服务器 6.5 万组合 19.5 ms/tok（**约 54倍**），
   因为服务器 `active` 只有 256、且 aarch64 的 Python 解释器与 dict 访问更贵。
   → **本机复现与服务器差一个数量级时，本机结论作废。**

### 7.2 P178–P183 追加的两条（**代价最大的两条**）

4. **先量「绕过封装 vs 完整封装」的差，再谈内核优化。**
   P178 花在「Rust vs numba 内核谁快」上的功夫全部作废，
   因为 65.8% 的时间在 **Python 校验层**（`idx.min()/idx.max()` 全量扫 9.47M 元素）。
   → **任何性能结论必须先回答：被测代码占总耗时的多少？**
5. **门禁 FAIL + 注释写「如实标注未生效」→ 先信门禁、查数据 dtype。**
   P181 我据此判定「Rust 融合核不可用」并回退，P182 发现真因只是
   **漏了 int64→int32 转换**（P178 落地 i32 时只改了原子算子）。
   → **「已知的坏」不等于「不可修」；先定位根因再下废弃结论。**
   ⚠ 附带：**修好数值后必须重新测性能** —— 修好后仍慢 3.2×（idx 转换 1.85 ms/次
   超过核本身 1.01 ms），需配套缓存才真正变快。

## 八、线程治理与待验证候选

>⚠ **P113 已把「候选 1（`--m2-kernel plain`）」从待验证移入已采纳**（§2.1 / §4.2），
> 默认值已改为 `plain`。本节现在是「线程治理现状 + 5 条仍待实测的候选」。

### 8.1 线程治理现状

**四个 BLAS 变量在 `import numpy` 之前 cap 到 8**（OpenBLAS 初始化后再设**无效**），
`OMP_PROC_BIND=close`，**不设 `OMP_PLACES`**，**`--numba-threads 8`**。

生效情况看启动行 `[parallel] numba prange threads = N … OMP_PROC_BIND=… BLAS/OpenMP threads=N`。

**为什么上限是 8 而不是更多**：

| 实测 | 值 | 平台 |
|---|---|---|
| 核内 1 → 6 线程 | 仅 **1.16×** | x86 本机 |
| 本机融合核带宽墙 | 1 → 8 线程 4.1 → 9.3 GB/s（**次线性**） | x86 本机 |
| 两张 ~64 MB 哈希表 | 远超 L3 → 瓶颈是内存流量 | — |

→ **超过 8 线程不再有收益，只增加调度与空转成本。**

**三个必须知道的时序约束**（违反后无法事后补救）：

| 约束 | 违反后果 |
|---|---|
| BLAS 线程上限必须在 **`import numpy` 之前**设 | 191 线程跑 1024×2048 的 sgemv → 1.1 核 + 百万级 CS/s |
| `numba.set_num_threads` 必须在**任何核首次执行之前** | 线程池首次调用时定型 → 191 线程跑千行级 `prange` → 纯空转 |
| `OMP_PROC_BIND` 必须在 **numba 初始化之前**进环境 | 绑核在 OpenMP 初始化时生效，**事后补不上** |

⚠ **门禁缺口**：这三条**都无法在 CI 上验证**（CI 机器核数不同）。
「限线程」的正确性**依赖部署机器的核数**，只能人工确认（`[台账]` B10）。

### 8.2 预取：只做跨文件并行

| 项 | 现行做法 | 依据 |
|---|---|---|
| `--prefetch-workers` 默认 | **`min(8, 核数×0.8, 文件数)`** | 单生产者按文件序归并，囤积 ≈ 0（`--prefetch-depth` 受此约束） |
| 为什么不做 token 级并行 | 单生产者时在途量 ≈ 0 | 真正有效的是跨文件并行 |
| 组大小 | 32M → **1M 字符** | 32M 组时并行度塌缩（组数 ≪ worker 数），且每组数百万 token 的字符串 pickle 成单点 |
| pyarrow 解码 | 库内多线程且释放 GIL | **单进程即吃满核**，多进程只增内存（每进程 ~100–200 MB） |

### 候选 2 的 P192 结论（2026-10-08）：**前提被推翻，本轮不做**

这条候选自 P113 起就是「收益最大、代价也最大」的架构级项。**P192 做了一次代码级核对，
结论是它的前提不成立**，故降级为「不做」：

1. **训练步的设备路径本来就没有阻塞式同步。**
   `phdnet/model.py:391-395` 走 `self.readout.forward_dev(h)` —— 返回**设备张量、零同步**；
   训练步把 `y` 置 `None`（不需要 numpy 化，P36）。
   `step()` 内**唯一**的显式 D2H 是 `nll_dev.item()`（`accel_readout.py:1231`），
   而它被 `nll_sync_every=8` 门控（P34/P62，默认 8）。

2. **因此「12.09 = 4.26 + 7.83 完全串行」若真存在，成因不是代码里的显式同步**，
   而是**运行时下发 / 队列背压**（与 msprof P144 的 `aclnnIndex` 占 89.3%、
   `aicore_time=0`、`wait` = 耗时 6.8× 指向同一处）。**要证实这一点需要服务器 msprof，
   本机（x86、无昇腾）无法验证，故不给任何结论。**

3. **跨 token 流水会在已有异步之上重新调度** —— 不能仅由静态代码断言收益为零；
   本轮没有保持语义的实现或 NPU 实测，且必须处理铁律③的时序风险：`STDP_learn(self._prev_rate, rate)` 读的是**上一步**的 rate，
   任何跨 token 的前移都等于**换一套时序规则**（`phdnet/model.py:369-382` 的 P117
   注释早已据此明确拒绝前移，本轮核对**确认该判断成立**）。

4. **唯一的跨 token `y` 依赖是 `readout_recurrence`**（`word_lm.py:145-146`，
   默认 **False**）。一旦打开它，流水会让 `recur_cue` 拿到**上一步**的 y ——
   这是**静默的语义错误**，比它可能带来的收益更危险。

→ **配置位保留但 fail-fast**：用户若传 `--readout-pipeline`，`train/train.py`
**直接报错退出**（退出码 1，发生在建模之前、无任何副作用）。
理由：留一个「开了没反应」的开关是最坏的一种 API —— 用户会以为自己在跑一个优化。
门禁 `tests/verifiers/verify_overlap_contract.py`（23/23）把上述四条钉死。

### 推理侧：为什么同样**不加**流水（这不是「还没做」，是**提法要更正**）

「减少训练**或推理**时 NPU 因 CPU 而空转」这个说法在推理侧**前提不同**，P192 核对如下：

| | 训练步 | 推理步（`sample_next`） |
|---|---|---|
| 读出调用 | `forward_dev(h)` → **设备张量、零同步** | `readout(h)` → 末行 `y.float().cpu().numpy()`（`accel_readout.py:1089`）**硬 D2H** |
| 为什么 | `model.py:391` 判 `learn and not readonly and _is_accel` → 推理 `learn=False` → 恒 False | 同左 |
| 下一步输入依赖上一步输出？ | **否**（每 token 独立消费 `x`） | **是** —— token t+1 的输入就是 token t 采样出来的结果 |

两条推论：

1. **推理阶段 CPU 与 NPU 天然串行，无法重叠。** 这是**定义**决定的
   （自回归），不是工程难度问题。任何声称能给推理做跨 token 流水的方案，
   都必须先解释它如何突破「下一步输入依赖上一步输出」这个依赖。
2. **相邻生成 token 的输入依赖是真实约束，完整 y 回读不是数学上的必需。**
   当前实现由 host 采样（`infer.py` 的 `y.astype(np.float64)`），因此先完整 D2H；
   设备端采样或减少传输仍是候选，须保持采样语义并做独立性能验证。
   不应把当前实现的 host 等待统称为不可优化的语义要求。

⚠ **本节不产生任何新的性能数字。** 本机（x86、无昇腾）实测推理采样段的
host 侧数学（V=51,962、top-k=8、200 次取均值）约 **0.77 ms/token**
（softmax 0.26 + argpartition 0.43 + 子集采样 0.01 + 归一化 0.07），
但**这是 x86 口径、且未计入 D2H 与 NPU GEMV**，**不能**据此推断昇腾收益。
唯一能确定的是：它只占训练步 CPU 侧 4.26 ms 的约 18%，**不是主要矛盾**；
若要优化推理，先测 D2H 本身。

⚠ **本节不产生任何新的性能数字。** 7.83 ms 仍是 `max(两侧)` 的**理论上限**，
不是实测；当前无任何实测重叠数据，收益估算一律不写。
