# PHD-Net 性能评估与迭代方案

> **适用范围**：`phdnet/` 包 + `train/train.py`（生产训练入口）+ `train/infer.py`（生产推理入口）
> 的**全部性能数字**：端到端步时、分段耗时、访存/带宽账、资源利用率、线程治理、精度取舍、被否决的优化。
>
> **本文是全仓库所有性能数字的唯一权威出处。** 其他文档一律**链接引用**，不复制数字。
> 机制原理见《PHD-Net_架构设计.md》；为什么吃不满多核与 NPU 的**论证**见《PHD-Net_并行与加速架构分析.md》；
> 后端矩阵与昇腾踩坑见《PHD-Net_硬件后端适配报告.md》；CPU/NPU 重叠的三方案与执行顺序见
> 《PHD-Net_CPU-NPU重叠执行计划.md》；缺陷台账（症状 → 根因 → **门禁缺口**）见 `BUGS.md`。
>
> **数据截止：2026-11-01（P213）**。当前生效的默认值：读出精度 fp32；`--m2-kernel` 默认 **`auto`**
> （按平台择优，昇腾 aarch64 → `plain`）；`--numba-threads` 默认 **16**；`--cython-kernels` 默认 **`auto`**；
> `--sparse-fwd-kernel` 默认 **`einsum`**；`eta_oja` 默认 **0**（>0 发散，见 §6.4）；
> 表征发育窗口 `pc_dev_steps=20000` + `eta_pc=0.02`；会话中学习四开关默认 True
> （`sdr_novelty`/`task_modulation`/`error_gated_memory`/`readout_replay`，`ltm_imprint_gate` 0.8→0.3）。
>
> ⚠ **两套基线口径并存，不可混用**：
> - **现行服务器实测（2026-11-01）**：端到端 **10.8 ms/tok**（CPU 侧 6.5 / NPU 读出 3.5），
>   来源 `train_1b_1b_pretrain_20261101-140007.log`（1b 档、24.5k token 稳态）。
> - **本文 §2/§3/§4 的分项归因基线（P113，2026-10-01）**：端到端 **12.09 ms/tok**，
>   来源 `train_1b_1b_pretrain_20261001-182721.log`（`--m2-kernel plain`）。
>   两者是**不同批次、不同机器状态**（读出前向已改 einsum、M4b 已批量化、replay 周期已改），
>   **绝对值不可互相替代**；§3.5 的 26.1× 等结论按 **P113 口径**成立。
>
> **铁律（违反即本文档失效）**：
> 1. **任何数字必须带口径**：平台（x86 本机 / 昇腾 191 核 + NPU）、档位（`smoke` / `1b` / `1b_max` / `30b`）、
>    单位（ms/tok）、测量来源（日志名 / 工具名）。无口径的数字视为无效。
> 2. **禁止预测值式表述**（「预期 ~13 ms/tok」「应该能降到 X」）。只写实测值；
>    没有实测的写「**待服务器实测**」，并归入 §八 待验证候选。
>    ⚠ **理论上限不是预测值，但也必须显式标注**：如「重叠后 12.09 → 7.83（`max` of 两侧）」
>    是**理论上限**，必须写明「不是实测」。
> 3. **x86 的性能结论不构成昇腾的证据**（见 §五）。
>    ⚠ **反面同样成立**：x86 上的「**无差别**」也不构成昇腾上「无差别」的证据。

### 1.4 影响测量的开关（`train/train.py`，源码核对 2026-11-01）

| 开关 | **现行默认** | 为什么影响测量 |
|---|---|---|
| `--step-profiling` | **开** | **唯一的分段计时来源**（九段 + 主循环三段）。开销 ~0.2µs/段可忽略；`--no-step-profiling` 关闭。不开只剩端到端一个数，无法归因 |
| `--readout-conn-k` | **128** | M6 读出稀疏度（0 = 稠密）。**128/3072 = 4.2% 连接率**，决定读出访存量（省 8.0×）。P108 取自 4M 档 A/B：k=128 时 PPL 477 vs 稠密 608 |
| `--readout-dtype` | **fp32** | 读出**存储**精度。低精度把感知器 `p−t` 的非目标行更新舍入丢弃 → 学习**部分退化为纯 Hebbian**（P110 保留率实测，见 §6.1）。要 fp8 的访存收益请配 `--readout-master-weight`（§6.2）。910B 无 fp8 算子 → 每步 CPU 转换 int8 计算可选（`--fp8-conv`） |
| `--readout-master-weight` | **off** | fp32 主权重 + 低精度影子副本（DeepSeek-V4-Flash 模式）。所有更新作用在 fp32 master（非目标行更新 100% 保留），影子只做前向 GEMV，每 N 步重量化一次。代价：多一份 fp32 master（1b 档 866.7 MiB）+ 最多 N 步 staleness；torch.compile 被禁用、NPU Graph 重量化移出图外。**默认 off**——fp32 存储时无收益 |
| `--readout-shadow-refresh` | 8 | 主权重模式下影子重量化间隔（步）。本机 A/B：r=4 → PPL 2.15、r=8 → 2.15、r=16 → 2.20 |
| `--fp8-conv` | **torch** | fp8→int8 CPU 转换核（**torch/nogil**）。🔴 **原第三选项 `rust` 已随「删除 rust 版本」整体移除**，传旧值**静默按 torch 处理**（不报错，两条 Python 路径逐位一致） |
| `--sparse-fwd-kernel` | **`einsum`** | 稀疏读出前向算子。`mulsum` = `(W*h[Wi]).sum(1)`，每步物化一个 `(n_out,k)` 临时张量（1b 档 25.37 MiB × 2 处）；`einsum` 不物化（省 50.74 MiB/步），但**归约顺序不同 → 非逐位**（max\|Δ\|≈3e-05），**昇腾收益未实测**（x86 结论不构成昇腾证据）。⚠ **§3.5 的字节账按 `mulsum` 口径给出** |
| `--m2-kernel` | **`auto`** | **按平台择优**（`phdnet/sparse_pc.py::default_m2_kernel`）：x86 → `fused`（本机实测快 1.34–2.05×），昇腾 aarch64 → **`plain`**（P113 服务器实测 5.41×，§2.1）。⚠ **x86 结论不构成昇腾证据，故按平台分而非硬编码**。三态**数值等价**（P113：sliding PPL 逐位相同，纯调度变化）→ 切换默认不改任何数值。`serial` 是 P99 加的**单核**融合核（**历史对照**）；`fused` 在昇腾退化 3–4×（已否）。⚠ `phdnet/config.py` 的库默认 `pc_fused_kernel=True` 是**另一条路径**（= fused），引用时必须指明层级（附录 A） |
| `--encoder-dtype` | **fp32** | M1 编码器权重精度。⚠ help 文本写「默认 fp64」，**与实际默认值不符**（见附录 A） |
| `--numba-threads` | **16** | numba `prange` 线程上限（P204 由 8 改 16）。191 核上不限必然空转。⚠ 本机 x86 16/32 因 fork/join 屏障是**负收益区**，**服务器 A/B 仍待做**（§八 候选） |
| `--omp-proc-bind` | 开 | 设 `OMP_PROC_BIND=close`。**不设 `OMP_PLACES`**（已撤，§七） |
| `--omp-wait` | `active` | OpenMP 空闲等待策略。`passive` 本机实测墙钟 **+90%**；191 核大规模下未 A/B |
| `--nll-sync-every` | 8 | nll 设备侧累积间隔。默认 1 时每步 `.item()` 把 NPU 延迟全额暴露给 CPU，流水永不重叠 |
| `--cython-kernels` | **`auto`** | `off`/`auto`/`force`。`auto` = 加载已编译扩展、否则就地构建，失败静默回落 numba。⚠ **开后有 fp32 级漂移**（~1 ulp，**非逐位等价**）；⚠ **昇腾端到端收益无实测** |
| `--readout-pipeline` | **关** | **保留但停用，传入即 fail-fast**（报错退出，§8.3） |
| `--cann-dispatch` | **关** | **不新增行为**，只核对 P120 已默认开的 `TASK_QUEUE_ENABLE=2`/`COMBINED_ENABLE=1` 是否真生效（官方列了两个静默失效条件，都不打日志） |
| `--accel-devices` | 1 | N>1 时读出按词表行切 N 卡（ShardedAccelReadout）。等价判据 fp32 容差 1e-6（max\|d\|=1.49e-08），**非逐位**；预期上限 1/(1−0.196+0.196/N)（N=4 → 1.15×） |

### 1.5 日志字段与读法

| 字段 | 读法 |
|---|---|
| `sliding PPL … X ms/tok` | 端到端步时。**跨 run 比较必须同数据、同 `--remote-fraction`、同机器、同 token 预算** |
| `readout X ms/tok (后端@设备, Y% of total)` | 读出分项。`% of total` 直接判断加速是否生效、耗时是否转移到 PC 栈 |
| `loop: tokenize A  encode_onehot B  step C` | **主循环三段**（需 `--step-profiling`）。此前主循环开销从未被测量 |
| `segments(cum): <名> <ms/tok> …` | **`net.step` 内部九段的历史平均**（从 token 0 起累加，`_prof` **从不清零**）→ ⚠ **混着启动期编译开销（含 JIT 冷编译），系统性高估稳态**。判断加速生效看下面这行 |
| `segments(win): <名> <ms/tok> … [N steps]` | 上一个打印间隔内的**真实平均**。**做性能判断一律用这行**。这就是「readout 从 28.77 衰减到 7.68」的真相——不是模型变快，是早期昂贵样本被摊薄 |
| `HBM-bw X%/vec Y%/aicpu Z%` | 来自 `npu-smi info -t usages`，每 4 tick 抽样。**判读规则：高 AICore + 低带宽 = 瓶颈在 kernel 下发/调度**，既不在算力也不在 HBM 带宽。⚠ 高 AICore 单独**不能**说明算力用满（大量小 kernel 也能顶到 99%） |
| `CPU …%  proc X核 … CS/s … GC …` | `proc X核` = 进程实际用核数；`CS/s` = 上下文切换频率（线程空转的指纹） |
| `NPU/GPU …%  HBM …GB` | AI Core%（瞬时，设备忙不忙）与 HBM（host 侧计数器）。**AI Core% ≠ 带宽利用率**，见 §三 |
| `[readout] backend=… \| fallback reason: …` | **读出是否真在设备上**。判断加速生效看这行，**不看「检测到设备」** |
| `[readout] compute precision = …` | 读出实际精度。精度降级必须在这一行可见 |
| `[parallel] numba prange threads = N … OMP_PROC_BIND=… BLAS/OpenMP threads=N` | 线程治理是否真生效（§八） |
| `[numba] cache dir = … size = X MB` | 持久缓存是否命中（命中启动 ~2.6 s） |
| `[ltm-diag] imprints=… / recalls=…` | LTM 规模与召回遍历量演化（每 10 次触发） |
| `[log] start: … argv: …` | 完整命令行。「行为没生效」**先查这里**，再查代码（`BUGS.md` E6） |

### 1.6 九段 + 三段的正确读法

**九段**（`phdnet/model.py` 的 `_prof_t` / `_prof_end` 段名）：
`M1_encode` / `M2_infer` / `M3_pred` / `M5_mod` / `M4a_wm` / `M4b_ltm`（内嵌 `M4b_imprint`）/
`PC_learn` / `STDP_learn`。

⚠ **`readout` 不在 `segments` 里** —— 它走独立累计器，打印在训练主行的
`readout X ms/tok`。所以 `segments` 之和**天然不含读出**，对账时必须把主行的读出值加进来。

⚠ **`M4b_ltm` 只覆盖 imprint 分支**。recall 分支没有独立计时，其时间落在
「九段之和 + 读出 ≠ `loop.step`」的差额里。

三步读法，缺一步就会得出错误结论：

1. **先对账**：`loop.step` 是否 ≈ 主行的 `ms/tok`。不等则差额在主循环或计时之外。
2. **再求和**：`segments` 九段之和 **+ 主行读出值** 是否 ≈ `loop.step`。
   不等则还有未计时的工作（已知两处：recall 分支、`critical_period` 突触修剪在 `PC_learn` 计时之外）。
3. **最后看趋势**：同一 run 内把 `segments` 按 token 数排成序列。
   **绝对值小但超线性增长的段才是真元凶** —— 2026-09-29 的 M4b 就是这样定位的：
   token 1500 时 `M4b_ltm` 仅 0.14 ms/tok，token 3500 涨到 19.54，
   同期 `M2_infer` 反而从 5.05 降到 2.70。

> 只看「当前最大段」会追错目标：那一段可能正在下降，而下一段正在超线性增长。
> ⚠ **趋势只能在同一 run 内读**——`segments(cum)` 混着启动期编译开销（含 JIT 冷编译），
> **判性能一律看 `segments(win)`**（见 §1.5）。

## 二、当前性能基线

> **本节分项归因基线口径（P113）**：`1b` 档（width=1024、conn_k=128）、vocab 51,962、
> 昇腾 191 核 + NPU、`--readout-conn-k 128`、`--readout-dtype fp32`、`--m2-kernel plain`、
> 16 个远程分片。来源：`train_1b_1b_pretrain_20261001-182721.log`（`[日志]`）。
>
> ⚠ **本节所有 12.09 / 7.83 / 1.28 等数字都属于 P113（plain）**。
>
> ⚠⚠ **口径提醒（易踩）**：读出默认精度历经 fp32 → fp8 → **回到 fp32**，
> fp8 阶段的 run 与本节数字**不可直接比较**（精度口径不同）。与本节对比必须显式带
> `--readout-dtype fp32`（现在恰好等于默认值）。
> 上一段的 17.63 / 7.68 / 6.92 属于 serial 口径，**只在 §2.1 的 A/B 对照表里出现**，
> 其余章节不再复述，避免两个口径混用。

### 2.1 端到端：现行 vs 历史对照

**一、现行服务器实测（2026-11-01，`train_1b_1b_pretrain_20261101-140007.log`）**：
端到端 **10.8 ms/tok**（CPU 侧 6.5 / NPU 读出 3.5），24.5k token 稳态。

**二、P113 口径的 A/B 对照表**（下表全部为 P113 口径，用于分项归因与倍数复核）：

| 量 | serial 口径（P111，`-172245.log`，**历史对照**） | plain 口径（P113，`-182721.log`，**现行归因基线**） | 倍数 |
|---|---|---|---|
| 端到端 | 17.63 | **12.09** | **1.46×** |
| 读出（NPU） | 7.68（43.5%） | **7.83**（**64.7%**） | — |
| `M2_infer` | 6.92（单核） | **1.28**（行级 prange） | **5.41×** |
| CPU 侧合计（端到端 − 读出） | 9.95 | **4.26** | **2.33×** |
| `M1_encode` | 1.12 | 1.03 | — |
| `M4b_ltm` / `M4b_imprint` | 0.44 / 0.44 | 0.40 / 0.40 | — |
| `STDP_learn` / `M3_pred` | 0.06 / 0.05 | 0.06 / 0.04 | — |
| `tokenize` / `encode_onehot` | **未采集** | 0.02 / 0.02 | — |

⚠ **serial 列的任何数字都不得单独引用** —— 它描述的是一个**已被换掉**的配置。
留在本文档里的唯一理由是**让 5.41× / 1.46× / 2.33× 这三个 A/B 倍数可复核**。

⚠ **读出绝对值几乎没变（7.68 → 7.83）**，所以端到端的 1.46× **全部来自 CPU 侧**
（M2 6.92 → 1.28 省下 5.64，摊平到其它 CPU 段后端到端省 5.54）。
**读出占比从 43.5% 涨到 64.7% 不是读出变慢了，是分母变小了。**

**零回归证据**：P113 与 serial 两个 run 在四个采样点
（10250 / 20250 / 30250 / 40250 token）的 sliding PPL **逐位完全相同**：
**38101.949 / 25042.421 / 22693.449 / 19602.394**。

⚠ 这份「逐位相同」是**生产日志观测**（两次 run 的其余条件相同，但不是同进程内比），

P113 的采样点止于 40250 token，**未跑到 56k**，所以它与 serial run 的稳态**不可比长度**。

## 三、访存与带宽账

> **GEMV 是带宽受限负载。** 判断优化空间时看**字节流量**，不看「利用率」——
> 一个 99% AI Core% 的 kernel 完全可能只用了估算带宽的个位数百分比（§3.5 实算）。

### 3.1 稀疏 vs 稠密的访存账（1B 档，设计词表 vocab 73,958 × n_h 3,072）

⚠ **两套词表口径，不要混用**：
- **73,958** = 设计态满词表（`tools/bench/bench_readout_devices.py` 的缺省 `V`），用于访存/带宽**上界**估算。
- **51,962** = 本次训练实建词表（`[日志]`），实际读出规模比上界小 30%。

| 布局 | 每步字节 | 相对稠密 |
|---|---|---|
| 稠密 fp32 W | **866.7 MiB**（= 908.8 MB） | 1.0× |
| **稀疏 k=128**：`val` fp32 37.9 MB + `idx` int64 75.7 MB | **113.6 MB** | **8.0× 省** |

⚠ **8.0× 是含 idx 开销的真实比值**（75.7 MB 的 int64 索引占了总量的 2/3）。
若只看 `val`，会得出 24× 的错误结论。

### 3.2 CSR 内存账与 25% 交叉点

| 布局 | 每突触/每权重字节 |
|---|---|
| CPU 侧 CSR（`phdnet/sparse_pc.py`：`idx` int64 + `val` float64） | **16 B/突触** |
| 稠密 fp32 | **4 B/权重** |

**交叉点 = 密度 25%**（`16 B × d = 4 B` → `d = 0.25`）。
即：**CSR 在密度 >25% 时反而比稠密 fp32 更大**。
1B 档 `k/n_in = 128/3072 = 4.2%`，在交叉点以下 6 倍，稀疏成立。
⚠ 这也解释了为什么 §3.1 的 8.0×（4.2% 密度）低于理论上限 `1/0.042 = 24×`。

来源：`tools/bench/bench_readout_sparse.py` 的 docstring（数值推导）+
`[日志]` 1B 档实测 113.6 MB。

### 3.3 ⚠ 稠密读出的旧口径（**已作废**）

> 稠密 866.7 MiB × 3 = 2600 MiB/步 的旧账**已作废**：分子用**稠密** W、
> 分母却是**稀疏臂**实测，且 `MiB → GB` 换算也差 5% → 「**带宽已用 21%**」这句话不得再引用。
> 更早的 bf16 稠密 960 MB/步 → 137–175 GB/s（≈HBM 9–11%）同为稀疏化之前的口径，同样只作历史对照。
> **正确诊断见 §3.5**（结论：不是带宽饱和，是算子效率问题）。

### 3.4 为什么 NPU 迁移是唯一出路（不是调优）

| 路径 | 实测 | 结论 |
|---|---|---|
| ~~CPU numba 读出核~~ | ~~43 GB/s ≈ DDR4 上限，`fastmath` 无收益~~ | ⚠ **该结论建立在错误的性能画像上**，已作废（方法论见下） |
| NPU gather-GEMV（现行） | 7.83 ms/tok（`accel:npu`），P113 口径 | 唯一出路已走通 |

**方法论教训（结论已推翻，教训成立）**：① 「CPU 侧已饱和」的错误画像源于**真实瓶颈一度在
Python 校验层**（`_check_csr` 对 9.47M 元素全量 `idx.min()/idx.max()` 扫描，单次 6.05 ms
= `m2_matvec` 总耗时的 65.8%），而非内核本身；② 「换核后仍慢」可能只差一个 **dtype 转换**
（漏 `int64→int32`）；③ **先量封装开销，再谈内核优化**。这三条已由 §7.1 / §7.2 覆盖。

**P76 否掉的是 prange 融合核，不是 CSR matvec 自身的行级并行** —— `plain` 已于 P113
服务器实测采纳为默认（5.41×，§4.2），这条区分已被实践验证。

### 3.5 ✅ 读出带宽诊断：不是带宽饱和，是算子效率问题（`tools/diag_readout_npu.py` 实算）

**这是读出优化的第一份实算诊断**，工具 = `tools/diag_readout_npu.py`（同步点静态扫描 + 字节流量拆解）。

**稀疏臂每步触达字节 = 229.15 MiB**，拆解如下（fp32 `val` + int64 `idx`，
vocab 51,962、k=128、**`mulsum` 前向口径**）：

| 环节 | 触达字节 | 倍数 |
|---|---|---|
| `idx`（int64 列索引） | 50.74 MiB | **2×** |
| `val`（fp32 权重本体） | 25.37 MiB | **3×** |
| 临时张量 `g`（稀疏 gather 出的 `(n_out,k)` fp32） | 25.37 MiB | **2×** |
| `dp`（感知器误差向量） | 0.59 MiB | — |
| **合计** | **229.15 MiB/步** | — |

**下界与实测的差距（本节唯一的核心结论）**：

| 量 | 值 | 口径 |
|---|---|---|
| 每步触达字节 | **229.15 MiB** | `[工具]` `diag_readout_npu.py` 实算 |
| 带宽假设 | ~800 GB/s | ⚠ **这是估算假设**，不是实测 HBM 带宽 |
| 搬运下界 | **0.300 ms** | 229.15 MiB ÷ ~800 GB/s，**估算值** |
| 实测墙钟 | **7.83 ms** | `[日志]` P113 |
| **实测 / 下界** | **26.1×** | — |

→ **不是带宽饱和，是算子效率问题。**
⚠ **绝对不要把 0.300 ms 当实测**：它依赖「~800 GB/s」这个假设带宽
（本项目 HBM 标称 ~1.6 TB/s，但稀疏 gather 的有效带宽远低于标称），
**下界是估算值**，这一点已写进工具的 docstring（引用纪律同 `BUGS.md` A8/B12）。

**同步点：已清零（静态扫描确认）**。`diag_readout_npu.py` 的静态扫描确认
读出热路径**已无设备同步点** —— 唯一一处每步 `torch.equal` 硬同步已修掉（P112）。
→ **所以 26.1× 的差距不能归因于「CPU 被设备等住」，只能是算子本身的效率**
（gather 指令效率、elementwise 临时张量、kernel launch 串行）。
⚠ 但**静态扫描只能证明「没有显式同步原语」**，不能证明设备端没有隐式同步；
后者需要 CANN 级 profiling（msprof）。

> ### 正确表述（对照 §3.3 的作废表述）
> **不是带宽用满了，也不是算力用满了。** 每步只触达 229.15 MiB，
> 按 ~800 GB/s 估算下界只有 0.300 ms，实测 7.83 ms 是它的 **26.1×**。
> 提高设备利用率只能靠改算子实现（融合、减少临时张量、减少 launch），
> **批处理是唯一能摊薄访存量的手段，而它违反铁律③ → 出局。**

### 3.6 ⚠ 三套字节口径刻意并存（**不要强行统一**）

| 口径 | 字节/步 | 词表口径 | 来源 | 换算 | 可用结论 |
|---|---|---|---|---|---|
| ① 稠密（**已作废**） | 2600 MiB | 设计态 73,958 | 旧文档口径 | 1.6 ms 下界 | ❌ 分子稠密 / 分母稀疏臂，**不可用** |
| ② 稀疏·设计词表 | **492.5 MB** | 73,958 | 《并行与加速架构分析》§3.3 复算 | 64.1 GB/s ≈ HBM 4.0% | 仅供访存**上界**估算 |
| ③ 稀疏·实建词表 | **229.15 MiB** | 51,962 | `diag_readout_npu.py` 实算（§3.5） | 0.300 ms 下界 | ✅ **26.1× 只能由本行给出** |

## 四、分段剖析与 CPU/NPU 不对称

### 4.1 不对称的量化（P113 口径，`[日志]`）

时间预算树见 §2.2（端到端 12.09 = NPU 侧 7.83 + CPU 侧 4.26，两侧合计 100%，无未拆分余量）。

**对账**：CPU 侧 4.26 = 端到端 12.09 − 读出 7.83，**是减出来的、不是日志直接给的**。
⚠ 早期日志给的是「CPU 侧占 50.6%」这个百分比，
**不要用它乘以任何端到端值反推 ms** —— 那会把一个百分比当成独立测量。

**这是本项目当前最重要的性能事实**：NPU 侧占 64.7% 且已满载，
CPU 侧只剩 35.2%（4.26 ms）。**不对称的方向翻转了** —— 早期是 CPU 侧占一半、
NPU 侧 43.5%；现在 NPU 侧是大头。
⚠ 2026-11-01 的最新批次方向**又反转**（CPU 6.5 / NPU 3.5，§2.1）→ **不对称比例随批次变化，
不可把任何一派的百分比写死成「当前架构事实」**；可写死的是「两侧都不满」。

**191 核不是「算力不够」，而是架构性用不满** —— 两层原因：

1. **逐 token 语义禁止批处理**：状态跨 token / shard / epoch 连续演化，
   读出 W 每步原地更新 → 数据并行（同一 batch 元素互相独立）在语义上不成立。
2. **模型状态跨 token 连续** → 同一样本的相邻 token 不能并行，
   而这是唯一能在不破坏语义的前提下用上多核的并行维度。

⚠ **M2 单核那条（配置性）已被摘掉**（`--m2-kernel plain`，§4.2）。
**剩下的是上面两条架构性的**，论证与量化见《PHD-Net_并行与加速架构分析.md》，本文不复制。

### 4.2 ✅ `M2_infer`：从单核 6.92 到并行 1.28（已采纳为默认）

**历史对照**：稳态下 `M2_infer` 曾占 6.92 ms/tok（39.3%），
是 `--m2-kernel serial` 的**单核**融合核（P99 加入，因为昇腾上 prange 融合核反而慢 3–4×）。

**现行实测结论**：`plain` 服务器实测 **6.92 → 1.28 ms/tok（5.41×）**，
端到端 17.63 → 12.09（1.46×），四个采样点 sliding PPL **逐位完全相同**
（38101.949 / 25042.421 / 22693.449 / 19602.394）→ **纯调度变化、零语义变化**。
**已采纳**（现行 `--m2-kernel auto` 在昇腾 aarch64 上即选 `plain`）。

**当初那个极易被误读的区分，现已被实践验证**：

| 被否掉的 | 没被否掉的 → **实测赢了** |
|---|---|
| **prange 融合核**（`--m2-kernel fused`）：把多次核调用融成一核 + 行间 prange。<br>昇腾实测 fused 20–27 vs plain 6.7–11.9 ms/tok，**慢 3–4×**（`[台账]` D5）。**已否决。** | **CSR matvec 自身的行级并行**：`--m2-kernel plain` 走的 `_csr_matvec`（`phdnet/sparse_pc.py:44`）**有 `prange` + `parallel=True`**，行内串行累加、行间并行。<br>**未被否 → 实测 5.41×，现为昇腾默认。** |

> **⚠ 写文档/做决策时不要把这两件事混为一谈。** P76 否定的是「融合 + prange」这个组合，
> 不是 CSR 行级并行本身。「191 核能否吃掉 M2 那 6.92 ms」曾是一个开放问题，
> 实测给出答案：能吃掉 5.64 ms（5.41×），但 191 核并没有被吃满
> —— CPU 侧整体只从 9.95 降到 4.26 ms（§2.1）。

**零回归门禁**：`tests/gates/gate_m2_infer_kernels.py` ——
三态（fused / serial / plain）在同一进程、同一输入下对拍：
A1 fused vs serial、A2 plain vs serial（**容差**，归约顺序不同，偏差 1e-7 量级）、
A3 `n_steps=1/2/3`（单步一致不代表多步一致）、B 类断言 plain 的行级 prange
**不改变求和顺序**（理论上与 serial 逐位相同）。
⚠ 日志观测到的「PPL 逐位相同」是**跨 run 观测**，本 verifier 才是**受控对拍**。
### 4.3 `M4b_ltm`：从 63.5 ms/tok 降到 0.40 ms/tok

**根因（必须写清，否则会误判为「又一个调优问题」）**：
**`predict` 每步做 18,000 次 Python dict 更新**。
具体量级：256 活跃行 × 约 72 槽 = **1.8 万次 dict 更新 + numpy 标量取值/step**（`[台账]` C3）。
C2 之后 recall 投影已 numba 化，但**跑在已物化的 dict 上** → dict 工作量原样保留。
**这类缺陷的特征是「单步便宜、逐步超线性」** —— token 1500 时 `M4b_ltm` 仅 0.14 ms/tok，
token 3500 涨到 19.54（§1.6 第 3 步读法）。

**当前稳态 = 0.40 ms/tok**（P113 口径；serial 段为 0.44），`[日志]`。

⚠ **关键判断**：这段**故意不上 numba gather 核** —— 1.8 万元素比批量 learn 的
64 万组合小两个数量级，核的固定开销会吃掉收益（`[台账]` C3）。

⚠ **诚实边界**：`[台账]` C7 记载 —— imprints 侧的批量核化**本机计时只有 1.0–1.1×**
（x86 Python 在这个规模已经够快），**收益完全押在服务器侧，该结论至今未复测**。
所以「0.40 ms/tok」是 `[日志]` 的**端到端实测值**，
而历史上的 44.6× / 21.9× / 1.44× 三个倍率是 **x86 本机实测**，
**两者不是同一口径，不可相乘外推**。

## 五、平台差异铁律（x86 ≠ 昇腾）

**四次方向相反的实测**：

| 改动 | x86 本机 | 昇腾 aarch64 |
|---|---|---|
| **M1 编码器 fp32** | 快 **1.80×**（606.7 → 337.7 µs） | 慢 **约 70×**（0.85 → 58–60 ms/tok） |
| **M2 融合核**（`fused` vs `plain`） | 快 **1.15–2.16×** | 慢 **3–4×**（fused 20–27 vs plain 6.7–11.9 ms/tok）⚠ 早前记为 8–13×，见附录 A。⚠ **该 plain 值是另一批 run**（线程配置未标），与 P113 的 1.28 ms/tok **不是同一口径** |
| **`--m2-kernel serial` vs `plain`** | 未 A/B | **plain 赢 5.41×**（6.92 → 1.28 ms/tok，P113）。⚠ 这是**同族反例的另一面**：同一条 CSR 行级 prange，在 x86 上无可测差别、在昇腾上赢 5.41×——**说明 x86 连「无差别」都不足以推断昇腾** |
| **`OMP_PLACES=cores`** | 无感 | 慢 **约 8×**，CS/s 升到 650 万 |

> ### 规则：x86 的性能结论不构成昇腾的证据。
> 任何优化必须在**目标机器**复测。本文凡标「x86 本机」的数字只在本机成立。
> **「无差别」同样不构成证据** —— 上表第三行是「同一条代码在两个平台结论相反」的直接反例。
> 文档中出现的**计数器开关**就是这条铁律的产物：`--m2-kernel`、`--encoder-dtype`、
> `--readout-dtype`、`--sparse-fwd-kernel`。

**唯一一条在两个平台都成立的规则**（`[台账]` D1/D2）：

> **GEMV/GEMM 前必须 `W.dtype == x.dtype`。**

fp32 权重 @ fp64 输入会**脱离 BLAS 的 sgemv**，走逐元素慢路径，
实测退化 **5.9×**（x86：857 → 5047 µs，修复后 606.7 → 337.7 µs）。
在 aarch64 上这条规则更严 —— fp32 sgemv 本身**慢约 70×**，
`phdnet/sparse_encoder.py` 因此做**平台自适应**：aarch64 走自写 numba GEMV
（`_gemv_rows`，行间 prange、行内顺序累加，容差 1–2 ulp），x86 保留 BLAS。

⚠ **混合 dtype 是隐形缺陷**：它不报错、结果正确，只是慢 ——
**在所有正确性门禁下都是不可见的**（`[台账]` D2）。目前**没有任何断言检查 `A.dtype == b.dtype`**。

⚠ **门禁覆盖不对称**：平台分支意味着两条路径的门禁覆盖不同 ——
`_gemv_rows` 只在 aarch64 生效，**x86 CI 永远跑不到它**（`[台账]` D3）。

## 六、精度与速度的取舍

### 6.1 读出精度的实测保留率（`tools/probe/probe_readout_precision.py`，`[工具]`）

**判据**：同精度舍入后元素是否**真的变了**（更新是否被保留）。
量级 `|W| ~ 1e-2`、`|dp| ~ 1e-6`（感知器 `p − t` 的非目标行更新）。

| 精度 | 非目标行保留率 | 目标行保留率 | 判读 |
|---|---|---|---|
| fp32 | **99.95%** | 100% | 语义正确（**现行默认**） |
| fp16 | **26.67%** | 100% | 73% 的非目标行更新被丢弃 |
| bf16 | **5.79%** | 100% | 94% 被丢弃 |
| **int8 / fp8** | **0.04%** | 92.19% | 几乎全丢（非目标抑制项基本消失）；e4m3fn 步长比 fp16 粗约 4× |

⚠ int8/fp8 行来自**真实生产码本**路径实测（`tools/probe/probe_precision_keep.py`，
口径 `n_out=2000, n_in=128`）；上表 fp32/fp16/bf16 三行是 P110 的**模拟舍入**口径。
两套口径在 fp32/fp16/bf16 上互相印证（差异 ≤0.55 个百分点），**结论可信**。

**目标行基本 100%**（目标更新 `~1e-2` ≫ 半 ULP）→ 低精度不是「完全不学习」，
而是**丢掉了非目标行的抑制项**。

> ### 结论：低精度的速度收益伴随语义损失，不能只看快。
> `p − t` 规则的非目标行更新被舍入 → 学习**部分退化为纯 Hebbian**
> （只提升目标行，无抑制）。

### 6.2 fp8：硬件限制、软件绕行与主权重模式

**硬件限制（`[台账]` B4/B11）**：

| 平台 | 实测 |
|---|---|
| 昇腾 Ascend910B4 + CANN 8.5 + torch_npu 2.9 | `float8_e4m3fn` / `float8_e5m2` 的 **create / cast / matmul 全部 ERR01007**；`torch.ops` 里**零个 fp8 算子** |
| CPU torch | 能分配 fp8 张量，但**无 fp8 addmv**（炸在 `@`） |

**软件绕行**：fp8 显式请求一律进候选链首（探测决定），910B 上走
**fp8 e4m3fn 位模式（uint8 承载）存储 + fp16 迭代计算**，访存与原生 fp8 相同（1 B/元素）；
前向可选每步 CPU 转换 int8 码本走真实存在的 int8 算子（`--fp8-conv` 选核）。
机制细节见《PHD-Net_硬件后端适配报告.md》§3.2，本文不复制。
⚠ 能力表里的一行「不支持」只能靠**目标机器实测**确认。

**主权重模式（DeepSeek-V4-Flash 模式）—— 现行正解**：
§6.1 的失败模式**不是 fp8 本身的问题**，而是**没有高精度累加器**：
**master weight = fp32 常驻**（所有更新作用于此 → 非目标行更新 **100% 保留**）+
**影子副本 = fp8/bf16/fp16 位模式**（只做前向 GEMV → 保留低精度访存收益）+
**每 `shadow_refresh` 步重量化一次**（默认 8，摊薄量化成本）。
即：**「fp8 的精度」= 前向访存/存储省 2–4×；「fp16 的迭代精度」= 实际更新在
fp32 master 上，比 fp16 更准**（dp/ht 仍按 `_cdtype`=fp16 算，保持迭代精度口径）。

**本机 A/B**（`tests/checks_p195.py --ab`，固定探针集，P146 纪律）：

| 配置 | PPL | vs 无 master | vs fp32 基线 |
|---|---|---|---|
| accel fp8 无 master | 2.84 | — | +33.5% |
| **accel fp8 + master (r=8)** | **2.15** | **−24.2%** | **+1.1%** |
| numba int8(=e4m3) 无 master | 2.83 | — | +33.2% |
| **numba int8 + master (r=8)** | **2.15** | **−24.1%** | **+1.2%** |

`r=4 → 2.15 / r=16 → 2.20`（staleness 与量化频度的权衡，默认 8 = DeepSeek 同款折中）。
**两条臂行为一致**（加速 / numba 回落）—— 这是 GAP-4 修复的结果：主权重参数
原来只接线到 `AccelReadout`，`--accel cpu` 下 silently 失效。

**代价**：多一份 fp32 master（1b 档 866.7 MiB）；前向有最多 N 步 staleness；
torch.compile 融合核被禁用、NPU Graph 的重量化移出图外。
故**默认 off**（不知情的人不该被动多付一倍内存），显式 `--readout-master-weight` 开启。

**检查点**：master 的 fp32 精确值**逐位**往返（`ro_W` 跳过 `ckpt_dtype` 压缩，
否则 §6.1 的精度收益归零）；非 master 模式按影子粒度恢复（与训练期同一把尺子）。

⚠ **两条方法论教训**（`[台账]` B13）：

1. **半 ULP 的数量级估算不能替代实测。** 曾判定「fp16 半 ULP 比 bf16 小 8 倍，
   能保住非目标行更新」→ 实测证明 fp16 只是「比 bf16 好」，**离正确还差一个数量级**。
   「8 倍差距」在跨越两个数量级的问题面前不成立。
2. **精度判据必须用同精度舍入后的基线。** 第一版拿 fp32 值与 fp16 值直接比，
   得到「fp16 保留 100%」的**反向假阳性**（fp32 值与 fp16 值几乎总不相等）。

⚠ **本节全部数字来自 `[工具]` 在 x86 本机的构造量级测量**，
反映的是舍入机制本身（dtype 半 ULP 是纯数值性质，与平台无关），
但**「哪种精度跑得快」的平台相关部分不在此表**。

### 6.3 低精度在本机 CPU 上是计算受限而非带宽受限

`[工具]` x86 本机读出更新核实测：fp32 **13.3 ms** vs fp16/bf16 **226 ms**（**慢 17×**）。
死因是**位运算重量化 > 带宽节省**。
→ **在 CPU 上「降精度换速度」是反的**；低精度的收益只在存储压缩与加速器原生张量核。
⚠ 此为 x86 口径，昇腾未复测。

### 6.4 `eta_oja > 0` 正反馈发散（生产规模实测）

曾把 `eta_oja=0.02` 作为默认（与表征发育的 `eta_pc=0.02` 一同）。
**生产规模（n_top=256 / 40K token）实测：3000 步后 probe_PPL 从 3403 恶化到 9.1e11。**

**根因**：`eta_oja` 更新上行识别权重（`up0/up1`），而这些权重**改变
`pc.infer` 的前向计算**（`r1/r2 = tanh(up · x)`）；`r1/r2` 又喂给 STDP
（`predict`/`step`）与读出（`_build_h`）——形成**正反馈环**。对比：

| 配置 | 3000 步后 probe_PPL |
|---|---|
| `eta_pc=0.02, eta_oja=0.02`（**已作废的旧默认**） | **9.1e11**（发散） |
| `eta_pc=0.02, eta_oja=0`（**现行默认**） | **916** ✅ |
| `eta_pc=0, eta_oja=0`（冻结主干，失去表征发育） | 1104 ✅ |

**发散机理**（逐层实测定位）：
1. STDP 权重 `|W|` 从 0 → 47（1500 步）；`h` 分量仍正常（max 0.66）；
2. logits `y` 的**动态范围达 55.9**（`y max=41.5, min=-14.4`）——
   softmax 后非最大项全部下溢为 0；target 若非最大则 `p=0` → nll=27.6；
3. 动态范围爆炸源于**上行 Oja 与 STDP 互相放大**：Oja 把 r1/r2 的尺度
   越推越大，STDP 的 `pred_feat` 随之增大，读出为拟合而拉大权重，
   反过来又影响 STDP 的 `prev_rate`。

**修法**：`eta_oja` 库默认改为 0.0，`build_cfg` 显式 0.0；
`PHDNetConfig.__post_init__` 对 `eta_oja > 0` 发 **RuntimeWarning**
（不 raise——发散与规模相关，小规模/短跑的机制测试合法地用 `eta_oja>0`）。
⚠ **表征发育窗口仍成立**（`eta_pc=0.02` + `pc_dev_steps=20000` 余弦退火，发育期后冻结）：
被推翻的只是 `eta_oja>0` 这一项（Oja 上行权重参与前向 → 正反馈环；eta_pc 本身无此问题）。

**验证**（`eta_pc=0.02, eta_oja=0`，40K token / 3392 词表）：
probe_PPL 从 3403（≈随机 3392）→ 1,000 步 **1512** → 5,000 步 **620** →
30,000 步 **389** → 40,000 步 742。**bigram 合法率 78%**（对比旧配置 5–13%），distinct 76.5%。
**PPL 从 3403 → 389（约 11×）**——读出头真的学会了语言的局部统计。

### 7.1 三条通用教训

1. **核的固定开销要先算**：访存/调度受限规模上，加并行度前先算核启动 + 线程同步成本。
2. **逐位对拍的基线必须是同库、同 fastmath 口径的串行实现**，否则满屏假阳性。
   ⚠ **假阳性比没测试更危险** —— 它会让人去「修」正确代码（`[台账]` E1）。
3. **计时必须复现「命中位置随机 + 行已满 + 真实规模」**。
   `[台账]` E5 记载：本机 800×800 组合 0.36 ms，服务器 6.5 万组合 19.5 ms/tok（**约 54 倍**），
   因为服务器 `active` 只有 256、且 aarch64 的 Python 解释器与 dict 访问更贵。
   → **本机复现与服务器差一个数量级时，本机结论作废。**

### 7.2 追加的两条（**代价最大的两条**）

4. **先量「绕过封装 vs 完整封装」的差，再谈内核优化。**
   曾花在「某个融合核 vs numba 内核谁快」上的功夫全部作废，
   因为 65.8% 的时间在 **Python 校验层**（`idx.min()/idx.max()` 全量扫 9.47M 元素）。
   → **任何性能结论必须先回答：被测代码占总耗时的多少？**
5. **门禁 FAIL + 注释写「如实标注未生效」→ 先信门禁、查数据 dtype。**
   曾据此判定「某个融合核不可用」并回退，真因只是**漏了 int64→int32 转换**。
   → **「已知的坏」不等于「不可修」；先定位根因再下废弃结论。**
   ⚠ 附带：**修好数值后必须重新测性能** —— 修好后仍慢 3.2×（idx 转换 1.85 ms/次
   超过核本身 1.01 ms），需配套缓存才真正变快。

## 八、线程治理与待验证候选

> ⚠ **本节现在的定位**：M2 核选择已实测并采纳（§2.1 / §4.2），不再是候选。
> 下面是「线程治理现状 + 7 条仍待实测的候选」。

### 8.1 线程治理现状

**四个 BLAS 变量（`OMP_NUM_THREADS` / `OPENBLAS_NUM_THREADS` / `MKL_NUM_THREADS` /
`NUMEXPR_NUM_THREADS`）在 `import numpy` 之前 cap 到 8**（OpenBLAS 初始化后再设**无效**），
`OMP_PROC_BIND=close`，**不设 `OMP_PLACES`**，**`--numba-threads 16`**。

生效情况看启动行 `[parallel] numba prange threads = N … OMP_PROC_BIND=… BLAS/OpenMP threads=N`。

**为什么 BLAS 上限是 8 而不是更多**：

| 实测 | 值 | 平台 |
|---|---|---|
| 核内 1 → 6 线程 | 仅 **1.16×** | x86 本机 |
| 本机融合核带宽墙 | 1 → 8 线程 4.1 → 9.3 GB/s（**次线性**） | x86 本机 |
| 两张 ~64 MB 哈希表 | 远超 L3 → 瓶颈是内存流量 | — |

→ **超过 8 线程不再有收益，只增加调度与空转成本。**
⚠ `numba` 上限现为 **16**（P204 由 8 改），但**本机 x86 上 16/32 是 fork/join 负收益区**
（屏障 4.7 → 24.7 → 64.3 µs/区）→ **服务器 A/B 仍待做**（§8.3 候选 5）。

**三个必须知道的时序约束**（**违反后无法事后补救**）：

| 约束 | 违反后果 |
|---|---|
| BLAS 线程上限必须在 **`import numpy` 之前**设 | 191 线程跑 1024×2048 的 sgemv → 1.1 核 + 百万级 CS/s |
| `numba.set_num_threads` 必须在**任何核首次执行之前** | 线程池首次调用时定型 → 191 线程跑千行级 `prange` → 纯空转 |
| `OMP_PROC_BIND` 必须在 **numba 初始化之前**进环境 | 绑核在 OpenMP 初始化时生效，**事后补不上** |

⚠ **门禁缺口**：这三条**都无法在 CI 上验证**（CI 机器核数不同）。
→「限线程」的正确性**依赖部署机器的核数**，只能人工确认（`[台账]` B10）。

### 8.2 预取：只做跨文件并行

| 项 | 现行做法 | 依据 |
|---|---|---|
| `--prefetch-workers` 默认 | **`min(8, 核数×0.8, 文件数)`** | 单生产者按文件序归并，囤积 ≈ 0（`--prefetch-depth` 受此约束） |
| 为什么不做 token 级并行 | 单生产者时在途量 ≈ 0 | 真正有效的是跨文件并行 |
| 组大小 | 32M → **1M 字符** | 32M 组时并行度塌缩（组数 ≪ worker 数），且每组数百万 token 的字符串 pickle 成单点 |
| pyarrow 解码 | 库内多线程且释放 GIL | **单进程即吃满核**，多进程只增内存（每进程 ~100–200 MB） |

### 候选 2 的结论（2026-10-08）：**前提被推翻，本轮不做**

这条候选自 P113 起就是「收益最大、代价也最大」的架构级项。**代码级核对结论是它的前提不成立**：

1. **训练步的设备路径本来就没有阻塞式同步。** `phdnet/model.py` 走 `self.readout.forward_dev(h)` ——
   返回**设备张量、零同步**；训练步把 `y` 置 `None`（不需要 numpy 化）。
   `step()` 内**唯一**的显式 D2H 是 `nll_dev.item()`，被 `nll_sync_every=8` 门控（默认 8）。
2. **因此「12.09 = 4.26 + 7.83 完全串行」若真存在，成因不是代码里的显式同步**，
   而是**运行时下发 / 队列背压**（与 msprof 的 `aclnnIndex` 占 89.3%、
   `aicore_time=0`、`wait` = 耗时 6.8× 指向同一处）。**证实这一点需要服务器 msprof，本机无法验证，故不给任何结论。**
3. **跨 token 流水会改变 `_prev_rate` / `_exp` 的推进时机 = 换一套时序规则（违反铁律③）。**
   前移 `learn_softmax` 等学习段后，`STDP_learn(self._prev_rate, rate)` 读到的就不再是**上一步**的 rate
   （`phdnet/model.py` 的 P117 注释早已据此明确拒绝前移，本轮核对**确认该判断成立**）。
4. **唯一的跨 token `y` 依赖是 `readout_recurrence`**（`phdnet/word_lm.py`，默认 **False**）。
   一旦打开它，流水会让 `recur_cue` 拿到**上一步**的 y —— 这是**静默的语义错误**，比它可能带来的收益更危险。

→ **配置位保留但 fail-fast**：用户若传 `--readout-pipeline`，`train/train.py`
**直接报错退出**（`SystemExit`，退出码 1，发生在建模之前、无任何副作用）。
理由：留一个「开了没反应」的开关是最坏的一种 API —— 用户会以为自己在跑一个优化。
门禁 `tests/gates/gate_cpu_npu_overlap_contract.py` 把上述四条钉死。

### 推理侧：为什么同样**不加**流水（这不是「还没做」，是**提法要更正**）

1. **推理步的读出走硬 D2H**：`readout(h)` 末行 `y.float().cpu().numpy()`
   （`accel_readout.py`），而训练步走 `forward_dev` 零同步。
2. **自回归依赖是定义性的**：token t+1 的输入就是 token t 采样出来的结果 →
   **推理阶段 CPU 与 NPU 天然串行，无法重叠**。任何声称能给推理做跨 token 流水的方案，
   都必须先解释它如何突破「下一步输入依赖上一步输出」这个依赖。
3. **完整 y 回读不是数学上的必需**：当前实现由 host 采样（`infer.py` 的 `y.astype(np.float64)`），
   因此先完整 D2H；**设备端采样或减少传输仍是候选**，须保持采样语义并做独立性能验证。
   不应把当前实现的 host 等待统称为不可优化的语义要求。
4. ⚠ **本节不产生任何新的性能数字。** 本机（x86、无昇腾）实测推理采样段的
   host 侧数学（V=51,962、top-k=8、200 次取均值）约 **0.77 ms/token**
   （softmax 0.26 + argpartition 0.43 + 子集采样 0.01 + 归一化 0.07），
   但**这是 x86 口径、且未计入 D2H 与 NPU GEMV**，**不能**据此推断昇腾收益。
   唯一能确定的是：它只占训练步 CPU 侧 4.26 ms 的约 18%，**不是主要矛盾**；若要优化推理，先测 D2H 本身。

⚠ 7.83 ms 仍是 `max(两侧)` 的**理论上限**，不是实测；当前无任何实测重叠数据，收益估算一律不写。

4. **换核后缺 PPL 级门禁**。M1/M2 换核后 relerr ~2e-07 在 1e-5 门内，
   但**尚未跑 PPL 对照** → 换核必须配 PPL 级门禁。
