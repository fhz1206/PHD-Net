## 一、测量方法

**没有测量方法就没有性能数字。** 本项目的性能结论全部来自下面这一套固定方法；
换方法即换口径，数字不可跨表比较。

### 1.1 影响测量的开关

| 开关 | 默认 | 为什么影响测量 |
|---|---|---|
| `--step-profiling` | 关 | **唯一的分段计时来源**（P35 九段 + P72 主循环三段）。关闭时零开销；不开就只剩端到端一个数，无法归因 |
| `--readout-dtype` | **fp16** | 决定读出的访存量与计算精度（fp8 副本已降级，见 §四） |
| `--fp8-refresh` | 8 | fp8 forward 副本的重建间隔（步）。重建是一次设备算子，摊到 N 步 |
| `--m2-kernel` | **plain** | `fused` 在昇腾退化 8–13×，x86 快 1.15–2.16×。默认随平台定，测速必须显式带上 |
| `--encoder-dtype` | **fp64** | M1 编码器精度。numpy 混合 dtype（fp64 W @ fp32 x）会脱离 BLAS → 慢5.9× |
| `--numba-threads` | 8 | numba `prange` 线程上限（0 = 不限）。191 核上不限必然空转 |
| `--omp-proc-bind` | 开 | 设 `OMP_PROC_BIND=close`。**不再设 `OMP_PLACES=cores`**（已撤，见 §五） |
| `--nll-sync-every` | 8 | nll 设备侧累积间隔。默认 1 时每步 `.item()` 把 NPU 延迟全额暴露给 CPU，流水永不重叠 |
| `--torch-compile` | 关 | inductor 在昇腾首次调用才编译，失败会崩生产。测速时保持默认关闭，否则测的是编译回落路径 |
| `--prefetch-workers` | 0（单进程即吃满核） | 数据加载。pyarrow 解码在库内多线程且释放 GIL，多进程只增内存 |
| `--ckpt-every` | 50000 | 检查点硬停顿的触发间隔（当前 0.8–37 s，见 §3.2） |

### 1.2 日志字段与读法

| 字段 | 位置 | 读法 |
|---|---|---|
| `sliding PPL …  X ms/tok` | 训练主行 | 端到端步时。**跨 run 比较必须同数据、同`--remote-fraction`、同机器** |
| `readout X ms/tok (后端@设备, Y% of total)` | 训练主行 | 读出分项。`% of total` 直接判断加速是否生效、耗时是否转移到 PC 栈 |
| `loop: tokenize A  encode_onehot B  step C` | 主行下一行（需 `--step-profiling`） | **主循环三段**。此前主循环开销从未被测量，导致「分段之和 < 总耗时」的缺口无法归因 |
| `segments: <名> <ms/tok> …` | 再下一行（需 `--step-profiling`） | **`net.step` 内部九段**，按耗时降序取前 6（`_prof` 累加值 ÷ 已完成 token 数） |
| `[ltm-diag] imprints=… combos=… rate_dims=…/… rows=…` | 每 10 次 imprint | LTM 规模演化。⚠ 门槛必须考虑**触发频率**——imprint 是条件触发，门槛设1000 时 3500 token 一行都不出 |
| `[ltm-diag] recalls=… scores=… bindings=…` | 每 10 次 recall | 召回侧遍历量，随表增长，是 M4b 超线性的**先行指标** |
| `CPU … proc X核 … CS/s … GC …` | 遥测行 | `proc X核` = 进程实际用核数；`CS/s` = 上下文切换频率（线程空转的指纹） |
| `NPU/GPU …%  HBM …GB` | 遥测行 | 设备利用率与显存。**AI Core% 走 `npu-smi` 外部子进程**（`torch.npu.utilization()` 内部同步设备流，会破坏被观测的流水线） |
| `[numba] cache dir = … size = X MB` | 启动行 | 持久缓存是否命中：命中启动 ~2.6 s，未命中会全量编译 |
| `[parallel] numba prange threads = N … OMP_PROC_BIND=… BLAS/OpenMP threads=N` | 启动行 | 线程治理是否真的生效（见 §五） |
| `[readout] compute precision = …` | 启动行 | 读出实际精度。**精度降级必须在这一行可见** |

### 1.3 九段 + 三段的正确读法

**九段**（`phdnet/model.py` 的 `_prof_t`/`_prof_end` 段名，与 `segments` 输出一一对应）：
`M1_encode` / `M2_infer` / `M3_pred` / `M5_mod` / `M4a_wm` / `M4b_ltm`（内嵌 `M4b_imprint`）/
`PC_learn` / `STDP_learn`。

⚠ **`readout` 不在 `segments` 里**——它走独立累计器（`_ro_ms_accum`/`_ro_calls`），
打印在训练主行的 `readout X ms/tok`。所以 `segments` 之和天然**不含读出**，
求和时必须把主行的读出值加进来，否则会误判为「有未归因的缺口」。

⚠ **`M4b_ltm` 只覆盖 imprint 分支**。recall 分支（`elif retrieve_now`）**没有独立计时**，
它的时间落在「九段之和 ≠ `loop.step`」的差额里。因此 M4b 剩余成本归因（开放项 1）
需靠 `M4b_imprint` 与差额的**联合判读**，不能只看 `M4b_ltm` 就断言 recall 侧便宜。

三步读法，缺一步就会得出错误结论：

1. **先对账**：`loop.step` 是否 ≈ 训练主行的 `ms/tok`。不等则差额在主循环（分词/onehot 之外）
   或在计时之外。
2. **再求和**：`segments` 九段之和 **+ 主行读出值** 是否 ≈ `loop.step`。不等则还有未计时的工作
   （已知两处：recall 分支、`critical_period` 突触修剪分支在 `PC_learn` 计时之外）。
3. **最后看趋势**：同一 run 内把 `segments` 按 token 数排成序列。**绝对值小但超线性增长的段
   才是真元凶**——2026-09-29 的 M4b 就是这样定位的：token 1500 时 `M4b_ltm` 仅 0.14 ms/tok，
   token 3500 涨到 19.54，而同期 `M2_infer` 反而从 5.05 降到 2.70。

> 只看「当前最大段」会追错目标：那一段可能正在下降，而下一段正在指数增长。

| 项 | 本机（x86） | 1B 服务器（昇腾） |
|---|---|---|
| CPU / 加速器 | Windows 11 / **8 线程** / 12.6 GB RAM / **无 GPU·NPU** | **191 核** + NPU（~1.6 TB/s HBM） |
| 语料 | `eval_corpus/internal_corpus.txt`（27,034 字符冻结基准）+ `ood_wiki.txt` | ModelScope `fhzfhz/Mixture-General-Mini` 前 30% 分片（HTTP Range 流式） |
| 词表口径 | 小栈 256 维栈 | **51,962 词表 × 3,072 隐层 = 1.596 亿读出参数**（bf16 =319.3 MB） |
| 用途 | 正确性对拍、机制消融、本机微基准、**回归检测** | **性能数字只以本列为准** |

是评测基准（非训练数据）。现行评测锚点见 §八。

> **纪律**：**性能数字只能来自服务器实测。** 本地 x86 **只用于回归检测**
> （判断改动是否引入退化），**不构成任何性能结论的证据**（依据见 §六）。

## 四、访存账（读出为什么是天花板）

读出 W **常驻设备**，每步只往返 h（12 KB 上行）与 y。流量全在 W 上。

| 口径 | 每步访存 | 备注 |
|---|---|---|
| bf16 全程 | **960 MB/步** | forward 读 W（320）+ update 读 W（320）+ 写 W（320） |
| 修复前 | 4,334 MiB/步 | `torch.outer` 物化了与 W 同尺寸的临时张量（1B 档 867 MiB） |
| `addmm_` 融合后 | **2,600 MiB/步（−40%）** | 改 rank-1 AXPY 原地融合，**正好触底**（读一次 + 读写各一次），数值逐位相同 |
| fp8 forward + fp16 更新 | **1.36 GB/步（+42%）** | ⚠ **不是访存收益**，是学习精度收益（见下） |

⚠ **`2 × 320 MB = 640 MB` 是简写，漏掉了 update 的写**。做带宽复算必须用详细账，否则低估 50%。

**为什么是访存受限而不是算力受限**（复算）：

| 量 | 算式 | 结果 |
|---|---|---|
| 单次读 W 的纯搬运下限 | 319.3 MB ÷ 1.6 TB/s | **0.2 ms** |
| 一步完整访存的搬运下限 | 960 MB ÷ 1.6 TB/s | **0.6 ms** |
| 实测读出墙钟 | — | **5.5–7 ms/tok** |
| 反算有效带宽 | 960 MB ÷ 5.5–7 ms | **137–175 GB/s ≈ HBM 的 9–11%** |
| 差值归因 | 5.5 − 0.6 ≈ 4.9 ms | 同步、kernel launch、小 kernel 串行提交 |

**结论**：**访存账是地板，launch/同步账是当前的天花板。**
再往下需要 CANN 自定义算子（把GEMV + softmax + addmm 融成一个核）或 msprof 内核级 profiling。

**fp16/fp8 必须连着精度一起读**：

- 默认 fp16 的动机**不是省访存**（更新侧 fp16 使总访存 +42%），而是**学习精度**：
  bf16 半 ULP ≈ 2e-4 ≫ 非目标行更新 `|dp| ≈ 1e-6` → 更新被舍入 → 学习退化为纯 Hebbian
  → PPL 震荡不降。本机验证：fp16 主副本下 **5,722 个非目标行格点**获得更新（bf16 下为 0）。
- fp8 在**昇腾与CPU 上均已不可用**（`Float8_e4m3fn has not been supported` + ERR01007；
  CPU 无 fp8 addmv）→ 探测必回落，**等同死代码**。fp4 保留代码但未启用。
- 因此「bf16 读出 PPL 略优」这类**旧语料口径的低精度正则化结论已作废**——
  它测的是「更新被舍掉后」的行为，不是低精度计算的行为。

**要真正降访存只有稀疏化一条路**（M6 读出目前 100% 稠密）：量级与论证见
《并行与加速架构分析》§五。

## 五、线程治理（BLAS / numba / OpenMP）

在 191 核机器上，**线程设置本身就是头号性能杠杆，也是最容易反噬的地方**。

### 5.1 三个必须知道的时序约束

| 约束 | 原因 | 违反后果 |
|---|---|---|
| BLAS 线程上限必须在 **`import numpy` 之前**设 | OpenBLAS 初始化后再设环境变量**无效** | 191 线程去跑 1024×2048 的 sgemv → 1.1–3.2 核 + 250 万 CS/s |
| `numba.set_num_threads` 必须在**任何核首次执行之前** | 线程池在首次调用时定型 | 191 线程跑千行级 `prange` → 纯空转 |
| `OMP_PROC_BIND` 必须在**numba 初始化之前**进环境 | 绑核在 OpenMP 初始化时生效 | 绑核不生效，且无法事后补 |

生效情况看启动行 `[parallel] …`。

### 5.2 为什么上限是 8 而不是更多

实测：**核内 1 → 6 线程仅 1.16×**，瓶颈是内存流量（两张 ~64 MB 哈希表远超 L3）。
本机融合核带宽墙同样是 1→8 线程 4.1 → 9.3 GB/s 的次线性曲线。
→ **超过 8 线程不再有收益，只增加调度与空转成本。**

### 5.3 已回滚的配置

| 配置 | 状态 | 依据 |
|---|---|---|
| `OMP_PROC_BIND=close` | **保留** | 绑物理核而非到处迁移 |
| `OMP_PLACES=cores` | **已撤** | 191 核 place 表 → 每次线程池同步都要遍历 → M2 再慢 **8×**（19–32 ms/tok）、CS/s 升到 650 万 |
| 核内 `prange`（词涌现） | **已回退** | 1→6 线程仅 1.16× |
| 局部词表复用 | **已放弃** | 破坏正确性。**性能优化先过对拍** |
| `torch.npu.utilization()` 遥测 | **禁用** | 它同步设备流，在热路径上砍一刀 |

> **教训**：绑核类环境变量在**超多核机器上可能反噬**（place 表规模 = 核数）。

## 六、平台差异铁律（x86 ≠ aarch64，三次反噬）

| 改动 | x86 | 昇腾 |
|---|---|---|
| M1 编码器 fp32 | 快 **1.80×**（606.7 → 337.7 µs） | **慢 70×**（0.85 → 58 ms） |
| M2 融合核 | 快 **1.15–2.16×** | **慢 8–13×**（2.4 → 19–32 ms） |
| `OMP_PLACES=cores` | 无感 | **慢 8×**、CS/s 650 万 |

补充：fp32 权重 @ fp64 输入在 **x86 上就已经慢 5.9×**（脱离 BLAS 的逐元素慢路径）——
这是唯一一条在两个平台都成立的规则：**GEMV/GEMM 前必须 `W.dtype == x.dtype`**。

> ### 规则：x86 的性能结论不构成昇腾证据。
> 任何优化必须在**目标机器**复测。本文档中凡标「本机」的数字只在本机成立。

## 七、被否决的优化（负收益同样是结论）

四次连续否决，全部**已回滚**。共同结论：在访存/调度受限的规模上，**加并行度不是免费午餐**。

| # | 优化 | 实测 | 死因 |
|---|---|---|---|
| 1 | `learn_predictive` 融合核 | 26 万边 1.36× / 105 万边 **0.96×** / 419 万边 **0.91×** | 12 个 `prange` 段的线程调度成本 > 省下的 11 次核启动；191 核服务器只会更差。**保留函数、停止调用**（验证脚本改为回归护栏） |
| 2 | LTM 表向量化 | `predict` 48/512/2048 行 = 1.00× / 0.92× / 1.36×（**无规律**）；`learn` **0.74×** | 原版靠 `ltp <= 0` 短路让循环极便宜，预取/向量化**无条件付出**。**分支密集的代码不要预先向量化** |
| 3 | `gather + prange` | 800×800 组合，0.36 → 0.38 ms（**0.96×**） | gather/scatter 的 `O(R·m_out)` 拷贝吃掉并行收益；且多步序列**逐位不一致**（误把结构可塑性绑到 `growth_guidance`） |
| 4 | `encode` numba 化 | **0.84×**（多次跑 0.84–1.75× 波动） | 核内去重是线性扫描，Python `set` 是 O(1) 哈希。核函数留在文件里仅作记录 |

**教训**：① 负收益立即回滚，不留「也许大项目会好」的代码；
② **逐位对拍的基线必须是同库、同fastmath 口径的串行实现**，否则满屏假阳性；
③ 优化「形状/顺序」的代码时，**对拍是唯一防线**（纯计时看不出段序错位，结果仍「跑得动」）。

⚠ **已知门禁缺口**：`encode` numba 核**无计时护栏**——「回退了所以没人会再误用」，
但核函数还在文件里，下次有人看到它会以为它可用。

## 八、本机（x86 8 核）明细

⚠ 以下数字**只在本机成立**，不可外推到昇腾，**也不构成本项目的性能结论**——
本机只用于回归检测。

| 项 | 实测 | 说明 |
|---|---|---|
| 词表扫描 | 33.4 亿 tokens / **500 s**（191 核服务器） | head/full 扫描；`--vocab-scan full` 数小时级 |
| 词表结构构建 | 5 万词建 trie **265 s → 0.48 s** | 修复 O(节点×词表) 卡死：一次遍历邻接表 + BFS 展平 |
| 锚点链扫描引擎 | 8.30 → **21.41 Mchar/s（2.58×）** | `tokenizer_core.py`：`@njit(nogil=True)` 的 CSR-trie 贪心轨道 + δ 前缀链 + 线程池（共享内存、零 pickle）。**原热路径是纯 Python dict/set 查找，全程持 GIL → 单纯线程化只能单核**，故先编译为释放 GIL 的机器码再线程化 |
| 查找结构自适应 | 5 万词表 0.66 → **11.59 Mchar/s（17×）** | 小词表 CSR 二分 / 大词表边哈希（阈值 2 万边），best-of-3 |
| 词涌现 | 4.7M 字符 63.1 → **9.0 s（7.00×）** | numba nogil（hash 去重 + 边回比 + 解析式熵）+ 层间线程池，逐位一致 |
| 组大小 | 32M → **1M 字符** | 32M 组时并行度塌缩（组数 ≪ worker 数），且每组数百万 token 的字符串 pickle 成单点 |
| 数据加载 | **预取默认 1 进程** | pyarrow 解码在库内多线程且释放 GIL，单进程即吃满核；多进程只增内存（每进程 ~100–200 MB） |
| 在途数据量 | 深度 64 → **8192** + `--prefetch-batch` | ⚠ 深度受**按文件序归并**约束：单生产者时囤积≈0。真正有效的是 `--prefetch-workers` 与 `--prefetch-batch` |
| numba 编译缓存 | 冷启动 3.96 → **2.60 s** | 全部 `@njit` 带 `cache=True`（唯一例外 `inline="always"` 小辅助，与 cache 互斥） |
| `torch.compile` | 开 26.34 vs 关 30.98 ms/tok（快 15%） | **现默认关**（inductor 首次调用才编译，昇腾失败会崩生产） |
| CPU 侧预计算 | onehot 14.12 → **0.33 µs（43×）** | ⚠ 占端到端仅 **0.069%**——方向对但量级很小。大头在 M2 推理（状态依赖无法预计算） |
| 读出参考路径 | fp32 **40.9 ms/token**（读出规模 9,219×3,072） | ⚠ **小栈口径**，与 1B 档（51,962×3,072）**不可混用** |

**读出精度的性能含义**：低精度在本机 CPU 上是**计算受限**，收益只在存储压缩与
加速器原生张量核。本机更新核实测 fp32 **13.3 ms**、fp16/bf16 **226 ms**
（位运算重量化 > 带宽节省）；fp8 仅昇腾/CUDA 有原生 matmul，CPU 回落 fp16。
fp4 当前逐张量缩放不足（块缩放 MX 已立项，未启用）。

**门禁**：

| 项 | 状态 |
