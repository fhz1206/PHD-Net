## 0. 为什么现在才做这件事

P113 之前，CPU 侧 9.95 ms > NPU 侧 7.68 ms，重叠的理论收益上限是
`9.95 − 7.68 = 2.27 ms`（占端到端 17.63的 12.9%）——**回报有限，且要动训练主循环**。

P113 把 M2 从 6.92 打到 1.28 ms 之后，格局反转：

| | P113 前（serial） | P113 后（plain） |
|---|---|---|
| CPU 侧 | 9.95 ms | **4.26 ms** |
| NPU 侧（读出） | 7.68 ms | **7.83 ms** |
| 端到端 | 17.63 ms | **12.09 ms** |
| 读出占比 | 43.5% | **64.7%** |
| 完全重叠的理论上限 | 9.95 ms（1.77×） | **7.83 ms（1.55×）** |

**现在 NPU 是 CPU 的 1.84 倍**，重叠的潜在收益（4.26 ms，占端到端 35%）才刚够得上
值得动主循环的工程量。而且它不与任何其它优化冲突——读出那段本来就独占设备。

## 1. 当前的串行结构（`phdnet/model.py::step`）

```
token t:
  ┌─ CPU ──────────────────────────────────────────────┐
  │ M1_encode      1.03 ms   编码 x → s0                │
  │ M2_infer       1.28 ms   预测编码推理（prange 行并行）│
  │ M3_pred        0.04 ms                             │
  │ M5_mod         0.02 ms                             │
  │ M4a_wm         0.06 ms                             │
  │ M4b_imprint    0.40 ms   ┐                          │
  │ M4b_ltm        0.40 ms   │ 0.80 ms                  │
  │ construct h               │                         │
  └────────────────────────────┼─────────────────────────┘
                               ↓ H2D（pinned, async）
  ┌─ NPU ──────────────────────────────────────────────┐
  │ M6 forward_dev  gather +Σ → y_dev                   │
  │ M6 learn_softmax  7.83 ms（含 softmax/CE/rank-1）   │
  │ nll 每 8 步同步一次（P34）                          │
  └────────────────────────────┼─────────────────────────┘
                               ↓ D2H（仅 nll）
  ┌─ CPU ──────────────────────────────────────────────┐
  │ PC_learn        （在读出之后，见 model.py 的        │
  │                  `_prof_t('PC_learn')`）             │
  └────────────────────────────────────────────────────┘
```

**实测吻合**：`4.26 + 7.83 = 12.09 ms`，与日志端到端**逐位一致** → 确认是完全串行，
没有任何隐含的重叠。

## 2. 三种重叠方案（按风险递增）

### 方案 A：读出异步化 + 下一 token 的 CPU 侧提前算（**推荐**）

**核心洞察**：读出的**前向**只需要 `h`，而 `h` 在 CPU 侧链走完就有了。真正必须
串行的是「读出的**更新**」→ 「下一个 token 的 M3 需要 `_prev_rate`（读出的输出）」。

所以：**把 token t 的读出更新提交到 NPU 队列后不等它，立刻开始算 token t+1 的 M1–M4b**，
在 token t+1 到达读出之前，再回头等token t 的读出完成。

```
时间轴 →
CPU:  [M1..M4b]_t  [M1..M4b]_{t+1}  [M1..M4b]_{t+2}  ...
NPU:            [RO_t]  [RO_{t+1}]  [RO_{t+2}]
                 ↑RO_t 需要 _prev_rate（来自 RO_{t-1}）
```

**依赖链的真实形状**（这是能不能做的关键）：

| 跨 token 依赖 | 从哪来 | 能否提前 |
|---|---|---|
| `_prev_rate` ← 读出的 y | RO_{t−1} | ❌ 必须等 RO_{t−1} |
| `_prev_pc` ← M2 的 e0 | M2_{t−1}（CPU） | ✅ 同侧，不构成跨设备等待 |
| M4b `prev` ← 上一 token 的 active | CPU | ✅ 同侧 |

`PC_learn`（在读出之后）依赖读出的 y → **它是真正的串行点**。

**收益上限**：把 CPU 侧 4.26 ms 藏进 NPU 的 7.83 ms 里 →
端到端 `max(4.26, 7.83) = 7.83 ms`，即 **12.09 → ~7.9 ms（1.53×）**。

**必须解决的三件事**：

1. **读出返回 numpy 的同步点**。`nll_sync_every=8` 已经把 nll 同步降到每 8 步一次，
   但 `learn_softmax` 仍需 `correct` 索引（主机侧，零成本）。真正的阻塞点是
   `forward_dev` 后如果调用方要 numpy → 必须显式提供「设备张量直传下一 token」的路径。
   **好消息**：模型已经在走 `forward_dev`（`model.py` 有 `getattr(self.readout, "_is_accel", False)`
   分支），这条管子已经铺了一半。
2. **`PC_learn` 的串行点**。它必须等 RO_t 的 y。可选：
   (a) 把 `PC_learn` 移回 CPU 侧、与下一个 token 的 M1 并行（**推荐**，它本来就是 CPU 机制）；
   (b) 让 PC_learn 读设备上的 y（它是 CSR matvec，上设备代价大于收益）。
3. **状态推进顺序**。`_prev_rate` / `_prev_pc` / `step_count` 的推进必须严格保序，
   不能因为「token t+1 的 M1 提前算」而错位。**这是本方案最大的风险点**——
   保序错了会静默改变学习规则（而不会崩）。

**新增开关**（铁律④：默认关闭）：
```
--pipeline-depth 0   # 0=关闭（当前行为，逐位不变）；N=预取 N 个 token 的 CPU 侧
```

**门禁**：
- 新建 `tests/verifiers/verify_pipeline.py`：同一 seed 下，`--pipeline-depth 0`
  与 `N=1/2/3` 的 **PPL 轨迹逐点对比**（不是最终 PPL，是整条轨迹）；
- `--help` 门禁自动覆盖；
- **零回归判据**：depth=0 必须与当前默认**逐位一致**（否则方案本身有 bug）。

**风险评估**：中高。收益 1.5×，但要动训练主循环 + 状态保序。

---

### 方案 B：把 M4b（0.80 ms）移出关键路径（**低风险，先做**）

M4b 的 imprint 是**写**（事件驱动），recall 是**读**。当前每步都做 imprint（0.40 ms）
+ 每 8 步做一次 recall。两者的**时机自由度**比 M1/M2 大得多：

- imprint 可以延后 N 步批量做（神经科学上这叫「突触巩固的时间整合」，
  仓库里 `minibatch_size` 已经是这个思路）；
- recall 只在需要时触发。

**收益**：0.80 ms → ~0.1 ms，端到端 12.09 → **~11.4 ms（1.06×）**。

**为什么不先做这个**：收益小。但它**便宜、无语义风险、且是方案 A 的前置练习**
（同样涉及「跨 token 延后执行 + 保序」）。如果方案 A 保序做对了，B 基本白送；
如果 A 失败，B 仍有 6% 的独立价值。

**门禁**：`verify_ltm_learn_batch` 已有 5 例对拍（批量 learn），扩展它即可。

---

### 方案 C：读出内部再优化（**收益已接近上限**）

读出 7.83 ms 里有几处可疑空间，但**天花板不高**，因为：

1. **带宽账（`tools/diag_readout_npu.py` 实算，1b 档真实参数）**：
   稀疏臂每步触达 **229.15 MiB**（idx 50.74×2、val 25.37×3、临时 g 25.37×2、
   dp 0.59），按 HBM ~800 GB/s（**估算**）算下限 **0.300 ms**。
   实测 7.83 ms = 下界的 **26.1×** → **不是带宽饱和，是算子效率问题**。
   与并行文档按另一口径复算的 492.5 MB / 0.62 ms / 12.6× **方向一致**
   （都远离带宽下界）但绝对值差 2.1 倍（口径不同：是否计idx 与临时张量）。
   ⚠ 两个数字都是估算，都别当实测。
2. **可疑点 1（已量化）**：`self.W * g` 每步物化一个 `(n_out,k)` fp32
   = **25.37 MiB**，前向与更新各一处 → **50.74 MiB/步的纯临时流量**，
   占总触达 **22%**。gather 本身已跨 forward→learn 缓存（`_cache_g_epoch`），
   但乘法结果每次都要重新物化。→ 可试：`torch.compile` 融合
   「mul + sum(1)」，或分块累加避免整块临时张量。
3. **可疑点 2**：`learn_softmax` 里 `(self.W * g).sum(dim=1)` 是
   **逐元素乘 + 归约**，两个 (n_out,k) 级张量运算。昇腾上这类操作可能
   远慢于 BLAS 级gemv → 值得试把稀疏前向改写成 **CSR SpMM**
   （`torch.sparse.mm` 或 `segment_reduce`），让设备用稀疏专用算子。
4. **可疑点 3**：softmax + cross_entropy 是 (n_out,) 上的小张量运算，
   在 NPU 上launch 开销占比可能很高（一个 51,962 元素的 kernel ≈ 几十 μs）。
   P38的 `torch.compile` 融合本来是为这个设计的，但**默认关**
   （P58：服务器上不稳定）。现在稀疏路径已不用融合核（`_compiled=False`），
   可以重新评估是否对稀疏路径单独开。

**收益估计**：若能把 7.83 压到 3 ms，端到端 → ~7.3 ms（1.65×），
**比方案 A 的 1.53×还好，且不碰训练主循环**。

**门禁**：`tools/bench_accel.py`（三档 + 等效带宽 GB/s）+ `verify_accel_sparse` 39 例。

## 2.5 ⚠ P117 依赖链核实：方案 A 的收益被**高估了约 4 倍**

写完上面的方案 A 之后，我读了 `model.py::step` 的**实际编排顺序**，
发现 §2 方案 A 假设的「把 CPU 侧 4.26 ms 全藏进 NPU 的 7.83 ms 里」**不成立**。

实际顺序与依赖（`phdnet/model.py::step` 代码事实）：

```
step(t):
  M1_encode → M2_infer → M3_pred → M5_mod → M4a_wm → M4b_*     ← CPU
  → M6 forward_dev + learn_softmax                                ← 设备
  → PC_learn   (CPU，用 cache = **本步** M2 的输出)
  → STDP_learn (CPU，用 self._prev_rate 与**本步** rate)
跨 token 状态：_prev_rate ← rate(t)（读出输出）、_prev_pc ← 本步 M2 cache、
              bigltm._prev ← cur(t)
```

**能安全重叠的只有 `M1(t+1)`**（1.03 ms）：它只依赖 `x(t+1)`，不依赖 t 的任何状态。

**不能重叠的部分**：
- `M2(t+1)` 依赖 PC 权重，而 PC 权重在 `PC_learn(t)` 里更新；
- 而 `PC_learn(t)` 在 `M6(t)` **之后** →
  **M6(t) → PC_learn(t) → M2(t+1) 是一条不可打断的串行链**；
- `STDP_learn` 依赖 `_prev_rate`，而它来自读出输出 → 同样在读出之后。

| 段 | ms | 能否与 M6(t) 重叠 |
|---|---|---|
| M1_encode(t+1) | 1.03 | ✅ **可**（只依赖 x） |
| M2_infer(t+1) | 1.28 | ❌ 等 PC_learn(t) |
| M3/M4a/M4b | 0.90 | ❌ 用本步 rate / LTM 状态 |
| PC_learn / STDP | — | ❌ 在读出之后 |
| **可重叠合计** | **1.03** | 上限 `max(7.83−1.03, …) ≈ 6.80` |

**修正后的方案 A 收益**：`12.09 → ~11.1ms`（**约 1.09×**），而非 §2 估的 1.53×。

### 更值得做的替代：把 `PC_learn` / `STDP_learn` 移到 M6 **之前**

这两个段目前在读出**之后**，但它们用的 `cache` 与 `rate` 都来自**本步的 M2**，
**不依赖读出输出**（唯一依赖读出的是 `STDP_learn` 里的 `_prev_rate`，
而那可以用**上一步**的 `rate`——已经是对的了）。所以：

```
现状：... M2(t) → M6(t) → PC_learn(t) → STDP_learn(t) → [M6(t+1)]
可改：... M2(t) → PC_learn(t) → STDP_learn(t) → M6(t) → [M1/M2(t+1) 与 M6 重叠]
```
这样 PC_learn 的 CPU 时间（本来就排在读出后面）可以与**下一次**读出重叠。
但⚠ **这会改变状态推进顺序**（`_prev_pc` 的赋值时机），是语义变更，
且 PC_learn 若参与 `eta_pc` 的自适应则更敏感。**需要独立验证。**

**结论**：方案 A 仍值得做（1.09× + 解锁后续流水），但**不要**按 §2 的 1.53× 期待。
且在方案 C 落地、读出压到 ~3 ms 之后，CPU 侧 4.26 ms 会成为新瓶颈，
届时方案 A 的收益会变成 `4.26 − 3 = 1.26 ms`（约 1.1×）——**仍然不大**。

     ⚠ 需要服务器 A/B，CANN 对稀疏算子的支持情况要实测

第 3 步（高风险，最后做）
  └─ 方案 A：--pipeline-depth 流水

     （因为那时剩余的 CPU 时间已不足 1 ms，重叠收益变小）

第 4 步（可选）
  └─ 幂律异质连接（sparse_alloc.py 已实现但未接入 readout）

**为什么不先做方案 A**：它的收益（4.26 ms）建立在「NPU 7.83 ms 不变」的前提上。
如果先做方案 C 把读出压到 3 ms，那CPU 4.26 就成了新瓶颈，重叠收益变成
`4.26 − 3 = 1.26 ms`（占端到端 ~17%）——**那时候方案 A 的工程量就不值了**。
**先压读出、再谈重叠，顺序不能反。**

## 4. 诚实边界

- 本文的**全部收益数字都是估算**，基于「实测 CPU/NPU 分段耗时 + 理想重叠」，
  **没有任何一条来自实测的重叠实验**。真机上的实际收益会被H2D 延迟、
  队列深度、Python 调度开销吃掉一部分。⚠ 禁止把这些数字当承诺。
- **x86 的结论不构成昇腾证据**（本项目已实测到三次方向相反的案例）。
  方案 C 的 SpMM 是否真快，**只能在服务器上测**。
- 方案 A 触及**训练主循环与状态保序**，是本项目至今最容易引入静默语义漂移的地方。
  逐 token 语义（铁律③）在这里不是约束而是**必须严格保住的东西**。
- CS/s 稳态只有 ~90 万而 NPU 显示 99%：P112 已修掉一个每步 `torch.equal` 硬同步。
  **已用 `tools/diag_readout_npu.py` 静态复查：读出热路径现已无同步点**
  （`W_cpu` / `_csr` / `forward` 里的 `.cpu()` 分别只在存盘、检查点恢复、
  旧 numpy 接口路径上，不在每步热路径）。⚠ 但静态扫描不等于运行时结论——
  真正判据仍是服务器日志的「读出 X ms/tok」与 CS/s；
  若要进一步确认，可在服务器上做「`--nll-sync-every=1` vs `8`」的 A/B
  （若两者读出耗时相同 → 确无隐藏同步；若 1 明显更慢 → 还有同步点）。

## 5. 外部 AI 分析的核对结果（StepFun Studio，2026-10-01）

有人拿外部 AI（StepFun Studio）对这个仓库做了一轮加速分析。它的**数据基于旧版文档**
（读出 5.5–7 ms、`conn_k` 尚未在加速器实现、M2 还是 6.92 ms），所以**方案一（稀疏化）
我们已经做完了**。但它有几条独立洞察，逐条核实如下（**已实测的才写**）。

### 5.1 ✅ 成立：计时是累计平均，会系统性高估稳态成本

**它的原话**：`_ro_ms_accum / _ro_calls` 是从 token 0 起的累计平均，
所以「当前瞬时成本低于打印值」。

**代码事实（已核实）**：`phdnet/model.py::_prof_end` 是
`self._prof[name] = self._prof.get(name, 0.0) + dt` —— **从不清零**；
打印时除以 `i - done`（总步数）。故 `segments:` 与 `readout X ms/tok`
**都是历史平均**。这解释了为什么 `readout` 从 28.77 一路"衰减"到 7.68
——**不是模型变快了，是早期昂贵样本（numba 首次编译、设备 kernel 首次编译）
被摊薄**。

**已落地修复（P115）**：并行维护滑窗累计 `_prof_win` / `_prof_win_n`，
训练循环每个打印间隔调`reset_prof_window()`，日志现在**同时打印两个口径**：
```
segments(cum): M2_infer 6.92  M1_encode 1.12 ... ms/tok     ← 历史平均（原有）
segments(win): M2_infer 1.28  M1_encode 1.03 ... ms/tok  [500 steps]  ← 区间真实值
```
⚠ 踩坑：滑窗分母**不能**在 `_prof_end` 里自增——`M2_infer` 一步内可能出现多次
（循环内调`infer`），实测 300 步被数成 **2095**。正确做法是 `step()` 开头
显式调 `_prof_step()` 计一次步。

**这条改变了我们看日志的方式**：此前所有 `segments` 数字都混着启动期开销，
**M2 改plain 后的真实稳态收益比 5.41× 可能更大**（待服务器用双口径复测）。

### 5.2 ❌ 已否：h 的稀疏度远不够，列稀疏不是「HUGE insight」

**它的原话**：读出的 rank-1 更新 `ΔW = -η·y⊗h` 在 h 上是**列稀疏**的，
若 h 密度 12.5% 则更新流量能从 640 MB 降到 80 MB，「HUGE insight」。

**实测（本机，256维栈，`_build_h` hook 299 步）**：

| 分量 | 稀疏度（\|x\|>1e-12占比） |
|---|---|
| `r2`（M2 tanh 输出） | **100%**（tanh 输出无零） |
| `pred`（M3 输出） | 8.89% |
| **`h = [r2; WM; pred]`** | **69.63%**（p10 68.4% / p90 70.8%） |

**结论：h 只有 30% 稀疏**，列稀疏最多省 30% 流量，不是 8×。
它自己也标了「先测密度再确认」——测完就是这个结果。**该方向收益被高估了约 25倍**。

### 5.3 ⚠ 部分成立：CANN 自定义融合算子

它建议写 CANN 自定义算子消除「launch/sync 缺口」（估 4.9 ms）。
**方向与我们计划里的方案 C 同向**，但它的 4.9 ms 是从旧日志（读出 5.5–7 ms）
推的，**在 P113 之后读出已占 64.7%（7.83 ms）**，缺口比例需重测。
且CANN 算子开发成本高，**建议先用 `torch.compile` 融合试**（见计划 §2方案 C，
稀疏路径现在`_compiled=False`，P38 的融合逻辑可复用但从未在稀疏路径验证过）。

### 5.4 ⚠ 部分成立：CSR 索引压缩到 4 B/突触

它建议列索引 `int64 → uint16`、值 `fp32 → bf16`，把 16 B/突触压到 ~4 B。
**数学上成立**（`n_h=3072 < 65535`，uint16 装得下列索引）。
但⚠ **两个坑**：
1. **bf16 值会触发 P110 已实测的语义退化**（非目标行更新保留率仅 5.79%）——
   值不能降到 bf16，只能是 fp32；**只有索引能压**（8 B → 2 B，1.43× 而非 4×）。
2. 昇腾 gather 对 uint16 索引的支持需实测（可能触发类型转换反而更慢）。
按当前实测流量 229.15 MiB估算，仅压索引 → 约 179 MiB（省 22%），**不是它说的 96×**。

> 🔴 **P186 进展【已删除臂历史，不可复现】**：当时 CPU 侧 u16 压缩 idx 的 Rust SpMV 核
> **已实现**（`phdnet_rs/src/m2_csr.rs::phdnet_m2_matvec_u16`，AVX2 零扩展 gather，
> 数值与 i32 核逐位一致，每突触 8B→6B 理论上限 1.33×）。
> **该文件已随 `phdnet_rs/` 于 P188 整体删除** —— u16 压缩 idx 的 CPU 侧实现**当前不存在**，
> 昇腾侧也一直未实测。⚠ 若要重做 u16 索引，只能在现存 numba /（可选 Cython）核上实现。

### 5.5 ✅ 值得跟进：数据集 `unk 47%`

它指出「若 47% token 是 unk，修复它 = 有效 token 密度提升 = 等价于训练加速」。
这与我们记忆里那条「远程分片 zh 仅 2%、unk 47%」的未决项**是同一件事**，
且视角不同：我们把它当「数据质量待核」，它指出这是**算力浪费**。
⚠ 但需先核实 unk 是否真是「代码混进语言标签的代码」——**若属实，修复它是所有优化里
单位收益最高的一项**（不需要动任何机制，只改数据制备）。
**注意这与本文件其余部分不同：它不是性能优化，是"不做无用功"。**

### 5.6 它明确「不建议做」的（与我们的判断一致）

写批处理/加卡（DDP 无对象，逐 token 语义）、追低精度读出（int8 吞 |dp|~1e6，
P110 已实测）、加 `OMP_PLACES`（已实测慢 8×）、继续调prange 线程数
（P22 已实测带宽饱和）。**这四条与我们已否决的完全重合，说明它的分析框架是对的。**
