# 文档写作规范（长期有效）

> 适用范围：本仓库**全部 16 份文档**（清单见 §3）。目的是**同一事实只有一处权威出处**、
> 数字永远带口径、不再出现「同一组数字抄在 4 份文档里然后漂移」。
> **数据截止：2026-10-02（P113）。** 与代码冲突时**一律以代码为准**，并回头修文档。

## 1. 硬性规则

1. **一个事实只在一处写**（见 §3 分工表），其它地方**链接引用**，不复制数字。
2. **数字必带口径**：机器（x86 8 核 / 昇腾 191 核）、档位（smoke / 1b / 1b_max / 30b）、
   版本（P 编号或 commit）、单位（ms/tok）。正例：`12.09 ms/tok（1b 档，昇腾 191 核 + NPU，
   P113，日志 -182721.log）`。⚠ **口径的完整形态还包括「哪一段日志/哪个工具」**——
   同一档位同一平台在不同 run 上可以差很多（P111 17.63 vs P113 12.09 就是同档位同平台）。
3. **每份文档开头必须写**：适用范围 + 数据截止日 + 相关文档链接。三项缺一不可。
4. **历史值必须显式标注**：写「旧口径 78.16 只存于 git 历史，不可混用」是好的；
   直接拿旧值做论据是不好的。
5. **表格只放并列事实**。有因果、有论证、有取舍的内容写成正文段落。
6. **中文正文 + 英文标识符**。命令、参数、字段名保持原样，不翻译。
7. **参数以源码为准**：写任何 CLI 参数前先 `grep add_argument` 核一遍，不照抄旧文档。

## 2. 项目事实基线（2026-10-01 P113，写文档时的唯一依据）

### 2.1 铁律四条

① 禁自注意力 / 位置编码 / 堆叠层。
② 每个机制须有神经认知对应。
③ **逐 token 语义**：状态跨 token / shard / epoch 连续演化，读出 W 每步原地更新
→ **不允许批处理**。
④ 行为变更以 config 开关承载且**默认关闭**（例外：`csr_online` / `k_sparse` default-on）。

### 2.2 六机制与容量账

| 机制 | 口径 |
|---|---|
| M1 稀疏分布式编码 | k-WTA，输出 **12.5%** 稀疏 |
| M2 预测编码主干 | CSR，`conn_k = n//8` → **12.5%** |
| M3 STDP 时侧向 | `m_lateral=16` → **1.56%**，**只走 numba CPU** |
| M4a 工作记忆 | PFC 漏整合 + 摘要槽 |
| M4b 大容量事件驱动稀疏表 | 1B 档 2²⁴×**72** = **1,207,959,552** 突触 |
| M5 神经调制 | 调制器门控学习/写入 |
| M6 读出 | 稀疏感知器 + softmax。库 `readout_conn_k=0`（稠密），生产 CLI 默认 **128**（4.2% 连接率，P108）|

**1B 档容量（`train/config_1b.py::capacity_report` 实跑，V=51,962，同词表）**：

| `readout_conn_k` | 固定突触 | 读出 | 大空间表 | 总容量 |
|---|---|---|---|---|
| 0（稠密） | 162,266,112 | 159,627,264（= 51,962×3,072 稠密等价） | 1,207,959,552 | **≈1.370e9** |
| **128（生产默认）** | **9,289,984** | 6,651,136（稀疏） | 1,207,959,552 | **≈1.217e9** |

⚠ **三个历史数字都曾经正确，口径不同，不可混用**：
`1.317e9` 是 `big_ltm_m=60` 时代；`1.370e9` 是**同词表 + 稠密读出**；
`1.217e9` 是**生产配置（conn_k=128）**。差值恰为读出的稠密/稀疏之差
（159,627,264 − 6,651,136 = 152,976,128）。写容量数字**必须带 `readout_conn_k` 与词表**。

### 2.3 语料

- 冻结基准**在仓库根 `eval_corpus/`**，不在 `datasets/`：
  `internal_corpus.txt` **27,034 字符**原文长度，按 `int(len*0.8)` 划分为
  **21,627 训练 / 5,407 评估**；`ood_wiki.txt` **20,187 字符**（OOD 探针）。
- 训练数据两入口：本地 `datasets/`（独立仓库）或 `--remote-data`
  （ModelScope `fhzfhz/Mixture-General-Mini`，HTTP Range 流式零落盘）。
- 远程分片实测语种：**en 50% / unk 47%（实为代码，CJK 0%）/ zh 仅 2%**——
  与早期记录「中文 95%」**直接矛盾**，标为**待核**（数据问题，非训练代码问题）。

### 2.4 精度现状

- 读出默认 **fp32**（P110，CLI 与库 config 一致）。动机是**学习精度**，不是访存：
  实测非目标行更新保留率 **fp32 99.95% / fp16 26.67% / bf16 5.79%**（|dp|~1e-6 档，
  `tools/probe_readout_precision.py`）→ 低精度下「只提升目标行」= **纯 Hebbian 退化**。
  ⚠ 曾有「fp16 半 ULP 只有 bf16 的 1/8，能保住更新」的估算，被实测推翻。
- **fp8 / fp4 在所有加速器禁用**（实测昇腾 Ascend910B4 + CANN 8.5 + torch_npu 2.9
  全 ERR01007；CPU torch 无 fp8 addmv）。仅 `--accel cpu --readout-dtype fp8` 可用
  ——那是 numba CPU 路径的量化核，不是加速能力。
- M1 编码器：库 `config.encoder_dtype=fp64`（形状参数默认），**生产 CLI 覆盖为 fp32**；
  昇腾走P77 平台自适应 numba GEMV（`_gemv_rows`，与 dtype 无关），x86 走 BLAS。
- 分词 onehot 缓冲 **fp16**（值域 0/1，无损）。
- 检查点：低精度存**位模式**（uint16 / uint8），加载侧按 `ckpt_dtype` 解码闭环。

### 2.5 性能（1B 档，昇腾 191 核 + NPU）

- **现行基线：2026-10-01 P113 实测**（`--m2-kernel plain`，日志
  `train_1b_1b_pretrain_20261001-182721.log`）：**12.09 ms/tok**。
  稳态分段：**读出 7.83 ms（64.7%，NPU）** / M2_infer **1.28**（10.6%，**行级
  prange，不再单核**）/ M1_encode 1.03 / M4b_ltm 0.40×2 / STDP 0.06 / M3 0.04 /
  tokenize 0.02 / encode_onehot 0.02。CPU 侧合计 **4.26 ms**（35.2%）。
  遥测：**进程仅用 1.1/191 核（0.6%）而 NPU 99%**。
- **历史对照（P113 之前，`--m2-kernel serial`，日志 `...-172245.log`）**：
  **17.63 ms/tok**，其中 **M2_infer 6.92 ms 跑在单核**（占 39.3%）、
  读出 7.68 ms（43.5%）。→ 端到端 **1.46×**、M2 **5.41×**、CPU 侧 **2.33×**。
  ⚠ **这组数字只能作为 A/B 的另一侧出现，不得单独引用。**
- **零回归**：P113 与 serial 两个 run 在四个采样点（10250/20250/30250/40250 token）
  的 sliding PPL **逐位完全相同**（38101.949 / 25042.421 / 22693.449 / 19602.394）。
- **读出诊断**：每步触达 **229.15 MiB**（`tools/diag_readout_npu.py` 实算），
  按~800 GB/s（**估算**）下限 0.300 ms，实测 7.83 ms = **26.1×**
  → **不是带宽饱和，是算子效率问题**；静态扫描确认热路径**已无设备同步点**。
- **这些数字只引用，不复算。唯一出处 = `docs/PHD-Net_性能评估与迭代方案.md`。**
  ⚠ **读出每步字节有三套口径**（稠密上界 2600 MiB / 本文复算 492.5 MB /
  P113 实算 229.15 MiB），**引用必须写清是哪一套**，详见性能文档附录 A第 7 条。

### 2.6 平台差异铁律（写性能文档必标）

| 改动 | x86 | 昇腾 |
|---|---|---|
| M1 fp32 | 快 1.80× | **慢 70×** |
| M2 融合核（`fused` vs `plain`） | 快 1.15–2.16× | **慢 8–13×** |
| **`--m2-kernel serial` vs `plain`** | **未 A/B** | **plain 赢 5.41×**（6.92 → 1.28 ms/tok，P113） |
| `OMP_PLACES=cores` | 无感 | **慢 8×** |

→ **x86 的性能结论不构成证据**。
⚠ **P113 加的推论更强**：第三行在 x86 上是「**未 A/B**」，不是「测了没差别」。
**x86 的「无差别」也不能用来推断昇腾** —— 必须去目标机器测。
