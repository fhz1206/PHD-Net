# 文档写作规范（长期有效）

> 所有 PHD-Net 文档都必须遵循。目的是：**同一事实只有一处权威出处**、数字永远带口径、
> 不再出现「同一组数字抄在 4 份文档里然后漂移」。

## 1. 硬性规则

1. **一个事实只在一处写**（见 §3 分工表），其它地方**链接引用**，不复制数字。
2. **数字必带口径**：机器（x86 8 核 / 昇腾 191 核）、档位（4M / 1B / 30B）、
   版本（P 编号或 commit）、单位（ms/tok）。例：`63.5 ms/tok（1B 档，昇腾，P70 前）`。
3. **每份文档开头写**：适用范围 + 数据截止日期 + 相关文档链接。
4. **禁止出现的表述**（除非明确标注为历史）：
   - 旧 PPL 锚点 78.16 / 90.2480 / 73.1166（2026-09-28 换了评测语料）
   - 预测值式的步时（如「预期 ~13 ms/tok」）
   - 不带平台的加速倍数（x86 与昇腾常常相反，见 §4）
   - 「fast 11 项」「全量 19/19」等旧门禁数（**现行 fast = 9 项**）
   - 「三套 CI」（**实际两套**，且仓库**没有 Jenkinsfile**）
5. **历史值要显式标注**：写「旧口径 78.16 只存于 git 历史，不可混用」是好的；
   直接用旧值做论据是不好的。
6. 中文正文 + 英文标识符；表格只放并列事实。

## 2. 项目事实基线（2026-09-30，写文档时的唯一依据）

### 硬约束
- 铁律：①禁自注意力/位置编码/堆叠层；②每机制须有神经认知对应；③**逐 token 语义**
  （状态跨 token/shard/epoch 连续演化，读出 W 每步原地更新）→ **不允许批处理**；
  ④行为变更以 config 开关承载且默认关闭（例外：`csr_online`/`k_sparse` default-on）。
- 六机制：M1 稀疏分布式编码（k-WTA）/ M2 预测编码（CSR 12.5% 连接）/ M3 STDP 时序
  预测（1.56%）/ M4a 工作记忆 / M4b 大容量事件驱动稀疏表（2²⁴×72 ≈ 1.208e9）/
  M5 神经调制 / M6 读出（**100% 稠密 = 架构欠账**，人脑连接率 2e-8、每神经元约
  1744 条突触；幂律稀疏化方案已设计未实施）。
- 容量账：1B 档总容量 ≈ 1.317e9（稀疏 88% + 稠密读出 11.6% + 编码器 0.16%）。
- 语料：冻结基准 `eval_corpus/internal_corpus.txt` **27,034 字符**（实测原文长度；
  训练段 18,803 / 评估段 4,701 是划分后口径）；`ood_wiki.txt` 为远域探针。
  训练数据两入口：本地 `datasets/` 或 `--remote-data`（ModelScope 流式）。

### 精度现状
- 读出 **`--readout-dtype` 默认 fp16**：forward 用 fp8_e4m3fn 副本（320→80 MB），
  **更新用 fp16 主副本**；`--fp8-refresh` 默认 8 步重建副本。
  动机是**学习精度**（bf16 半 ULP≈2e-4 ≫ 非目标行更新 |dp|≈1e-6 → 更新被舍 →
  退化为纯 Hebbian；fp16 主副本下本机实测 5722 个非目标行格点获得更新，bf16 下为 0）。
  **不是访存收益**（更新侧 fp16 使总访存 +42%）。fp8 matmul 仅昇腾/CUDA，CPU 回落 fp16。
- M1 编码器默认 **fp64**（昇腾 numpy GEMV 病态 → aarch64 走自写 numba 核，x86 走 BLAS）。
- 分词 onehot 缓冲 fp16（值 0/1 无损，1B 词表 208→104 KB/步）。
- 检查点：bf16/fp8 存位模式（uint16/uint8），加载侧按 `ckpt_dtype` 解码闭环。

### 性能现状（1B 档，昇腾 191 核 + NPU）
- 区间 **20–110 ms/tok**（本轮修平台差异期间波动大）。
- 读出 5.5–7 ms/tok，**访存受限**（960 MB/步：读 320 + 读 320 + 写 320），
  反算有效带宽 137–175 GB/s ≈ HBM 的 9–11%。
- 本轮修掉：M4b（曾 63.5 ms/tok，imprint 侧 aarch64 单次 ≈20 s）、
  M1 平台差异（58 ms）、M2 融合核退化（27 ms）、检查点硬停顿（0.8–37 s）。
- 191 核用不满是**架构性**：逐 token 串行 + 每步可并行工作量太小。
- **性能数字的唯一出处是 `docs/PHD-Net_性能评估与迭代方案.md`**，别处引用它。

### 平台差异铁律（写性能文档必标）
| 改动 | x86 | 昇腾 |
|---|---|---|
| M1 fp32 | 快 1.80× | **慢 70×** |
| M2 融合核 | 快 1.15–2.16× | **慢 8–13×** |
| OMP_PLACES=cores | 无感 | **慢 8×** |
→ **x86 的性能结论不构成证据**。

### 门禁与 CI
- `python tests/run_tests.py fast` = **9/9**（零回归门槛）；专项 verifier 18 个。
- CI **两套**：`.gitcode/workflows/ci.yml`、`.github/workflows/ci.yml`（镜像，
  **当前仍红**，无日志权限待 traceback）。
- 评测：256 维栈、eta_readout=0.15；现行锚点 **4K 394.4687 / 全语料 359.2603**
  （`tools/rebaseline.py`）。

### 已知开放项
M4b 复测归因 / fp8 下 PPL 是否下降 / 数据集语种（实测中文仅 2%，与文档记录矛盾）/
检查点 compact_csr（10 万行 3.9 s）/ **M6 幂律稀疏化（架构欠账）** / GitHub Actions 仍红。
